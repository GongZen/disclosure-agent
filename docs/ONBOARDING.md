# 온보딩 — 지금까지 무엇을 만들었고 다음에 무엇이 필요한가

이 문서는 프로젝트에 처음 합류하는 사람을 위한 것이다. 이전 대화나 작업을
지켜보지 않았다는 것을 전제로 쓴다. 용어는 처음 나올 때 한 번씩 뜻을 붙인다.

목적이 둘이다.

```
1  지금까지 만든 것을 이해한다 — 데이터가 어떻게 생겼고 검색이 어떻게 도는가
2  다음에 만들 것을 이해한다 — 매칭표를 어떤 구조로 왜 그렇게 만들어야 하는가
```

급하면 8장부터 읽어도 된다. 다만 7장까지가 "왜 그 형식이어야 하는가" 의
근거이므로, 8장만 읽으면 형식은 알아도 판단이 안 선다.

기준일 2026-08-31.

---

# 1. 이 프로젝트가 무엇인가

제10회 2026 미래에셋증권 AI Festival 참가작이다. 만드는 것은 공시 Agent 다.

공시(公示)는 상장기업이 법에 따라 의무적으로 공개하는 문서다. 사업보고서,
분기보고서, 계약 체결 사실, 대주주 지분 변동 같은 것이 여기 들어간다.

우리가 만드는 것은 그 공시를 근거로 질문에 답하는 시스템이다.

```
사람    "삼성전자의 주주환원 정책이 어떻게 되는지 알려줘"

시스템  삼성전자 2025년 사업보고서
        III. 재무에 관한 사항 > 6. 배당에 관한 사항
        → 그 절의 내용을 근거로 답을 만든다
```

평가는 우리가 띄운 API 서버에 심사측이 질의를 보내고 응답을 보는 방식이다.
응답에는 답변만이 아니라 근거로 쓴 공시가 무엇인지도 담아야 한다.

## 절대 금지 넷 — 어기면 실격이다

무엇을 하기 전에 이것부터 안다. 제안·설계·구현 어느 단계에서든 여기 걸리면
즉시 멈춘다.

```
1  HyperCLOVA X 외 LLM 사용 금지
     생성 모델은 HyperCLOVA X 만 쓴다. OpenAI · Gemini · Claude · Llama 전부 금지
     단 임베딩·리랭커·형태소 분석기는 제약 대상이 아니다. 생성 모델에만 걸린다

2  제공 코퍼스 외 데이터 사용 금지
     주최측이 준 공시 데이터 외에는 아무것도 안 쓴다
     뉴스 · 애널리스트 리포트 · 위키 · 웹 크롤링 전부 금지

3  외부 공시 API 실시간 호출 금지
     OpenDART 같은 것을 실행 중에 부르지 않는다

4  공시에 근거 없는 미래 예측·투자 의견 생성 금지
     주가 전망 · 매수매도 의견을 만들지 않는다
     확인할 수 없으면 "공시에서 확인되지 않음" 이라고 적는다
     이것은 감점이 아니라 평가 항목이다
```

1번이 특히 헷갈린다. 우리는 지금 OpenAI 임베딩을 쓰고 있는데 이것은 위반이
아니다. 임베딩은 글을 숫자 벡터로 바꾸는 것이지 글을 만들어내는 것이 아니다.
금지는 생성 모델에만 걸린다.

# 2. 원본 데이터가 어떻게 생겼는가

주최측이 준 것은 파일 덩어리다. 합쳐서 약 5.5GB 다.

```
assets/공시/공시/corpus/raw/
    periodic/     정기공시     사업보고서 · 반기보고서 · 분기보고서
    exchange/     거래소공시    단일판매·공급계약 체결 등
    major/        주요사항보고   유상증자 · 자기주식취득 등
    holding/      지분공시      대량보유상황보고 등
```

대상은 상장기업 70곳, 기간은 2023~2026년이다.

## 파일 하나가 어떻게 생겼나

정기공시는 XML 파일이다. 그런데 표준 XML 이 아니다. 이것이 나중에 큰 문제가
된다(5장 참조).

```xml
<DOCUMENT>
  <TITLE ATOC="Y">I. 회사의 개요</TITLE>
  <SECTION-1>
    <TITLE>1. 회사의 개요</TITLE>
    <P>당사는 ...</P>
    <TABLE>
      <TR><TH>구분</TH><TH>당기</TH></TR>
      <TR><TD>자산총계</TD><TD><TE ACONTEXT="CFY_e_ConsolidatedMember"
           ADECIMAL="-6">455,905,980</TE></TD></TR>
    </TABLE>
  </SECTION-1>
</DOCUMENT>
```

`TE` 태그에 붙은 `ACONTEXT` 와 `ADECIMAL` 이 중요하다. 이것이 XBRL 이라는
회계 표준의 흔적이고, 이 값에서 "이 숫자가 어느 기간의 것인가",
"연결인가 별도인가", "단위가 백만원인가 천원인가" 가 전부 결정된다.

```
ACONTEXT = CFY_e_ConsolidatedMember
           CFY            당기      (PFY 는 전기, BPFY 는 전전기)
           e              시점값     (d 는 기간값)
           Consolidated   연결      (Separate 는 별도)

ADECIMAL = -6   백만원 단위          (-3 은 천원, 0 은 원)
```

표 머리글을 읽어서 이것을 알아내려 하면 실패한다. 계정 이름 표기가 여섯 가지가
넘고 단위도 문서마다 섞여 있기 때문이다. 태그를 쓰면 전부 결정론적으로 풀린다.

## 사업보고서의 목차는 70개사가 전부 같다

이것이 나중에 매칭표를 만들 수 있는 근거다. 사업보고서는 법정 서식이라
기업이 달라도 같은 번호에 같은 제목이 온다.

```
I.    회사의 개요
II.   사업의 내용
III.  재무에 관한 사항
IV.   이사의 경영진단 및 분석의견
V.    회계감사인의 감사의견 등
VI.   이사회 등 회사의 기관에 관한 사항
VII.  주주에 관한 사항
VIII. 임원 및 직원 등에 관한 사항
IX.   계열회사 등에 관한 사항
X.    대주주 등과의 거래내용
XI.   그 밖에 투자자 보호를 위하여 필요한 사항
XII.  상세표
```

각 대분류 아래 소분류가 있다. `III` 아래 `1. 요약재무정보` `2. 연결재무제표`
… `6. 배당에 관한 사항` 같은 식이다. 우리는 이 위치를 경로(path) 로 부른다.

```
III/6      III. 재무에 관한 사항  >  6. 배당에 관한 사항
VIII/2     VIII. 임원 및 직원 등  >  2. 임원의 보수 등
III/2/2-1  III. 재무  >  2. 연결재무제표  >  2-1. 연결 재무상태표
```

경로가 기업마다 같다는 것이 핵심이다. 어떤 기업이든 "배당" 을 물으면
`III/6` 을 보면 된다.

# 3. 우리가 만든 데이터베이스

원문은 절대 건드리지 않는다. 읽기만 하고, 만든 것은 전부 `data/` 아래
새로 쌓는다. 원문이 변형되면 그것은 더 이상 근거가 아니기 때문이다.

데이터베이스는 `data/corpus.db` 하나다. SQLite 이고 5.4GB 다.
테이블 12개가 들어 있다. 아래 행 수는 전부 실측이다.

| 계층 | 테이블 | 행 수 | 무엇인가 |
|---|---|---:|---|
| 기준 | `company` | 70 | 대상 기업 |
| 기준 | `document` | 4,619 | 공시 문서 한 건이 한 행 |
| 관계 | `doc_relation` | 1,024 | 정정공시가 어느 원본을 고쳤는지 |
| 이벤트 | `event_contract` | 1,169 | 단일판매·공급계약 |
| 이벤트 | `event_major` | 598 | 주요사항보고 |
| 이벤트 | `event_holding` | 1,083 | 대량보유·임원소유 |
| 원자료 | `contract_item` | 24,558 | 계약 공시의 항목별 원값 |
| 원자료 | `major_item` | 83,641 | 주요사항 공시의 항목별 원값 |
| 원자료 | `holding_item` | 1,530,018 | 지분 공시의 항목별 원값. 가장 크다 |
| 사실 | `fact_financial` | 38,893 | 재무제표 숫자 |
| 본문 | `section` | 122,871 | 본문을 목차 단위로 자른 것 |
| 본문 | `chunk` | 171,564 | section 을 검색 단위로 다시 자른 것 |

`document` 는 `doc_group` 다섯으로 갈린다.

```
periodic  1,054   정기공시 — 사업·반기·분기보고서
exchange  1,469   거래소공시 — 단일판매·공급계약 등
holding   1,083   지분공시
major       598   주요사항보고
audit       415   감사보고서. 사업보고서 첨부에서 떼어냈다 (2026-08-31)
```

`audit` 이 따로 있는 이유는 감사의견을 근거로 답할 때 근거 공시가
사업보고서로 표시되면 안 되기 때문이다. 원래는 같은 `doc_id` 아래 이어
담겨 있던 것을 별도 문서로 떼어냈다. `doc_subtype` 과 `base_year` 는 부모
사업보고서에서 물려받았다. 검색이 그 둘로 거르기 때문이다.

## 계층을 나눈 이유

같은 데이터를 두 벌 담는 것처럼 보이는 곳이 있다. `event_*` 셋과 `*_item`
셋이다. 일부러 그렇게 했다.

```
*_item      공시에 적힌 항목을 그대로 담는다. 판정을 안 한다
event_*     거기서 답에 쓸 값을 추린 것. 판정이 들어간다
```

판정 기준이 바뀌면 `event_*` 만 다시 만들면 된다. 원문 5.5GB 를 다시 읽지
않아도 된다. 원자료를 남기는 값이 여기 있다.

## section 과 chunk 의 차이

이 둘의 구분이 뒤에서 계속 나오므로 확실히 해 둔다.

```
section    목차 한 칸이 한 행이다.  "6. 배당에 관한 사항" 전체가 section 하나
chunk      section 을 5,000자 한도로 자른 것. 긴 section 은 여러 chunk 가 된다
```

왜 자르냐면 임베딩 모델이 한 번에 받을 수 있는 글자 수에 한도가 있기 때문이다.

```
chunk 는 찾기 위한 단위다
section 은 답을 주는 단위다
```

검색은 chunk 로 하고, 맞았는지 채점하거나 생성 모델에 넘길 때는 section 으로
올린다. `6. 배당에 관한 사항` 이 chunk 열둘로 잘려 있을 때 그중 어느 것이
걸리든 답은 같기 때문이다.

## chunk 에 든 것

`chunk` 테이블에는 본문 말고도 검색용 데이터가 세 벌 들어 있다.

```
tokens        171,564 / 171,564    BM25 용 형태소. 채워졌다
embedding_oa  171,564 / 171,564    OpenAI 임베딩 3,072차원. 채워졌다
embedding         420 / 171,564    CLOVA 임베딩 1,024차원. 속도 측정분만
```

임베딩(embedding) 은 글을 숫자 벡터로 바꾼 것이다. 의미가 비슷한 글은 벡터도
가까워지므로, 질의를 같은 방식으로 벡터로 바꾸면 가까운 조각을 찾을 수 있다.

BM25 는 낱말이 얼마나 겹치는지로 점수를 매기는 고전적인 검색 방식이다.
임베딩이 의미로 찾는다면 BM25 는 글자로 찾는다. 둘은 서로 놓치는 것이 다르다.

## W3 에서 한 것 — 정정공시 잇기

공시는 틀리면 정정공시를 다시 낸다. 그러면 같은 사실에 대한 문서가 둘이 된다.
어느 것이 최신인지 모르면 틀린 값으로 답하게 된다.

`doc_relation` 이 "이 정정공시는 저 원본을 고친 것" 을 1,024건 이어 놓았다.
재무 값을 담을 때 정정본이 있으면 그쪽을 쓰고 원본은 건너뛴다.

## W5 에서 한 것 — 재무 숫자 뽑기

2장에서 본 `ACONTEXT` · `ADECIMAL` 태그를 1차 경로로 삼아 38,893행을 담았다.
태그가 없는 문서만 표를 파싱하는 2차 경로로 처리했다.

정확한지 어떻게 아는가. 사람이 원문을 직접 읽어 만든 정답지가 있다.

```
data/golden/golden_values.csv     22문서 × 6항목 = 132행
                                  사람이 읽어 채운 것 60행
                                  XBRL 태그로 자동 채운 것 69행
                                  빈칸 3행 (단위 불명이라 사람이 읽어야 함)
```

여섯 항목은 자산총계·부채총계·자본총계·매출액·영업이익·당기순이익이다.
앞의 셋을 고른 이유는 `자산총계 = 부채총계 + 자본총계` 가 성립해서 옮겨 적는
실수까지 잡히기 때문이다. 22문서 전부에서 이 항등식이 맞았다.

## W6 에서 한 것 — 본문 자르기와 임베딩

이 단계에서 한 번 크게 틀렸다. 다음 장에서 따로 다룬다.

# 5. 크게 틀렸던 것 둘 — 같은 함정을 다시 밟지 않기 위해

이 프로젝트에서 가장 값비쌌던 두 사건이다. 읽어 두면 비슷한 상황에서
같은 판단을 안 한다.

## 사건 1 — 파서가 표를 통째로 삼키고 있었다

W6 1차 산출물을 전량 버리고 다시 만들었다.

원문 XML 이 표준 XML 이 아니었다. 본문 텍스트에 꺾쇠가 이스케이프 없이
들어 있었다.

```
원문     <TABLE><TR><TD>제 <전기말> 기</TD></TR></TABLE>
                          ↑ 이것을 파서가 태그 시작으로 읽는다

결과     </TD>    가  <전기말> 을 닫는다
         </TR>    가  <TD> 를 닫는다
         </TABLE> 가  <TR> 을 닫는다
         <TABLE> 은 닫히지 못하고 그 뒤 문서 전체를 삼킨다
```

원인이 셋이었다.

```
본문의 꺾쇠        <배틀그라운드> 를 태그로 읽는다        문서 1,008건 · 42,002개
속성 값의 따옴표    ENG=""Snow" 에서 태그가 통째 버려진다  문서 84건 · 손실 31~68%
파일 이어붙이기     루트가 여럿이라 감사보고서가 빠진다     210건
```

`src/sanitize.py` 가 파싱 전에 이것을 교정한다. 전수 1,051건 기준으로
파서 오류 1,008→0, 깨진 표 468→0, 글자 손실 84→0 이 됐다.

```
입력   "삼성전자의 2025년 사업보고서 기준 주주환원 정책"
```

생성 모델을 안 쓴 이유는 규칙으로 충분했기 때문이다. 평가 질의 28개 중

여기서 한 번 크게 실패했다. STOP 을 과하게 걸었더니 이렇게 됐다.

```
질의    삼성전자의 사업부문 구성과 주요 매출처를 알려줘
검색어  ['사업', '회사']       ← 이것만 남았다
```

두 낱말로는 아무것도 못 가린다. 모든 사업보고서에 나오는 말이다. 잡음을

질의의 낱말이 그것과 겹치면 그 절의 조각을 순위에서 앞으로 당긴다.

## 층 3 — 찾는다  `src/retrieval.py`

세 가지를 쓴다.

```
BM25    낱말이 겹치는 정도로 점수를 낸다
벡터     임베딩으로 의미가 가까운 것을 찾는다
RRF     위 둘의 순위를 하나로 합친다
```

RRF(Reciprocal Rank Fusion) 는 두 검색 결과를 합치는 방법이다. 점수를 직접
더하지 않고 순위의 역수를 더한다. BM25 점수와 코사인 유사도는 단위가 달라
직접 더할 수 없기 때문이다.

지금 가중치는 1:1 이다. 확정한 값이 아니다.

## 지금 성적

`python scripts/eval_body.py --mode=path` 로 잰 값이다. 사례 37건.

```
              1위      3위내    8위내
경로 없음     12/37    22/37    29/37
경로 적용     14/37    23/37    29/37
```

경로를 짚으면 1위 적중이 12 → 14 로 올랐다. 8위내는 그대로다.

채점은 절 단위로 한다. 같은 절의 다른 조각이 걸려도 맞은 것으로 센다.
조각은 찾기 위한 단위이고 답을 주는 단위는 절이기 때문이다.

### 이 숫자를 그대로 믿으면 안 된다

37건 중 28건은 AI 가 질의와 정답을 모두 만든 것이다. 사용자가 만든 것은
9건뿐이다.

AI 가 질의를 만들면 편향이 들어간다. 조각을 읽고 질의를 만드니 답이 있는
것만 묻게 되고, 구현한 구조에 맞춰 묻게 되고, 약한 곳을 피해 간다.

종합 성능 검토는 평가 질의 28개의 정답지를 받는 때 한다. 정답지를 미리
받지 않는 것은 의도된 것이다. 시험지를 보고 만든 시스템은 그 시험지에만
맞춰지기 때문이다.

# 7. 지금 막힌 지점 — 왜 매칭표가 필요한가

37건 중 8건을 못 찾는다. 무작위가 아니라 두 유형에 몰려 있다.

```
1. 사업의 개요 (II/1)
   대표 낱말이 "부문" 하나뿐이고 점수가 3.8 이다
   내용이 일반적이어서 그 절만의 낱말이 안 나온다

IV. 이사의 경영진단 및 분석의견
   "실적 변화" 같은 질의가 절 이름과 낱말이 안 겹친다
   대표 낱말이 아예 안 잡혔다

무형자산 주석
   "전속 연예인" 이 회계 계정 이름과 멀다
```

## 왜 자동으로는 안 되나

지금 `pathmap.csv` 는 데이터에서 기계적으로 뽑은 것이다. 방법은 이렇다.

```
점수 = (그 절에 나오는 문서 비율) ÷ (전체 절에 나오는 문서 비율)

크면 그 절에서만 쓰이는 낱말이다
```

`배당성향` 은 `III/6` 에서만 나오므로 40.9 가 나온다. 반면 `부문` 은
`II/1` 에도 나오지만 다른 절에도 많이 나오므로 3.8 밖에 안 된다.

즉 내용이 일반적인 절은 원리상 자동으로 안 잡힌다. `1. 사업의 개요` 는
그 기업이 무슨 사업을 하는지 서술하는 절이라 어느 산업이냐에 따라 낱말이
전부 다르다. 70개사에 공통으로 나오면서 그 절에만 나오는 낱말이 없다.

그리고 재무제표 본체(`III/2/2-1` 연결 재무상태표 등)는 거의 숫자라
낱말 자체가 안 나온다.

## 사람이면 할 수 있는 이유

사람은 "질의에 이런 말이 나오면 이 절을 보면 된다" 를 안다.

```
"무슨 사업을 하는 회사인가"    →  II/1  사업의 개요
"실적이 왜 이렇게 변했나"       →  IV    이사의 경영진단 및 분석의견
"자산이 얼마인가"              →  III/2/2-1  연결 재무상태표
```

지금 시스템이 이 셋을 어떻게 처리하는지 실제로 찍어 본 결과다.

```
"실적이 왜 이렇게 변했는지 설명해줘"
    검색어  ['실적', '이렇', '변하']        짚은 절  []      못 짚는다

"삼성전자가 어떤 사업을 하는 회사인가"
    검색어  ['사업', '회사']                짚은 절  []      못 짚는다

"삼성전자의 주주환원 정책이 어떻게 되는지 알려줘"
    검색어  ['주주', '환원', '정책']        짚은 절  []      못 짚는다
```

셋 다 빈 리스트다. 사람은 어느 절인지 바로 아는데 시스템은 하나도 못 짚는다.
이 빈 리스트를 채우는 것이 매칭표가 할 일이다.

데이터에는 이 연결이 안 적혀 있다. 사람 머릿속에만 있다. 그것을 표로
꺼내 놓는 것이 매칭표다.

목차가 70개사 전부 같다는 것이 이 작업을 가능하게 한다. 한 번 만들면
모든 기업에 적용된다.

# 8. 매칭표 명세 — 무엇을 어떻게 만들 것인가

여기가 이 문서의 본론이다.

## 8.1 결과물이 어디로 들어가는가

`src/retrieval.py` 의 `guess_paths()` 함수가 이 표를 읽는다. 코드는 이렇다.

```python
def guess_paths(terms, top=2):
    """검색어로 볼 만한 절 경로를 고른다. 점수 합이 문턱을 넘어야 한다."""
    hits = []
    for path, d in pathmap().items():          # d 는 {낱말: 점수}
        s = sum(v for w, v in d.items() if w in terms)   # 겹친 낱말의 점수를 더한다
        if s >= PATH_MIN:                      # PATH_MIN = 15.0
            hits.append((s, path))
    hits.sort(reverse=True)
    return [p for _s, p in hits[:top]]         # 상위 2개만
```

동작을 말로 풀면 이렇다.

```
1  질의에서 뽑은 검색어(terms) 를 받는다
2  표의 모든 절에 대해, 검색어와 겹치는 낱말의 점수를 더한다
3  합이 15.0 이상인 절만 남긴다
4  점수가 높은 순으로 최대 2개를 고른다
5  그 절에 속한 조각은 순위를 20 만큼 앞으로 당긴다 (PATH_BOOST = 20)
```

여기서 두 가지를 꼭 이해해야 한다.

### 개수가 아니라 점수의 합이다

낱말이 몇 개 겹쳤는지는 안 본다. 점수를 더한다. 이렇게 바꾼 이유가 있다.

처음에는 개수로 셌더니 성적이 12/37 에서 10/37 로 떨어졌다.

```
질의          "주주환원 정책"
잘못 짚은 곳   IV/6   그 절의 대표 낱말에 "정책" 이 있었다
정답          III/6  배당에 관한 사항
```

`배당성향` 은 `III/6` 을 특정하지만 `정책` 은 아무 절이나 가리킨다.
개수로 세면 둘이 같은 한 표다. 점수로 바꾸니 14/37 이 됐다.

### 좁히지 않고 순위만 올린다

짚은 경로의 조각을 앞으로 당기되 나머지를 후보에서 빼지 않는다.
잘못 짚어도 정답이 후보에 남아 있게 하기 위해서다.

이것이 중요한 이유는 잘못 짚었을 때 회복이 가능하다는 뜻이기 때문이다.
표를 만들 때 "틀리면 큰일" 이라고 겁먹을 필요가 없다. 다만 문턱 아래로
설계하면 아무 효과가 없으므로 점수 설계는 신중해야 한다.

## 8.2 파일 형식

`data/eval/pathmap.csv` 와 같은 형식으로 만든다. 컬럼 6개다.

| 컬럼 | 뜻 | 예 |
|---|---|---|
| `path` | 절 경로 | `III/6` |
| `title` | 절 제목 | `6. 배당에 관한 사항` |
| `n_corp` | 그 낱말이 나온 기업 수 | `84` |
| `terms` | 낱말 목록. 공백으로 구분 | `배당성향 배당수익률 결산배당` |
| `scores` | `낱말:점수` 목록. 공백으로 구분 | `배당성향:40.9 배당수익률:41.2` |
| `top_score` | `scores` 중 최고값 | `41.2` |

실제로 코드가 읽는 것은 `path` 와 `scores` 둘뿐이다. 나머지는 사람이 보기
위한 것이다. 다만 형식을 맞춰 두면 기존 표와 합치기 쉽다.

기존 행의 실제 모습이다.

```
path       III/6
title      6. 배당에 관한 사항
n_corp     84
terms      결산월 가부 배당금총액 배당수익률 배당성향 수익률 백만원 결산배당 성향 중간배당 현금배당 주식배당
scores     결산월:42.4 가부:42.4 배당금총액:42.4 배당수익률:41.2 배당성향:40.9 수익률:37.7 백만원:37.6 결산배당:35.4 성향:34.3 중간배당:34.0 현금배당:32.4 주식배당:32.1
top_score  42.4
```

### 파일을 따로 둘 것을 권한다

기존 `pathmap.csv` 를 직접 고치지 말고 `data/eval/pathmap_manual.csv` 같은
새 파일로 만들어 달라. 이유가 둘이다.

```
1  pathmap.csv 는 scripts/build_pathmap.py 가 다시 만들면 덮어써진다
     사람이 넣은 줄이 날아간다

2  자동으로 뽑은 것과 사람이 넣은 것이 섞이면 어느 쪽이 효과가 있었는지 못 잰다
     따로 두면 켜고 끄며 잴 수 있다
```

두 파일을 합치는 코드는 이쪽에서 넣는다. 파일만 만들어 주면 된다.

## 8.3 점수를 어떻게 매길 것인가

이것이 가장 어려운 부분이다. 자동으로 뽑은 점수는 실제 빈도 비율이지만,
사람이 넣는 것은 그런 근거가 없다. 그래서 규칙을 정해 둔다.

### 문턱은 15.0 이다

합이 15.0 을 넘어야 그 절을 짚는다. 이 숫자를 기준으로 설계한다.

```
낱말 하나로 확정할 수 있다      →  16.0 ~ 25.0
     그 낱말이 나오면 그 절이 거의 확실한 경우
     예: "배당성향" → III/6

낱말 둘이 함께 와야 한다        →  각 8.0 ~ 10.0
     하나만으로는 애매하고 둘이 겹치면 확실해지는 경우
     예: "사업" + "개요" → II/1

거들기만 한다                   →  3.0 ~ 6.0
     방향은 맞지만 이것만으로는 못 정하는 경우
     예: "부문" → II/1
```

### 왜 이런 층을 두는가

`정책` 사건이 다시 일어나지 않게 하기 위해서다. 흔한 낱말에 높은 점수를
주면 그 낱말이 들어간 모든 질의가 그 절로 끌려간다.

스스로에게 이렇게 물어보면 된다.

```
"이 낱말이 질의에 나왔을 때, 다른 절을 봐야 할 경우가 있는가?"

없다        →  16.0 이상. 혼자서 문턱을 넘게 한다
가끔 있다    →  8.0 ~ 10.0. 짝이 있어야 넘게 한다
자주 있다    →  3.0 ~ 6.0. 또는 아예 넣지 않는다
```

### 넣지 말아야 할 낱말

```
모든 사업보고서에 나오는 말      회사 · 당사 · 사업 · 내용 · 현황 · 기준
질의 동사                       알려줘 · 정리해줘 · 설명해줘
숫자나 단위                     원 · 백만원 · 년
```

`src/query.py` 의 `STOP` 목록에 이런 말이 이미 들어 있어 검색어 단계에서
빠진다. 표에 넣어도 매칭이 안 된다.

### 형태소에 맞춰야 한다

중요한 함정이다. 질의는 형태소 분석기를 거쳐 낱말로 쪼개진다.
`알려줘` 는 `알리` 가 되고 `배당하는` 은 `배당` 이 된다.

표에 `배당하는` 이라고 적으면 절대 안 걸린다. 원형으로 적어야 한다.

복합어도 쪼개진다. 이것이 특히 함정이다. 실제로 찍어 본 결과다.

```
"삼성전자의 주주환원 정책이 어떻게 되는지 알려줘"
    검색어  ['주주', '환원', '정책']        ← "주주환원" 이 둘로 갈렸다

"실적이 왜 이렇게 변했는지 설명해줘"
    검색어  ['실적', '이렇', '변하']        ← "변했는지" 가 "변하" 가 됐다

"삼성전자가 어떤 사업을 하는 회사인가"
    검색어  ['사업', '회사']                ← 둘만 남았다
```

표에 `주주환원` 이라고 적으면 안 걸린다. `주주` 와 `환원` 을 따로 넣어야 한다.

확인하는 방법은 9장에 적었다. 표를 만들면서 실제로 어떤 낱말이 나오는지
직접 찍어 보는 것을 권한다. 이 확인을 건너뛰면 표를 다 만들고도 하나도
안 걸리는 일이 생긴다.

## 성적 재기

평가 스크립트는 하나뿐이다. 새로 만들지 않는다.

```bash
python scripts/eval_body.py --mode=path      # 경로 필터 켜고 끄고 견준다

python scripts/eval_body.py --mode=path --cases=queries_set1.csv   # 다른 질의 세트로
```

`--mode=path` 가 경로 필터를 켠 것과 끈 것을 나란히 낸다. 표를 넣기 전과 후를
견주면 효과가 바로 보인다.

## 질의가 어떤 낱말로 쪼개지는지 보기

8.3 에서 말한 형태소 함정을 피하려면 이것을 먼저 찍어 본다.

```python
import sys
sys.path.insert(0, "src")
sys.stdout.reconfigure(encoding="utf-8")
import query as Q

for q in ["실적이 왜 이렇게 변했는지 설명해줘",
          "삼성전자가 어떤 사업을 하는 회사인가"]:
    print(q)
    print("  검색어:", Q.parse(q).terms)
```

여기 나온 낱말과 표의 낱말이 정확히 같아야 걸린다.

## 표가 실제로 절을 짚는지 보기

```python
import sys
sys.path.insert(0, "src")
sys.stdout.reconfigure(encoding="utf-8")
import query as Q
from retrieval import guess_paths

for q in ["실적이 왜 이렇게 변했는지 설명해줘"]:
    terms = Q.parse(q).terms
    print(q, "->", terms, "->", guess_paths(terms))
```

빈 리스트가 나오면 문턱을 못 넘은 것이다.
