# W1. 협업 기반

일정 1일 · 담당 공동

## 왜

파트너가 환경을 못 갖추면 24일 중 상당 기간이 1인 작업이 된다. 그리고 앞으로 만들 모든 스크립트가 공통 함수에 의존하므로, 이걸 먼저 만들어야 각자 작업이 충돌하지 않는다.

경로 문제도 여기서 해결한다. 지금 코퍼스 경로는 압축을 풀 때 우연히 생긴 형태다. 파트너가 다르게 풀면 코드가 데이터를 못 찾는다.

## 무엇을

| 파일 | 내용 |
|---|---|
| `src/corpus.py` | 코퍼스 루트 자동 탐지, 한글 경로 정규화, manifest·universe 로딩 |
| `scripts/verify_corpus.py` | 배치 검증 — 4,204건 접근 가능 여부, 유형별 건수 |
| `docs/SETUP.md` | 파트너용 환경 구성 안내 |
| `docs/GIT.md` | 협업 규칙 — 브랜치, PR, 충돌 대처, 파일 소유권 |

## 어떻게

경로를 하드코딩하지 않는다. `assets/` 아래를 훑어 `manifest.jsonl`이 있는 폴더를 코퍼스 루트로 판별한다. 한글 정규화는 NFD와 NFC를 모두 시도한다.

```python
def resolve(rel_path: str) -> Path:
    for form in ("NFD", "NFC"):
        p = CORPUS / ud.normalize(form, rel_path)
        if p.exists():
            return p
    raise FileNotFoundError(rel_path)
```

원문은 읽기 함수만 노출하고 쓰기 경로를 두지 않는다.

## 검증

파트너 PC에서 `verify_corpus.py`가 `4204 / 4204 건 접근 가능`을 출력한다.

## 무엇이 해결되나

파트너가 문서만 보고 스스로 시작할 수 있다. 폴더 구조가 달라도 코드가 데이터를 찾는다. 두 사람이 동시에 일할 수 있게 된다.

## 관계

|---|---|
| 선행 | 없음 |
| 후행 | W2 이후 전부 |
| 필요한 정의 | 없음 |
| 구현하는 단계 | 없음 (기반 작업) |

# W2. 기준 계층

일정 2일 · 담당 사용자

## 왜

4,204건에서 대상 문서를 좁히는 첫 관문이다. 이후 모든 작업이 "어느 문서에서 뽑을지"를 여기서 결정한다.

참고 질의 6개 중 5개가 기업·기간·유형으로 특정 가능하다. 검색이 아니라 필터링 문제다.

## 무엇을

`company`(70행)와 `document`(4,204행) 테이블 구축.

```
company     corp_code PK · stock_code · corp_name · listed_name · alias[]
            market · industry · sector · listing_date · market_cap
            IDX  corp_name · listed_name · alias

document    doc_id PK · corp_code FK · doc_group · doc_subtype · category
            report_nm · rcept_no · rcept_dt · base_year · base_month
            is_correction · file_path
            IDX  (corp_code, doc_group, base_year) · (corp_code, rcept_dt) · category
```

## 어떻게

`manifest.jsonl`과 `universe.csv`를 SQLite로 적재한다. 추출이나 파싱이 없어 판단이 들어가지 않는다.

기업 지칭 방식은 별도 별칭 테이블을 만들지 않는다. 제공 데이터 안에 이미 세 가지 지칭이 들어 있고, 세 컬럼에 인덱스를 거는 것으로 끝난다.

```
corp_name     현대자동차       DART 공식 법인명. raw/ 폴더명과 동일
listed_name   현대차           거래소 통용 종목명
sector        자동차·모빌리티   "2차전지 기업 A와 B" 같은 지칭
```

포스코·하이닉스·삼바 같은 시장 은어는 만들지 않는다. 제공 데이터 어디에도 없고, 평가 규칙이 외부 데이터 추가를 금지하므로 평가 질의도 제공 데이터 안의 이름을 쓸 가능성이 높다.

`document.category`는 D1이 정해지면 채운다. 지금은 빈 컬럼으로 두고 스키마만 잡는다.

## 검증

행 수가 70과 4,204인지 확인한다. `listed_name`으로 현대차를 조회하면 현대자동차 문서가 나오는지, `sector`로 2차전지를 조회하면 3개사가 나오는지 확인한다.

## 무엇이 해결되나

"삼성전자 2025년 사업보고서"를 SQL 한 줄로 특정할 수 있게 된다. S2와 S3이 동작한다.

# W3. 관계 계층

일정 2일 · 담당 사용자

## 왜

정정본이 있는 문서에서 어느 값이 유효한지 정하지 않으면, 이후 추출한 모든 값이 틀릴 수 있다.

실측 사례다. 공급계약 1,106건에서 회사가 기재한 매출액대비 비율을 재계산하니 89건이 어긋났고, 그중 88건이 정정공시였다. 정정 전 값을 잡았기 때문이다. 정정 헤더를 분리하고 본문에서만 읽으니 일치율이 89.6%에서 99.3%로 올랐다.

W4·W5보다 먼저 하는 이유가 이것이다. 판본 판정이 안 된 상태에서 값을 뽑으면 그 값이 틀린다.

## 무엇을

`doc_relation` 테이블 구축.

```
doc_relation  id PK · from_doc_id · to_doc_id · rel_type 정정/해지/후속
              target_date · target_hint 상대방·보고서명
              resolved · unresolved_reason
              IDX  from_doc_id · to_doc_id · (rel_type, resolved)
```

## 어떻게

정정공시는 본문 헤더의 "정정대상 공시서류의 최초제출일"로 연결한다. 다만 날짜만으로는 유일 식별이 안 된다. (기업, 유형, 날짜) 조합 3,048개 중 141개(4.6%)에 원본이 2건 이상 있다. 정정 전 값을 후보와 대조해 확정한다.

계약 해지는 `관련공시` 필드로 연결한다. 날짜와 유형이 함께 적혀 있고 계약 상대방 이름도 있어 이중 확인이 가능하다.

연결 실패는 사유와 함께 기록한다. 이건 실패가 아니라 답변해야 할 사실이다.

## 검증

연결 건수, 미연결 건수, 사유별 분포를 낸다. 건수만 세지 않고 연결의 방향·기업 일치·유형 일치를 함께 본다.

건수 검사로는 오연결이 안 잡힌다. 실제로 잡은 것은 내용 검사였다.

```
유형 일치            오연결 15건   회사합병결정 정정본 → 타법인주식양수결정
계약 식별 항목 일치    오연결 26건   FCS 정정본 → 잠수함 원본 · 파나마 정정본 → 샤힌 원본
```

시행착오는 `feedback/W3.md` 참조. 적재를 열두 번 다시 했고 그 과정을 열다섯 항목으로 남겼다.

## 무엇이 해결되나

S4 판본 해소와 S5 관계 추적이 동작한다. Q5 계열 질의에 답할 수 있게 된다. 그리고 W4·W5가 올바른 판본에서 값을 뽑게 된다.

여기서 해결되는 것과 아닌 것을 구분해 둔다.

```
해결   문서와 문서의 관계. 어느 정정본이 어느 원본을 고쳤는가
       미연결 사유. D7 네 갈래 중 하나로 확정된다
       HCX 는 "이 공시가 정정됐나, 원본이 뭔가"를 판단하지 않는다

미해결 값 자체. doc_relation 에는 계약금액도 수주일자도 없다
       두산퓨얼셀 원본의 수주일자 오타 2026-02-12 는 원문에 그대로 있다
       W4 가 event_contract 를 만들 때 어느 판본의 값을 쓸지 정해야 한다
```

W3 은 그 판단의 재료를 만든 것이지 값을 고친 것이 아니다.

# W5. 사실 계층 · 재무

일정 3일 · 담당 사용자

## 왜

난이도가 가장 높다. 계정명 6종, 단위 3종, 한 표 3개년, XBRL 시점 공백이 겹친다.

정형 3종을 먼저 하고 여기를 나중에 하는 이유는 두 가지다. 앞에서 만든 추출·검증 방식을 여기 그대로 쓸 수 있고, 시간이 부족하면 커버 범위를 줄일 수 있는 쪽이 여기이기 때문이다.

## 무엇을

```
fact_financial  id PK · doc_id FK · corp_code · item_code ifrs-full_*
                context · fiscal_year · period_type · basis 연결/별도
                value_raw · decimals · value_krw · source_section · extract_method
                IDX  (corp_code, item_code, fiscal_year, basis)
```

## 어떻게

두 경로로 채운다.

XBRL 보유 488건은 속성에서 직접 읽는다. `ACONTEXT`에 기간·기간유형·연결/별도가, `ADECIMAL`에 단위가 들어 있어 표 헤더를 볼 필요가 없다.

```xml
<TE ACODE="ifrs-full_Revenue"
    ACONTEXT="CFY2024dFY_..._ConsolidatedMember"
    ADECIMAL="-6">107,448,752</TE>
```

같은 태그가 부문정보 표에도 붙으므로 `ACONTEXT`의 축으로 구분한다. 손익계산서 안은 축이 2종, 그 외 표는 146종이다.

나머지 406건은 표 파싱으로 채운다. 계정명 사전, 단위 헤더 판독, 연도 열 매핑이 필요하다.

## 검증

XBRL 보유 488건을 정답지로 삼는다. 같은 문서를 표 파싱으로도 뽑아 두 값을 대조하면 파서가 제대로 작동하는지 자동으로 채점된다. 검증된 파서를 태그 없는 406건에 적용한다.

## 무엇이 해결되나

Q1·Q3 계열 수치 질의와 비교 연산이 가능해진다.

# W6. 본문 계층

일정 3일 · 담당 사용자

## 왜

서술형 질의는 값으로 답할 수 없다. 그리고 사업보고서가 평균 58만 자, 최대 91만 자라 통째로 넣을 수 없다. HCX 최대 입력이 32,768 토큰이다.

## 무엇을

```
section  section_id PK · doc_id FK · path · seq · title · char_len · has_table · text
         IDX  (doc_id, path) · title

chunk    chunk_id PK · section_id FK · doc_id · seq · text · token_est
         embedding · header 기업·기간·유형·섹션
         IDX  vector(embedding) · section_id
```

## 어떻게

정기공시는 목차가 법정 서식이라 `SECTION-2` 단위로 자른다. 삼성전자 사업보고서에서 `TITLE` 태그가 135개, 대분류 섹션이 14개였고 기업이 달라도 대분류는 같다.

다만 서식 청킹만으로는 부족하다. 40건을 잘라 1,952개 조각의 크기를 재니 중앙값은 2,926자로 잘 잘렸지만 꼬리가 길었다.

| 한도 | 초과 조각 |
|---|---|
| 임베딩 8,192토큰 (약 13,107자) | 319개 (16.3%) |
| HCX 입력 32,768토큰 (약 52,429자) | 153개 (7.8%) |

한도를 넘는 조각만 2차 분할한다. 이때 표를 깨뜨리지 않는 규칙이 필요하다. 재무 수치는 전부 표 안에 있고, 헤더와 숫자가 분리되면 어느 항목의 값인지 알 수 없게 된다.

각 청크에 기업·기간·유형·섹션을 헤더로 붙인다. 조각만 떼어 놓으면 어느 기업 어느 시점의 이야기인지 알 수 없다.

임베딩은 CLOVA Studio v2(bge-m3, 8,192 토큰)를 쓴다. 임베딩 모델은 대회 제약 대상이 아니다.

## 검증

조각 크기 분포를 다시 재서 한도 초과가 0이 되었는지 확인한다. 표가 잘린 조각이 있는지 표본으로 확인한다.

## 무엇이 해결되나

Q2·Q6 계열 질의가 가능해진다. S7이 동작한다.

## 관계

| 항목 | 내용 |
|---|---|
| 선행 | W2 |
| 후행 | W7 |
| 필요한 정의 | 없음 |
| 구현하는 단계 | S7 본문 검색 |

청킹 단위는 뒤집기 어렵다. 바꾸면 전체를 다시 임베딩해야 한다. 여기서 신중해야 한다.

# W7. 검색·라우팅

일정 3일 · 담당 파트너

## 왜

질의를 받아 어느 경로로 보낼지 정하는 부분이다. 여기가 없으면 데이터가 있어도 꺼낼 수 없다.

## 무엇을

S1 질의 해석, S3 필터 로직, S7 검색 로직, S8 연산.

## 어떻게

질의 해석은 Structured Outputs로 스키마를 강제한다. few-shot 예시를 넣기에 가장 값어치가 큰 지점이다.

검색은 메타데이터 필터를 먼저 걸고 그다음 본문을 찾는다. 필터로 후보를 수천에서 수십으로 줄인 뒤 검색하면 같은 알고리즘이라도 정확도가 달라진다.

본문 검색은 BM25와 벡터를 섞는다. 공시는 고유명사·종목코드·법률 용어가 많아 정확 문자열 매칭이 필요하고, 동시에 "자금조달"에서 "유상증자"로 넓히는 의미 확장도 필요하다. 융합은 RRF를 쓴다. 점수 정규화 방식은 튜닝이 필요한데 RRF는 순위만 쓰므로 하이퍼파라미터가 사실상 없다.

한국어 BM25는 형태소 분석기가 필요하다. 공백 토크나이저로는 "전환사채의"와 "전환사채가"가 다른 토큰이 되어 무력화된다. Windows 환경이므로 `kiwipiepy`를 쓴다.

연산은 Python으로 한다. 단위 정규화를 먼저 하고 계산한다.

## 검증

자체 평가셋으로 Recall@k를 측정한다. 참고 질의 6개를 템플릿 삼아 기업만 바꿔가며 만든다.

## 무엇이 해결되나

자연어 질의가 테이블 조회로 번역된다.

## 관계

| 항목 | 내용 |
|---|---|
| 선행 | W2·W3의 스키마 확정 |
| 후행 | W8 |
| 필요한 정의 | D2 설비투자 · D5 기간 해석 |
| 구현하는 단계 | S1 · S3 · S7 · S8 |

## 흐름 제어를 무엇으로 할 것인가

함수 체이닝으로 시작한다. 상태 객체 하나를 두고 각 단계 함수를 순서대로 호출하며, 조건 분기는 `if`로 쓴다.

지금 조건 분기가 5개이고 사이클이 1개(검색 재시도)라 이 규모에서는 `if`가 더 읽기 쉽다. LangGraph는 표현력이 남아돌고 학습 비용과 디버깅 부담만 늘어난다.

다만 11단계가 충분하다는 것은 검증되지 않은 가설이다. 다음 패턴이 실제 평가 질의에 나오면 부족해진다.

| 패턴 | 예 | 함수 체이닝으로 되나 |
|---|---|---|
| 전수 스캔 | "매출 증가폭 상위 3개사" | 됨 |
| 동적 팬아웃 | "CB 발행 기업들의 발행 직전 부채비율" | 됨. 서브 파이프라인 재귀 |
| 적응형 검색 | "실적 악화 이유가 공시에 있나" | 되지만 지저분해짐 |

셋째가 LangGraph가 설계된 목적이다. LLM이 검색 결과가 충분한지 판단하고 부족하면 되돌아가는 구조다.

### 전환 신호

W10 자체 평가에서 아래가 관측되면 LangGraph로 옮긴다.

```
1  Open 질의의 근거 완전성이 낮고, 원인이 "한 번 검색으로 부족"으로 진단될 때
2  조건 분기가 10개를 넘을 때 (현재 5개)
3  서브 파이프라인 재귀가 2단계 이상 필요할 때
```

### 전환 비용을 낮추는 규칙

처음부터 아래를 지키면 전환이 하루 이내로 끝난다. 함수 본문을 손대지 않고 노드로 감싸기만 하면 된다.

```
1. 각 단계는 독립 함수. 입력도 출력도 State 하나
2. 전역 변수를 쓰지 않는다
3. 조건 판단을 단계 함수 밖으로 뺀다 (라우팅 함수를 따로 둔다)
4. 각 함수는 상태만 갱신하고 다른 부작용을 만들지 않는다
```

CLOVA Studio는 LangChain을 공식 지원한다. `langchain-naver` 패키지가 `ChatClovaX`와 `ClovaXEmbeddings`를 제공하고, 문서에 LangGraph 활용 가능이 명시돼 있다. 즉 전환 시 기술적 장벽은 없다.

# W8. 답변 생성·검증

일정 3일 · 담당 파트너

## 왜

평가지표 4·6·7이 전부 여기 걸린다. 그리고 지표 5의 `think_trace`도 여기서 만들어진다.

지금 사각지대인 영역이기도 하다. 프롬프트 공격 대응은 지금까지 한 번도 다루지 않았다.

## 무엇을

S9 근거 조립, S10 답변 생성, S11 출력 검증, 그리고 입력 방어.

## 어떻게

실행 기록을 구조화된 형태로 남긴다. 문자열이 아니라 JSON으로 두면 같은 데이터가 `think_trace`와 데모 UI 양쪽에서 쓰인다. 문자열로만 만들면 나중에 파싱해서 되살려야 한다.

답변은 정해진 형식을 따른다.

```
1. 답할 수 있는 만큼 답한다
2. 어떤 기준으로 골랐는지 밝힌다
3. 답하지 못한 부분은 범위 밖·미공시·추출 실패로 구분해 적는다
4. 다른 관점이나 후보를 안내한다
```

되묻는 문장은 두지 않는다. 평가는 GET 요청 한 번으로 끝나므로 되물으면 그 질의의 답이 없다.

검증은 코드로 한다. 모델은 확률적으로 동작하므로 프롬프트로 금지해도 지켜지지 않을 수 있다.

## 검증

답변에 담긴 수치가 `retrieved_context`에 실제로 존재하는지 대조한다. 요구 항목이 다 등장하는지 확인한다. 질의와 무관한 개인 신상이 딸려 나오지 않았는지 확인한다.

## 무엇이 해결되나

응답 4필드가 완성된다.

## 관계

| 항목 | 내용 |

| 선행 | W7 |
| 후행 | W9 |
| 필요한 정의 | D7 확인 불가의 네 갈래 (확정) |
| 구현하는 단계 | S9 · S10 · S11 · 입력 방어 |

# W9. 통합·배포

일정 2일 · 담당 파트너

## 왜

지금 서버에는 CLOVA 직결 코드만 있다. 데이터와 파이프라인을 올려야 실제로 동작한다.

## 무엇을

데이터 업로드, 서버 코드 교체, 자동 재시작 재검증, 응답 시간 측정.

## 어떻게

원문 5.5GB를 통째로 올릴 필요는 없을 수 있다. 태그를 걷어낸 순수 텍스트는 약 1.3GB로 추정된다. 사실 테이블은 수십 MB, 벡터 인덱스는 수백 MB다.

무엇을 올릴지는 W6이 끝난 뒤 실제 크기를 보고 정한다.

업로드는 RDP 드라이브 매핑으로 시작하고, 느리면 OpenSSH Server를 설치해 scp로 바꾼다.

## 검증

서버를 재시작하고 3~5분 뒤 아무도 손대지 않은 상태에서 외부 호출이 성공하는지 확인한다.

응답 시간을 측정한다. 검색 없이 순수 CLOVA 호출만으로 한글 질의가 5.3초였다. 여기에 검색과 계산이 더해진다.

| 선행 | W6, W8 |
