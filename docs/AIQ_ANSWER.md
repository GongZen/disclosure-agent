# 1. 먼저 답이 필요한 셋

## 1-1. `더할것` 낱말의 점수 — 사람이 매긴다. 다만 지금은 안 매겨도 된다

### 결론

```
지금 단계    낱말만 적는다. 점수는 비워 둔다
다음 단계    표를 다 채운 뒤 이쪽에서 일괄로 매긴다
```

### 왜 지금은 안 매기나

점수를 매기려면 문턱이 있어야 하고, 문턱은 실측으로 정해야 한다. 지금 그 실측이
불가능하다. 표가 비어 있어 재 볼 것이 없기 때문이다.

닭과 달걀처럼 보이지만 순서가 있다.

```
1  낱말을 모은다            지금 하는 일
2  낱말 목록으로 성적을 잰다   낱말이 모여야 잴 수 있다
3  문턱과 점수를 함께 정한다   성적을 봐야 정할 수 있다
```

2단계에서는 점수를 일괄로 같게 두고 재도 된다. 그러면 "이 절을 짚을 낱말이
질의에 몇 개나 걸리는가" 를 먼저 보게 된다. 그 분포를 보고 3단계에서
점수 층을 정하는 편이 감으로 매기는 것보다 정확하다.

### `ONBOARDING.md` 8.3 의 3층 기준은 아직 유효한가

방향은 유효하고 숫자는 무효다.

```
방향   혼자 확정할 낱말 / 짝이 있어야 하는 낱말 / 거들기만 하는 낱말
       이 구분은 그대로 쓴다

숫자   16~25 · 8~10 · 3~6 은 pathmap.csv 기준이다
       새 표는 점수 스케일이 2.77배라 그대로 쓰면 안 된다
```

`ONBOARDING.md` 8장은 `pathmap.csv` 를 전제로 쓴 문서다. 새 표로 갈아타면
8장 전체를 다시 써야 한다. 지금은 "판정 기준" 부분만 유효하다고 보면 된다.

### 그래서 지금 해 주면 되는 것

낱말을 고르면서 셋 중 무엇인지 감이 오면 `메모` 에 적어 달라. 형식은 자유다.

```
메모   경영진단·분석의견은 단독으로 확정 가능. 나머지는 짝 필요
```

나중에 점수를 매길 때 그 메모가 근거가 된다.

## 1-2. `더할것` 낱말이 본문에 없어도 된다 — 그것이 이 작업의 핵심이다

### 결론

```
넣어도 된다. 오히려 그런 낱말이 이 작업의 존재 이유다
```

### 왜 충돌처럼 보이나

지적한 그대로다. 점수 정의가 `(그 절 비율) ÷ (전체 비율)` 이라 본문에 없으면
분자가 0이다. 그런데 이건 자동 추출의 정의이지 매칭표의 정의가 아니다.

둘을 갈라 보면 충돌이 없다.

```
자동 추출    절 본문에서 낱말을 뽑는다.  점수가 통계에서 나온다
매칭표       질의에서 절로 잇는다.       점수가 판단에서 나온다
```

`guess_paths()` 가 대조하는 것은 질의의 검색어와 표의 낱말이다. 절 본문과는
대조하지 않는다. 그래서 본문에 없는 낱말도 정상으로 동작한다.

```python
def guess_paths(terms, top=2):
    for path, d in pathmap().items():       # d 는 {낱말: 점수}
        s = sum(v for w, v in d.items() if w in terms)   # terms 는 질의에서 온다
```

즉 자동 추출이 못 하는 일을 사람이 하는 것이고, "본문에 없는 낱말" 이 정확히
그 일이다. 자동으로 나올 낱말이면 이미 표에 있다.

### 경영진단 사례 — 이쪽에서도 재 봤다

70개사 전체 `IV` 계열 588절 기준이다. 본문에 그 문자열이 든 절의 비율이다.

```
경영진단   27절 /  588   4.6%
분석의견   15절 /  588   2.6%
경영      275절 /  588  46.8%
진단       36절 /  588   6.1%
의견       31절 /  588   5.3%
실적      178절 /  588  30.3%
```

그쪽 값(비금융 30개사 3,789절 기준)과 다른 것은 모집단이 달라서다. 결론은
같다 — `경영진단` · `분석의견` 은 본문에 거의 없다.

그리고 `IV` 부모 절은 이렇다.

```
84건 · 0자 78건 · 100자 이상 4건 · 최대 137자
```

내용이 없는 껍데기라 표에서 빠졌다. 그쪽이 잰 69건 중 67건 0자와 같은 사실이다.

### 그래서 어디에 넣나

`IV` 자체가 표에 없으므로 하위 절에 넣는다. 어느 하위 절인지가 판단이다.

```
IV/2  개요                    경영진단의 총론.  "경영진단 의견" 이 여기 맞다고 본다
IV/3  재무상태 및 영업실적       실적 변화 질의
IV/4  유동성 및 자금조달과 지출
IV/6  그 밖에 투자의사결정에 필요한 사항
```

`IV/1 예측정보에 대한 주의사항` 은 법적 면책 문구라 답이 될 내용이 없다.
여기에는 넣지 않는 편이 낫다. 자세한 것은 `pathmap_review.md` 의
"특별히 볼 절 하나" 에 있다.

다만 이 배분은 이쪽 판단이고 확정이 아니다. 본문을 보고 다르게 보이면
그쪽 판단을 따르겠다. `section_terms.csv` 에 `IV/2`~`IV/6` 의 낱말과 용례가
들어 있으니 그것으로 확인할 수 있다.

## 2-1. `section_terms.csv` — 낱말 하나가 한 행이고 용례가 붙어 있다

### 왜 필요한지에 동의한다

`pathmap_review.csv` 에 용례를 넣었던 것이 바로 그 이유였다. `이유` 를 빼야

용례  정관변경일 │ 해당주총명 │ 주요변경사항 │ 변경이유

`section_schema.csv` 를 만들 때 이 칸을 빠뜨렸다. 절이 한 행이라 낱말이
14~20개씩 몰려 있어 용례를 붙일 자리가 없었기 때문인데, 그 결과 판정 근거를
없앤 셈이 됐다.

### 만든 것

```
data/eval/section_terms.csv    2,405행 · 11칸
```

| 칸 | 무엇인가 |
|---|---|
| `대분류` `열쇠` `열쇠뜻` `기업수` | 어느 절인지 |
| `낱말` `점수` `확률` | 판정 대상과 수치 |

`section_schema.csv` 쪽 `더할것` 칸에 적어 달라. 두 파일을 오가야 하는데,
빼는 일과 더하는 일의 성격이 달라 어쩔 수 없다고 본다.

## 2-2. `case_key_map.csv` — 채점 사례 37건과 열쇠를 이었다

data/eval/case_key_map.csv    69행

한 사례가 정답 절을 여럿 가질 수 있어 37건이 69행이 됐다.

# 3. 결과가 검색에 어떻게 반영되는가

## 3-1. 열쇠를 조각에 잇는 방법 — 아직 코드가 없다. 설계는 이렇다

### 지금 상태

관찰한 그대로다.

```
retrieval.py 226행    cp.byid[cp.ids[i]]["path"] in want      완전일치
search.py     70행    s.path = ? OR s.path LIKE ?/%           접두일치
```

두 곳의 대조 방식이 다른 것도 맞다. `search.candidates()` 는 후보를 좁힐 때
접두로 훑고, `retrieval` 은 부스트할 때 완전일치로 본다. 쓰임이 달라 생긴 차이인데
헷갈리기 쉬운 자리다.

### `section.aclass` 커버리지

```
2025 사업보고서 정기공시 12,755절 중 aclass 있음 6,981절 (54.7%)
```

절반뿐이고 그 절반이 거의 전부 `III` 이다. 그래서 열쇠가 두 종류다.

### 새 표로 갈아탈 때의 대조 규칙

`Corpus` 가 조각마다 `path` 는 갖고 있지만 `aclass` 는 안 갖고 있다. 그래서
`Corpus` 의 조회에 `s.aclass` 를 추가해야 한다. 그 뒤 이렇게 대조한다.

```
열쇠종류 tag     조각의 aclass 와 완전일치
열쇠종류 title   조각 제목을 정규화해 완전일치
                 정규화는 build_section_schema.norm() 을 그대로 쓴다
```

`norm()` 은 세 가지를 한다. 앞 번호 제거 · 공백 전부 제거 ·
`(연결)` `(제조서비스업)` `(금융업)` 꼬리표 제거.

`III` 에서 태그가 없는 절(U 코드이거나 aclass 자체가 없는 경우)은 제목 쪽으로
떨어진다. 스키마를 만들 때와 같은 규칙이라 어긋나지 않는다.

### 지금 효과를 시뮬레이션하려면

코드가 없으므로 대신 이 방법을 쓸 수 있다.

```
1  낱말을 넣는다
2  guess 를 흉내 낸다 — 질의 검색어와 표의 낱말을 겹쳐 점수를 더한다
3  그 열쇠에 속한 절이 case_key_map.csv 의 정답과 맞는지 본다
```

3번에 필요한 대조표를 이번에 만들었다. 실제 검색 순위까지는 못 재지만
"이 낱말로 이 절을 짚는가" 는 잴 수 있다.

코드를 언제 고칠지는 4장 뒤에 적었다.

## 3-2. 문턱 — 지금은 상대 크기만 맞추면 된다

### 결론

```
41.6 을 가정하지 마라. 표를 다 채운 뒤 실측으로 정한다
```

### 왜 단순 환산이 안 되나

2.77배는 분모 비율일 뿐이다.

```
pathmap.csv          3,561절 기준
section_schema.csv   9,877절 기준
```

같은 낱말의 점수가 42.4 대 117.8 이 되는 것은 맞다. 그런데 문턱은 점수 하나가
아니라 "질의에 걸린 낱말들의 점수 합" 과 비교된다. 그 합의 분포는 표에 낱말이
몇 개 들어가느냐에 따라 달라진다.

지금 표는 절당 낱말이 평균 14.6개다. `pathmap` 은 12개였다. 여기에 `더할것` 이
붙으면 또 달라진다. 그러니 지금 문턱을 가정하면 표를 채우고 나서 다시 정해야 한다.

### 그래서 무엇을 맞추면 되나

낱말 간 상대 크기만 생각하면 된다. 1-1 에 적은 대로 지금은 점수를 안 매겨도
되고, 감이 오면 `메모` 에 적어 두면 된다.

---

## 3-3. `top=2` — 유지가 기본이다

### 왜 유지인가

662행이라 후보가 는 것은 맞지만, 실제로 짚히는 것은 문턱을 넘는 열쇠뿐이다.
지금 `pathmap` 에서 37건 중 9건만 경로를 짚었다. 표가 커져도 한 질의가
문턱을 넘기는 열쇠는 몇 개 안 될 것으로 본다.

그리고 `top` 을 늘리면 부작용이 있다.

```
PATH_BOOST = 20   짚은 절의 조각을 20위까지 당긴다
top = 2           두 절의 조각이 앞으로 온다
top = 4           네 절의 조각이 앞으로 온다.  정답이 뒤로 밀릴 수 있다
```

8위내를 재는 지표에서는 앞자리를 차지하는 것이 손해가 될 수 있다.

### 그래서 낱말 개수 설계에 주는 함의

`top` 이 2라는 것은 "한 질의가 두 절을 짚는다" 는 뜻이지 "한 절에 낱말을
두 개만 넣어라" 가 아니다. 낱말 개수와는 직접 관계가 없다.

굳이 관계를 따지면 이렇다. 한 절에 낱말이 많을수록 그 절이 문턱을 넘기 쉬워지고,
여러 절이 문턱을 넘으면 `top=2` 가 그중 점수가 높은 둘만 고른다. 즉 낱말을
많이 넣으면 경쟁이 생긴다.

절당 6~12개를 권했던 것이 그 이유다. 다만 이 숫자도 `pathmap` 기준이라
새 표에서 다시 재야 한다.

## 4-1. IV 채점 문제 — 이쪽 의견은 `가` 다. 다만 그쪽이 정한다

### 문제를 다시 정리하면

채점   grade() 가 g in h.title 로 본다

`set1-10` · `set1-19` · `set1-28` 세 건이 여기 걸린다. 검색이 완벽해도 0점이다.

### 세 방향의 성질

```
가  grade 가 부모·자식을 인정한다
    얻는 것 — 사례를 안 건드린다.  정답지가 사람이 만든 것이라는 원칙이 지켜진다
              "IV 를 보라" 는 지시를 "IV 아래 어디든" 으로 읽는 것이 자연스럽다
    잃는 것 — 채점이 느슨해진다.  IV/1 예측정보 주의사항이 걸려도 정답이 된다
              그 절은 법적 면책 문구라 답이 될 내용이 없다

나  gold 를 실제 내용 절로 고친다
    얻는 것 — 채점이 정확해진다
    잃는 것 — 세 건을 사람이 다시 봐야 한다
              set1 은 AI 가 만든 것이라 사용자 정답지는 아니지만, 고치는 순간
              "AI 가 자기 채점 기준을 만든다" 에 가까워진다

다  그대로 둔다
    얻는 것 — 아무것도 안 한다
    잃는 것 — 성적이 실제보다 세 건 낮게 나온다.  IV 낱말 작업의 효과를 못 잰다
```

### 이쪽 의견

`가` 를 권한다. 다만 `IV/1` 을 후보에서 빼는 것과 함께 가야 한다고 본다.

```
가 + IV/1 제외
   부모·자식을 인정하되 답이 될 내용이 없는 절은 애초에 후보에서 뺀다
   목차 조각과 【대표이사 등의 확인】 을 뺀 것과 같은 이유다

```

이유는 셋이다.

```
1  set1 의 gold 는 AI 가 만든 것이지만 그것을 AI 가 다시 고치면 순환이 된다
2  "IV 를 보라" 는 지시는 사람이 봐도 "IV 아래 어디든" 으로 읽힌다
3  느슨해지는 위험이 IV/1 하나에 몰려 있고, 그건 따로 뺄 수 있다
```

### 다만 그쪽이 정하는 것이 맞다

정답지는 그쪽이 만든 것이고, 이건 채점 기준의 문제다. 이쪽 의견은 참고로만
써 달라. 어느 쪽으로 정하든 그에 맞춰 코드를 고치겠다.

`가` 로 가면 `retrieval.grade()` 를 이쪽이 고친다. `나` 로 가면

## 5-2. `chunk.header` 에 상위 장 제목이 없다 — 맞다. 그리고 이건 결함이다

### 확인했다

```python
def make_header(corp, report, path, title):
    parts = [x for x in (corp, report, path, title) if x]
    return " · ".join(parts)
```

`IV/2` 조각의 헤더는 이렇게 된다.

```
NAVER · 사업보고서 (2025.12) · IV/2 · 2. 개요
```

`경영진단` 이라는 말이 없다. `IV/2` 라는 경로 문자열은 있지만 그건 벡터에도
BM25 에도 도움이 안 된다.

### 왜 문제인가

헤더는 임베딩 대상 본문에 붙는다. `build_embedding.py` 가 이렇게 부른다.

```python
emb.embed(f"{r['header']}\n{r['text']}")
```

즉 "경영진단 의견" 이라는 질의가 `IV/2` 조각과 벡터로도 안 가까워진다.
본문에도 없고 헤더에도 없기 때문이다.

### 그래서 이 지적이 큰 것을 하나 뒤집는다

1-2 에서 "매칭표로 넣으면 된다" 고 답했는데, 헤더를 고치는 쪽이 더 근본적일 수
있다. 헤더에 상위 장 제목을 넣으면 매칭표 없이도 벡터가 잡을 가능성이 있다.

```
지금   NAVER · 사업보고서 (2025.12) · IV/2 · 2. 개요
고치면  NAVER · 사업보고서 (2025.12) · IV. 이사의 경영진단 및 분석의견 · 2. 개요
```

### 다만 지금은 못 고친다

헤더를 바꾸면 조각 본문이 바뀌고, 그러면 임베딩을 다시 부어야 한다.

```
OpenAI 임베딩   53,785원 지출한 것을 다시 부어야 한다
CLOVA 임베딩    지금 돌고 있다.  9월 2일 기준 14% 진행
```

CLOVA 를 붓는 중에 헤더를 바꾸면 앞부분과 뒷부분의 헤더가 달라진다. 그것이
더 나쁘다.

### 그래서 이렇게 다루려 한다

```
지금       매칭표로 메운다.  헤더는 안 건드린다
CLOVA 뒤   헤더 개선의 효과를 실측으로 잰다
           표본 몇백 조각만 헤더를 바꿔 다시 임베딩해 견준다
           효과가 크면 전면 재작업을 검토한다
```

이건 이쪽에서 처리하겠다. 지적 고맙다. 기록으로 남기려고
`docs/HANDOFF.md` 미결 위험에 넣겠다.

## 5-3. 경로 대조 방식이 두 곳에서 다른 것 — 맞다. 다만 결함은 아니다

```
search.candidates()   s.path = ? OR s.path LIKE ?/%     접두
retrieval.py 226행     path in want                     완전
```

쓰임이 다르다.

`guess_paths()` 가 `III/6` 을 돌려줬는데 `III/6/1` 까지 당기면 의도와 다르다.
그래서 다르게 둔 것이다.

다만 헷갈리기 쉬운 자리인 것은 맞다. 새 표로 갈아탈 때 이 부분을 다시 볼 때
주석을 달아 두겠다.
