# 2. 만든 것 — `src/match.py`

질의에 등장한 이름을 `company` 테이블의 실제 기업으로 확정하는 모듈이다.
`company` 한 테이블만 읽고 아무것도 쓰지 않는다.

## 조회 순서

네 단계이고 위에서부터 걸리는 대로 끝난다.

| 걸음 | 무엇을 보나 | 예 |
|---|---|---|
| 1 | 다섯 컬럼 완전 일치 | `삼성전자` → `corp_name` · `현대차` → `listed_name` · `전력기기` → `sector` |
| 2 | 분류 컬럼 부분 일치 | `자동차` → `sector` 자동차·모빌리티 |
| 3 | 기업 컬럼 부분 일치 | `현대` → 열 곳에 걸림 |
| 4 | 유사도 | 오타로 보고 후보만 제시. 확정하지 않는다 |

2 걸음이 3 걸음보다 앞에 있는 것이 핵심이다. 왜 그런지는 3절 세 번째 항목에 적었다.

## 돌려주는 것

`PIPELINE.md` S2 영향표의 "남기는 것"(확정된 `corp_code` 목록, 매칭 실패 시 사유)에
대응한다. 상태는 셋이다.

```
resolved       한 컬럼에서 확정됐다. kind 가 company 인지 group 인지 함께 준다
ambiguous      부분 일치로 여럿에 걸렸다. 후보 목록을 준다
out_of_scope   제공 데이터 70개사 밖이다. GLOSSARY.md D7 의 out_of_scope 다
```

`ambiguous` 일 때 되묻지 않는다. `PIPELINE.md` S2 의 "되묻지 않는다" 를 따랐다.
`kind` 를 company 와 group 으로 나눈 것은 뒤 단계가 하는 일이 다르기 때문이다.
company 는 그 회사만, group 은 속한 회사 전부로 넓힌다.

| 칸 | 내용 |
|---|---|
| 무엇을 했나 | 완전 일치가 실패하면 `corp_name` · `listed_name` 에만 부분 일치를 걸었다 |

| 어떻게 알았나 | 사용자 지적. `반도체` 결과가 한미반도체 한 곳으로 나온 것을 보고 이상하다는 지적을 받았다 |
| 어떻게 고쳤나 | 분류 부분 일치를 기업 부분 일치 앞에 넣었다. 판정 로직을 따로 만들지 않았다 |
| 무엇이 남았나 | `소비재` 한 종. 아래에 따로 적는다 |

### 왜 순서만으로 해결되나

1 걸음이 이미 다섯 컬럼 완전 일치를 처리한다. 따라서 2 걸음에 도달했다는 것 자체가
"기업명과 완전 일치하는 값이 없다" 는 증명이다. 그러므로 분류를 앞에 두기만 하면
"기업은 완전 일치일 때만 기업으로 보고, 아니면 분류로 본다" 가 자동으로 성립한다.

`SK` 처럼 어느 분류 값의 조각도 아닌 말은 2 걸음을 그냥 통과해 3 걸음으로 간다.

### 왜 이런 일이 생겼나

`sector` 값 20종 중 8종이 `·` 로 묶인 복합어인데 사람은 그 한쪽만 부른다 (실측 2026-08-19).

```
반도체·전자부품     자동차·모빌리티     방산·항공우주     바이오·제약
금융·보험          소비재·유통        운송·물류        AI소프트웨어·플랫폼
```

`방산` 이라는 값은 존재하지 않고 `방산·항공우주` 만 존재한다.

### 조용한 오답이 가장 나쁘다

`out_of_scope` 10종은 못 찾았다는 신호가 남는다. 기업으로 잘못 확정된 5종은 신호가
남지 않는다. `자동차 업종 기업들` 을 물으면 현대자동차 한 곳만 답하고 넘어간다.
평가지표 6 안전성과 7 정보한계 대응에서 가장 위험한 형태라 우선순위를 여기 두었다.

### 남은 것 — `소비재`

세 분류에 걸려 확정 대신 후보를 제시한다. 실측하면 결함이 아니라 실제 중의성이다.

```
sector   소비재·유통       CJ제일제당 · LG생활건강 · 아모레퍼시픽 · 이마트
industry 필수소비재        CJ제일제당 · LG생활건강 · 아모레퍼시픽 · 이마트   ← 위와 같은 집합
industry 경기관련소비재     기아 · 현대모비스 · 현대자동차
```

앞의 둘은 이름만 다르고 회사 목록이 같다. 실제 갈림길은 "소비재 4개사냐, 자동차
3개사냐" 하나이고 이 둘은 뜻이 다르다. 후보를 제시하는 지금 동작이 맞다고 본다.

다만 후보 3개 중 2개가 같은 집합이라 그건 소음이다. 결과 집합이 같은 후보를 하나로
합쳐 후보를 2개로 줄이는 것이 개선 여지다. 아직 넣지 않았다.

## 검증 설계에 남길 것

`feedback/README.md` 는 사용자 지적으로만 잡힌 유형을 다음 작업의 검증 항목에
넣으라고 한다. 항목 3 이 여기 해당한다.

```
넣을 검증 항목   분류 축의 값이 복합어일 때, 그 조각으로 조회해도 분류로 잡히는가
```

항목 1·2 는 표본 확인이 잡았고 항목 3 은 표본 확인이 못 잡았다. 표본을 사람이 고르면
자기가 아는 이름만 넣게 된다는 것이 드러난 셈이라, 전수 조회로 바꿨다.

# 5. 일곱 걸음을 어떻게 적용했나

W4 의 일곱 걸음은 원문에서 값을 뽑아 적재하는 작업의 절차다. S2 는 원문을 읽지도
적재하지도 않으므로 그대로는 맞지 않는다. 억지로 맞추지 않고 두 가지만 가져왔다.

```
0번 걸음의 취지    표본 하나로 규칙을 만들지 않는다
                  → sector 값을 20종 전부 열어보고서야 8종이 복합어임을 알았다.
                     반도체 하나만 보고 넘어갔으면 항목 3 을 못 찾았다

통과 조건         숫자로 답할 수 있는 조건을 미리 정한다
                  → 4절의 세 가지
```

나머지 다섯 걸음(서식 판별기 · 항목 이름 사전 · 값 추출 · 검산 · 적재)은 S2 에 대응하는
것이 없다. S7 본문 검색은 청킹과 임베딩 적재가 있으므로 그때 일곱 걸음을 그대로
쓰는 것이 맞다고 본다.
