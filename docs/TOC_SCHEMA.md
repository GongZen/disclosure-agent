# 70개사 포괄 목차 스키마 — 실측과 설계 논의

매칭표를 만들기 전에 "절을 무엇으로 식별할 것인가" 를 정해야 한다. 그 판단에
필요한 실측을 모아 둔 문서다. 결론은 아직 안 났고, 무엇이 사실인지까지 적었다.

읽는 순서를 단계로 나눴다. 앞 단계를 건너뛰면 뒤 단계의 숫자가 무슨 뜻인지
안 보인다.

기준일 2026-08-31. 측정 대상은 2025년 사업보고서다.
문서 84건(정정본 포함) · 기업 70곳 · 제목 있는 절 12,653개.

---

# 0. 왜 이 문제가 생겼나

## 매칭표가 하는 일

검색은 질의를 받아 "이 질문은 어느 절을 봐야 하나" 를 먼저 짚는다. 짚으면
그 절의 조각을 순위에서 앞으로 당긴다.

```
"주주환원 정책이 어떻게 되나"   →   III/6 배당에 관한 사항을 짚는다
```

이 판단에 쓰는 표가 `data/eval/pathmap.csv` 다. 절마다 대표 낱말을 달아 둔다.

## 지금 표는 경로(path)를 열쇠로 쓴다

```
III/6   배당성향 · 배당수익률 · 결산배당 …
VIII/2  퇴직소득 · 보수총액 · 등기이사 …
```

`III/6` 같은 것이 경로다. 목차에서의 위치 번호다.

## 그런데 경로가 기업마다 흔들리는 곳이 있다

`무형자산` 주석을 찾아보니 이랬다.

```
"무형자산" 이라는 제목의 절이 64곳에 있는데, 경로가 32가지다

   A사  III/3/13      B사  III/3/15      C사  III/5/11
```

주석 항목 개수가 기업마다 달라 번호가 밀린다. 경로로 짚으면 11곳만 맞고
나머지는 놓친다.

여기서 "70개사를 전부 포괄하는 스키마를 만들자" 는 논의가 시작됐다.

사업보고서가 법정 서식이라 대분류는 예외 없이 같다. 스키마의 뼈대를 여기에

# 2단계. 하위 절은 세는 기준에 따라 개수가 다르다

"하위 절이 몇 개인가" 에 답이 하나가 아니다. 네 가지로 세어 봤다.

```
경로         목차에서의 위치 번호            III/3/13
제목 원본     절에 적힌 이름 그대로           13. 무형자산 (연결)
제목 정규화   번호·공백·꼬리표를 뗀 것        무형자산
태그 우선     aclass 가 있으면 그것, 없으면 경로
```

정규화 규칙은 이렇다.

```
1  앞의 번호 제거          "13. 무형자산"    → "무형자산"
2  공백 전부 제거          "공정가치 측정"    → "공정가치측정"
3  꼬리표 제거            "(연결)" · "(제조서비스업)" · "(금융업)"
```

# 3단계. 세 기준이 서로 어긋난다

어느 하나로 통일하면 되지 않을까 싶지만, 실측하면 셋이 양방향으로 어긋난다.

## 같은 경로인데 제목이 다르다

```
II/3   원본 제목 그대로 세면              정규화 뒤

       59곳  3. 원재료 및 생산설비          62곳  원재료및생산설비
        8곳  3. 파생상품거래 현황           11곳  파생상품거래현황
        3곳  3. (제조서비스업)원재료 및 생산설비
        3곳  3. (금융업)파생상품거래 현황
```

경로는 같은데 내용이 완전히 다르다. `II/2` ~ `II/5` 가 전부 이렇다.
금융지주·보험사 11곳이 다른 서식을 쓰고, 겸업사 3곳은 두 벌을 다 갖는다.
그래서 `(제조서비스업)` · `(금융업)` 꼬리표가 붙은 제목이 따로 나온다.

번호가 밀리는 경우도 있다.

```
49곳   2-2 연결 포괄손익계산서   2-3 연결 자본변동표   2-4 연결 현금흐름표
21곳   2-2 연결 손익계산서      2-3 연결 포괄손익계산서  2-4 연결 자본변동표   2-5 연결 현금흐름표
```

금융업이 손익계산서와 포괄손익계산서를 따로 두어 뒤가 하나씩 밀린다.
"연결 현금흐름표" 가 49곳은 `2-4`, 21곳은 `2-5` 다.

## 같은 제목인데 경로가 다르다

```
무형자산          64곳 · 경로 32가지
충당부채          51곳 · 경로 28가지
연결 현금흐름표     70곳 · 경로  2가지
```

## 같은 태그인데 제목이 다르다

`aclass` 는 원문 XML 에 붙은 XBRL 분류 코드다. 표기 차이를 흡수해 줄 것으로
기대했는데, 실측하니 그렇지 않았다.

```
NT_C_D810000  (60곳)   일반사항 42% · 지배기업의개요 11% · 회사의개요 9%
NT_C_D825700  (60곳)   관계기업및공동기업투자 27% · 관계기업투자 21% · 공동기업및관계기업투자 12%
NT_C_D822420  (60곳)   매출채권및기타채권 49% · 매출채권 11% · 매출채권및기타금융자산 8%
```

같은 코드가 붙은 같은 항목인데 기업마다 이름이 다르다. 띄어쓰기 문제가
아니라 작명 문제라 정규화 규칙으로는 못 합친다.

그리고 흔한 절일수록 더 갈린다.

```
기업 수      코드    제목 1가지    제목 2가지+    주 제목 점유율
50곳+        58        6          52          57%
20~49곳      44        6          38          56%
10~19곳      21        0          21          32%
1~4곳       321      173         148          80%
```

## 같은 제목인데 태그가 다르다

반대 방향도 성립한다.

```
제목 1,000가지 중 aclass 가 2가지 이상인 것 524가지 (52%)

  기타금융자산   →  NT_C_D822300 · D822390 · D822430 · D822470
  파생상품      →  NT_C_D822390 · D822430 · DS819000 · DX819000
```

기업이 XBRL 코드를 일관되게 붙이지 않는다.

## 정리

```
제목 정규화가 못 잡는 것    같은 것의 다른 이름     일반사항 / 지배기업의개요
태그가 못 잡는 것          같은 이름의 다른 코드    기타금융자산 4개 코드
경로가 못 잡는 것          같은 이름의 다른 위치    무형자산 32개 경로
```

셋이 다대다다. 어느 하나가 정답이 아니다.

다만 `aclass` 는 `III` 에만 있고 나머지 열한 개 대분류에는 하나도 없다.
그래서 12개를 전부 꿰는 기준으로는 제목 정규화가 유일하다.

```
대분류      aclass 있음    없음
I                 0        504
II                0        661
III           6,981      1,443     ← 여기에만 있다
IV                0        588
V ~ XII           0      2,304
```

## 띄어쓰기는 문제가 맞다. 다만 작다

```
번호만 뗀 제목            1,224가지
+ 공백까지 전부 제거       1,167가지
차이                        57가지  (4.7%)
```

띄어쓰기만 다른 짝이 52개다.

```
'중요한 회계추정 및 가정'  ·  '중요한 회계 추정 및 가정'
'공정가치측정'            ·  '공정가치 측정'
'당기손익-공정가치측정금융자산' · '당기손익-공정가치측정 금융자산'
```

공백 제거로 해소된다. 정규화 규칙에 넣어 두면 된다.

# 5단계. III 의 실체 — 3분의 2가 한 기업 전용이다

`III` 의 정규화 제목 1,054개가 각각 몇 곳에서 쓰이는지 세어 봤다.

```
   1곳       710개   67.4%     ← 3분의 2가 단 한 기업에만 있다
   2~4곳     189개   17.9%
   5~9곳      65개    6.2%
  10~19곳     29개    2.8%
  20~49곳     38개    3.6%
  50곳+       23개    2.2%
             ─────
             1,054개
```

20곳 이상 쓰는 것은 61개, 전체의 5.8% 다.

## 이것이 왜 중요한가

키워드를 뽑는 방식이 통계이기 때문이다.

```
점수 = (그 절에 나오는 문서 비율) ÷ (전체 절에 나오는 비율)

필터  MIN_COVER 0.7    그 절의 70% 이상 문서에 나와야 후보가 된다
      MIN_DF    5      전체에서 5개 절 이상에 나와야 한다
```

1곳짜리 절은 표본이 1이라 70% 를 잴 분모가 없다. 710개에는 이 계산이
성립하지 않는다.

사람이 손으로 채워도 마찬가지다. 그 기업 문서를 직접 읽어야 낱말이 나오고,
그렇게 만든 낱말은 그 기업 질의에서만 쓰인다.

# 6단계. 스키마와 작업표는 목적이 다르다

5단계의 결론은 이렇게 갈린다.

```
스키마로서    1,054 전량이 맞다
                누락이 없다. "이 절이 어디 갔지" 를 안 묻게 된다

작업표로서    61개(20곳 이상)가 맞다
                나머지는 키워드를 뽑을 근거가 없다
```

## 임계값을 어디에 두느냐에 따른 규모

태그 우선 기준으로 잰 값이다.

```
             III 만    12개 대분류 합계
   1곳 이상    465개        525개
   5곳 이상    144개        194개
  10곳 이상    134개        183개
  20곳 이상    113개        161개

  50곳 이상     69개        116개

```

정규화 제목 기준으로 재면 `III` 의 20곳 이상은 61개다. 기준이 다르므로
숫자를 섞지 않는다.

# 7단계. 남은 결정

## 결정 1 — 스키마에 무엇을 담을 것인가

```
방향 가   1,054 전량 + 키워드 칸은 비워 둔다
          얻는 것 — 누락 없는 전체 지도
          잃는 것 — 710행이 영구히 빈칸. 작업표로 쓰면 압도된다

방향 나   61개만 담는다
          얻는 것 — 그대로 작업표가 된다
          잃는 것 — 993개 절이 표에 없다. 나중에 "왜 빠졌지" 를 다시 묻는다

방향 다   한 파일에 두 층으로 담고 칸으로 구분한다
          기업수 칸을 두고 20곳 이상에만 키워드 칸을 연다
          얻는 것 — 지도와 작업표를 겸한다. 임계값을 나중에 바꿀 수 있다
          잃는 것 — 1,054행이라 열었을 때 한눈에 안 들어온다
```

## 결정 2 — 식별 열쇠를 무엇으로 할 것인가

```
제목 정규화 단일     12개를 다 덮는 유일한 기준. 같은 것의 다른 이름을 못 합친다
태그 우선           III 에서 더 잘 묶이나 나머지 11개에는 태그가 없다
대분류별로 다르게     각 구간에서 가장 안정적인 열쇠를 쓴다. 표가 두 종류가 된다
```

어느 것도 완전하지 않다는 것이 3단계의 실측 결론이다.

# 8단계. 이 조사에서 곁가지로 나온 것 셋

매칭표와 직접 관련은 없지만 알아 둘 것들이다.

## 하나 — 재무제표 주석은 pathmap 에 아예 없다

`III/3` · `III/5` 가 `pathmap.csv` 에 없는 이유를 추적했다.

```
III/3  연결재무제표 주석
   전체                        173개
   + char_len 300~30,000       84개
   + level in (major,minor)     0개   ← 여기서 전멸
```

주석은 둘 중 하나다. 하위로 다 쪼개져 `III/3` 자체는 빈 껍데기가 되거나
(79개, 0자 수준), 안 쪼개지고 통째로 남아 20만 자가 되거나(5개). 중간이 없다.
그리고 쪼개진 하위 3,157개는 전부 `level='group'` 이라 필터에서 빠진다.

## 둘 — IV 부모 절이 빈 껍데기다

```
IV 부모       84개 · 평균 7자 · 전부 300자 미만 · chunk 6개
IV/1 ~ IV/6   713조각.  내용은 전부 여기 있다
```

앞서 "IV 는 낱말이 없다" 고 적었던 것은 틀렸다. `IV/1`~`IV/6` 은 전부
12개씩 갖고 있다. 부모만 비어 있고, 그건 내용이 없어서다.

## 셋 — 그래서 채점이 안 되는 사례가 셋 있다

채점이 제목 부분일치다.

```python
def grade(hits, gold):
    return [h.rank for h in hits if any(g in h.title for g in gold)]
```

```
gold  "IV. 이사의 경영진단 및 분석의견"
hit   "3. 재무상태 및 영업실적"   →   불일치
```

정답을 `IV` 단독으로 지정한 사례가 셋이다.

```
set1-10   신한지주 경영진이 밝힌 경영진단 의견을 설명해줘
set1-19   엔씨소프트의 실적 변화를 설명해주고 그 이유를 찾아줘
set1-28   네이버 경영진이 밝힌 사업 전망과 위험 요인을 설명해줘
```

셋 다 못 찾는 8건에 들어 있다. 검색이 완벽해도 0점이다. 즉 실제 검색 실패는
8건이 아니라 5건이다. 셋 다 AI 가 만든 `set1` 이라 사용자 정답지는 아니다.

처리 방향은 정하지 않았다.

```
가  grade 가 부모·자식을 인정하게 고친다 (경로 접두사 판정)
나  gold 를 실제 내용 절로 고친다 (set1-19 → IV/3 재무상태 및 영업실적)
다  그대로 둔다. 성적이 실제보다 3건 낮게 나온다는 것을 알고 간다
```

# 9단계. 스키마를 실제로 만들면서 잡은 것 셋

2026-08-31 에 `section_schema.csv` 를 만들었다. 만드는 과정에서 앞 단계의
측정에 섞여 있던 오류 셋이 드러났다. 앞 단계 숫자를 읽을 때 감안해야 한다.

## 하나 — 감사보고서 564절이 섞여 있었다

감사보고서를 별도 문서로 떼어낼 때 `doc_subtype` 을 부모에서 물려받게 했다.
검색에서 살아 있게 하려던 것인데, 그 탓에 `doc_subtype='annual'` 로 거르면
감사보고서도 딸려 온다.

```
periodic   12,089절   경로 335가지
audit         564절   경로 1·2·3·4      ← 사업보고서 목차와 다른 체계다
```

`doc_group='periodic'` 을 조건에 넣어 걸렀다. 2~6단계의 숫자에는 이 564절이
들어 있다.

## 둘 — aclass 의 U 코드는 뜻이 없다

3단계에서 `aclass` 가 표기 차이를 흡수한다고 했는데, 절반만 맞았다.
`_D` 코드는 IFRS 표준 분류라 잘 묶이지만 `_U` 코드는 기업이 스스로 만드는
확장 슬롯이다.

```
D 코드 404종   코드당 제목 4.2가지 · 주 제목 점유율 74%
U 코드  38종   코드당 제목 9.0가지 · 주 제목 점유율 32%

NT_C_U800100   41절인데 제목이 26가지
    기타금융자산 · 당기손익-공정가치측정금융자산 · 보험가입자산 · 비지배지분 …
```

"사용자 정의 주석 1번" 자리에 회사마다 다른 것을 넣는다. 이걸 묶으면 무관한
절이 한 단위가 되어 공통 낱말이 하나도 안 나온다. 실제로 U 코드 15개가 전부
낱말 0개였다. `_U` 는 태그로 쓰지 않고 정규화 제목으로 떨어뜨린다.

## 셋 — 빈 껍데기 절이 하위 절과 합쳐졌다

상위 절과 하위 절의 제목이 같은 경우가 있다.

```
I    "I. 회사의 개요"   84절 · 평균 0자
I/1  "1. 회사의 개요"   84절 · 내용 있음
```

정규화하면 둘 다 `회사의개요` 라 한 단위가 된다. 절수가 168이 되고
`MIN_COVER 0.7` 이 118절 이상을 요구하는데 내용은 84절에만 있어 최대 50% 다.
낱말이 전멸했다. `I/1` 이 `pathmap.csv` 에서 갖고 있던 `신규연결` 등 12개가
통째로 사라졌다.

`char_len >= 300` 으로 빈 절을 뺐다. 상한은 두지 않는다. 낱말은 본문 앞
4,000자만 보므로 큰 절을 배제할 이유가 없고, 배제하면 주석처럼 큰 절을 잃는다.

## 정정된 수치

세 가지를 고친 뒤 다시 잰 값이다. 임계값도 20곳에서 5곳으로 바뀌었으므로
6단계의 표와 직접 비교하지 않는다.

```
III 절 6,955개 · 글자 26,583,615

제목 정규화만        단위 976가지 · 5곳 이상 143개 · 글자 커버 67.5%
태그 우선 (U 제외)   단위 584가지 · 5곳 이상 123개 · 글자 커버 72.7%
```

태그를 쓰면 단위가 20개 줄면서 커버리지가 5.2퍼센트포인트 오른다.
이 조사 도중에 "49% → 76%" 라고 보고했던 값이 있다. U 코드가 잘못 묶이고
빈 절이 섞인 상태에서 20곳 임계로 잰 것이라 위 숫자로 대체한다.

## 점수 스케일이 pathmap 과 다르다

나중에 검색에 물릴 때 반드시 봐야 하는 대목이다.

```
section_schema.csv 의 분모(전체 절)   9,877
pathmap.csv 의 분모                  3,561
배율                                 2.77배
```

점수가 `(그 단위 비율) ÷ (전체 비율)` 이라 분모가 커지면 점수도 그만큼 커진다.
같은 `신규연결` 이 `pathmap` 에서 42.4 이고 새 스키마에서 117.6 이다.

즉 `src/retrieval.py` 의 `PATH_MIN = 15.0` 을 그대로 쓰면 안 된다. 새 스키마로
갈아탈 때 문턱을 다시 재거나 점수를 정규화해야 한다.
