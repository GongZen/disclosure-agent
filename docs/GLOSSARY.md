```

   ↓   논의·확정
확정된 답                  이 문서의 결정란
```

정의를 바꾸면 구현물만 다시 만들면 된다. 코드 구조는 그대로다. 이것이 둘을 나누는 실익이다.

# 고정 용어

D1~D7이 아직 안 정해진 질문이라면, 아래는 이미 정해져서 흔들리면 안 되는 말이다. 새 이름을 만들지 않는다.

## 문서 관계

정정공시와 계약 해지를 다룰 때 쓰는 말은 여섯 개뿐이다.

| 용어 | 뜻 | DB 컬럼 |
|---|---|---|
| 정정본 | 앞선 공시를 고친 문서. 되짚기의 출발점 | `from_doc_id` |
| 원본 | 정정본이 아닌 최초 문서. 되짚기의 도착점 | `to_doc_id` |
| 지목일 | 정정본이 "이 날 낸 것을 고친다"고 적어둔 날짜 | `target_date` |
| 후보 | 지목일에 존재하는 같은 기업·같은 유형 문서들 | — |
| 연쇄 깊이 | 정정본에서 원본까지 되짚은 횟수. 0이면 직접 연결 | `chain_depth` |
| 미연결 사유 | 원본을 못 찾은 이유. D7의 네 갈래 | `unresolved_reason` |

읽는 순서는 이렇다.

```
정정본이 "지목일"을 적어둔다
       ↓
지목일에 있는 문서들 = 후보
       ↓
후보 중 정정본이 아닌 것 = 원본. 여기서 끝
후보가 또 정정본이면 그것의 지목일로 다시 간다  ← 연쇄 깊이 +1
```

후보는 지목일에 있는 문서의 수이지 원본의 수가 아니다. 후보 4건이어도 그중 원본은 1건일 수 있다.

## 기호가 겹치지 않게

같은 말을 다른 뜻으로 쓰면 문서를 읽을 수 없다. 아래를 지킨다.

| 말 | 이것만 가리킨다 | 문서 |
|---|---|---|
| 단계 | S1~S11. Agent가 질의를 처리하며 밟는 순서 | `PIPELINE.md` |
| 층 | D7의 값 추출 실패 판정. 1층·2층·3층 | 이 문서 D7 |
| 작업 | W1~W10. 우리가 순서대로 하는 일 | `PLAN.md` |
| 계층 | DB 테이블 묶음. 기준·관계·사실·본문 | `SCHEMA.md` |

연쇄 정정을 되짚는 횟수는 단계가 아니라 연쇄 깊이다. "레이어"는 쓰지 않는다.

# D1. 자금조달의 범위

## 질문

주요사항보고서 28개 유형 중 어디까지를 자금조달로 볼 것인가.

## 왜 문제인가

참고 질의가 "유형별(유상증자, CB, BW, EB)"이라고 네 유형을 예로 들었으나, 실제 데이터는 그 예시와 어긋난다. 예시 중 하나는 아예 없고, 예시에 없는 유형이 예시보다 많다.

경계에 있는 유형의 건수가 커서 포함 여부가 결과를 크게 바꾼다. 전체 598건 중 341건이 자기주식 관련이다.

## 관측된 사실

주요사항보고서 598건의 유형 전수 집계다.

### 자금조달 — 자본

| 유형 | 건수 |
|---|---|
| 유상증자결정 | 55 |
| 감자결정 | 6 |
| 무상증자결정 | 5 |

무상증자는 자본금이 늘지만 회사로 돈이 들어오지 않는다. 감자는 자본이 줄어든다. 둘 다 자금조달로 보기 애매하다.

### 자금조달 — 부채·메자닌

| 유형 | 건수 |
|---|---|
| 상각형조건부자본증권발행결정 | 71 |
| 전환사채권발행결정 (CB) | 22 |
| 자본으로인정되는채무증권발행결정 | 6 |
| 교환사채권발행결정 (EB) | 4 |
| 신주인수권부사채 (BW) | 0 |

상각형조건부자본증권은 금융지주사가 발행하는 자본성 증권이다. CB의 세 배가 넘는데 참고 질의 예시에는 없다.

BW는 코퍼스에 0건이다. 평가 질의에 BW가 나오면 "제공 데이터에서 확인되지 않음"이 정답이고, 이것이 지표 7번의 득점 지점이다.

### 자기주식

| 유형 | 건수 |
|---|---|
| 자기주식처분결정 | 157 |
| 자기주식취득결정 | 91 |
| 자기주식취득신탁계약체결결정 | 47 |
| 자기주식취득신탁계약해지결정 | 43 |
| 자기전환사채매도결정 | 2 |
| 제3자의전환사채매수선택권행사 | 1 |

처분은 회사에 돈이 들어오는 경우가 있어 자금조달로 볼 여지가 있었다. 157건을 전수로 열어 확인했다.

#### 자기주식처분 157건 전수 (2026-08-15)

공시 건수와 실제 사건 수가 다르다. 정정본 15건 중 13건이 같은 유형 원본에 연결돼 있고, 그 13건은 이미 센 처분의 재공시다. 연결은 `doc_relation` 조회로 확인했다.

```
공시 157건  −  정정 중복 13건  =  실제 144 사건
```

처분목적을 갈래로 나눈 결과다. 목적 문자열은 78가지였고 추출 실패와 빈 값은 없다.

| 갈래 | 공시 | 사건 |
|---|---|---|
| 보상·상여 | 145 | 136 |
| 교환사채 대응 | 5 | 2 |
| 합병·주식교환·단주 | 5 | 4 |
| 자금 확보 | 2 | 2 |

돈이 실제로 들어왔는지는 목적이 아니라 서식 `6. 처분방법`이 가른다. 네 갈래에 주식수를 나눠 적게 돼 있다.

```
시장을 통한 매도 · 시간외대량매매   시장에 판 것.   회사가 대금을 받는다
장외처분 · 기타                  임직원 계좌로 교부.  현금이 오가지 않는다
```

시장 쪽에 주식수가 있는 것은 5 사건뿐이다.

| 기업 | 처분예정금액 | 목적 |
|---|---|---|
| 엘에스일렉트릭 | 635.4억 | 투자재원 확보 및 재무구조 개선 |
| 한미반도체 | 279.8억 | 신규장비 개발자금 확보 |
| 현대오토에버 | 3.7억 | 주식매수청구권 취득분·합병 단주 |
| 신한지주 | 2.8억 | 포괄적 주식교환 과정의 단주 매각 |
| 메리츠금융지주 | 0.2억 | 주식매수청구권 취득분 기한 내 처분 |

보상·상여 갈래에서 시장 매도는 0건이다. 전부 교부다.

앞의 두 건은 사업보고서 현금흐름표와 대조된다. 회계기준이 대금을 받은 처분만 재무활동 현금유입에 적고 교부는 "현금유출입이 없는 중요한 거래"로 따로 표시한다.

```
엘에스일렉트릭   공시 635.4억  ↔  현금흐름표 633.9억
한미반도체      공시 279.8억  ↔  현금흐름표 276.4억
```

다만 현금흐름표는 판정 기준으로 쓸 수 없다. 연간 총액이라 개별 처분 건과 대응되지 않는다. 위 두 건이 맞아떨어진 것은 그 해에 처분이 하나뿐이었기 때문이다. 판정은 처분방법으로 하고 현금흐름표는 회계기준과 어긋나지 않는지 보는 보조 근거로 둔다.

### 보류한 것

상각형조건부자본증권을 자본·부채·메자닌 중 어디로 분류할지는 정하지 않는다.

```
이유   상위 카테고리를 요구하는 질의가 참고 질의 6개에 없다
       유형별 나열로 답하면 카테고리가 답에 등장하지 않는다
       서식에 자본·부채 표시가 없어 코퍼스 안에 분류 근거가 없다

재개   상위 카테고리를 요구하는 질의가 실제로 관측되면 그때 정한다
```

### 확인하지 못한 것

SK하이닉스 사업보고서 현금흐름표에 자기주식 처분 재무활동 유입이 2025년 650억, 2024년 938억으로 잡혀 있다. 그런데 그 회사의 자기주식처분 공시 15건은 전부 교부다.

주요사항보고서는 이사회 결의를 요하는 건만 나오고 현금흐름표는 그 해 전체 흐름이라 범위가 다른 것으로 보이나 확인하지 못했다. 자기주식 처분을 통한 자금조달을 물으면 공시 기준으로 답하되 그것이 회계상 전부가 아닐 수 있음을 밝힌다.

# D2. 설비투자의 의미

## 질문

설비투자를 연간 총액으로 볼 것인가 개별 투자 건으로 볼 것인가.

## 왜 문제인가

같은 단어에 두 가지 답이 있고, 데이터도 두 곳에 있다. 질의에 따라 다른 답이 나와야 한다.

## 관측된 사실

연간 총액은 XBRL 태그로 뽑을 수 있다. 사업보고서 25건 표본 전부에 있다.

```
ifrs-full_PurchaseOfPropertyPlantAndEquipmentClassifiedAsInvestingActivities   25/25
```

현금흐름표의 유형자산 취득액이고 연간 설비투자 총액에 해당한다.

개별 투자 건은 거래소 신규시설투자 공시다. 43건, 21개사뿐이다.

```
SK하이닉스 (2024-04-24)
  투자구분      시설증설
  투자대상      청주 M15X 건설
  투자금액(원)  5,296,200,000,000
  자기자본대비   9.90%
  투자기간      2024-04-24 ~ 2026-10-30
```

## 선택지

| 질의 형태 | 어디서 |
|---|---|
| 규모 비교 — "A와 B 중 어느 쪽이 큰가" | 연간 총액 (XBRL) |
| 내역 조회 — "어떤 설비투자를 했나" | 개별 공시 (거래소) |

# D3. 매출액 계정명 통합

## 질문

업종에 따라 다른 계정들을 하나로 묶어도 되는가. 묶는다면 어떤 근거로 묶고 답변에서 무엇이라고 부를 것인가.

처음에는 "여섯 가지 표기를 어떻게 통합할 것인가"로 적었으나 그 질문이 틀렸다. 매출액과 영업수익은 같은 항목의 다른 표기가 아니라 정의상 다른 계정이다. 재화 판매 수익과 서비스·금융업 영업 수익을 회계 기준이 업종에 따라 다르게 표시하도록 정한 것이다. 표기 변형으로 취급하면 "삼성전자와 HMM의 매출을 비교해달라"에 근거 없이 두 값을 나란히 놓게 된다.

## 왜 문제인가

표 파싱은 계정명을 찾아 그 옆 숫자를 읽는 방식이다. 이름이 다르면 못 찾는다. 그리고 금융·보험사는 계정 체계 자체가 다르다.

묶을 근거의 후보는 XBRL 태그다. 서로 다른 계정명이 같은 태그(`ifrs-full_Revenue`)를 달고 있으면 회계 기준이 같은 요소로 본다는 뜻이다. 실측으로 확인한 뒤 정한다.

## 관측된 사실

사업보고서 207건의 연결 손익계산서 첫 계정 집계다.

| 계정명 | 건수 |
|---|---|
| 매출액 | 103 |
| 영업수익 | 24 |
| 수익(매출액) | 24 |
| 수익 | 11 |
| 매출 | 9 |
| 패턴 미매칭 | 36 |

미매칭 36건은 금융·보험사가 보험수익 등 다른 계정 체계를 쓰기 때문으로 보인다. 이 부분은 추가 확인이 필요하다.

XBRL 태그가 있는 문서에서 계정명을 자동 수집할 수 있다. 사업보고서 60건에서 뽑은 결과다.

```
ifrs-full_CostOfSales  ←  매출원가(64) · 매출원가 (주21)(4) · 매출원가 (주20,24)(4)
ifrs-full_GrossProfit  ←  매출총이익(87) · Ⅲ.매출총이익(4) · 매출총이익(손실)(3)
ifrs-full_ProfitLoss   ←  당기순이익(312) · 당기순이익(손실)(303) · 당기순손익(49)
```

손으로 세어 여섯 가지였던 표기가 자동 수집으로는 76가지가 나온다. 다만 계정명의 30%가 두 개 이상 태그에 매핑되고, 부문별 표에서 온 노이즈가 섞인다.

## 선택지

## 태그 보유 실측 — 2026-08-17

앞서 "정기공시 894건 중 488건"이라고 적었으나 모집단이 틀렸다. 정기공시는 1,054건이고 전수 스캔 결과는 이렇다.

```
XBRL 태그 보유   562건 (53%)
태그 없음        492건    그중 474건은 연결/별도 축 문맥을 갖고 있다
```

그리고 태그 유무가 무작위가 아니라 시기로 갈린다.

```
태그 있음   2023  78 · 2024 102 · 2025 310 · 2026  72
태그 없음   2023 260 · 2024 230 · 2025   1 · 2026   1
```

2025년부터 거의 전부 태그가 있다. 이 편향 때문에 태그로 만든 정답지로 표 파서를 채점하면 2025년 서식에만 맞춰질 수 있다. 대비책은 같은 기업의 2025년 문서에 실린 과거 연도 비교 열을 쓰는 것이다. 태그 있는 문서의 2023년 값과 태그 없는 2023년 문서의 값을 대조하면 시기를 건너뛴 채점이 된다.

| 방향 | 결과 |
|---|---|
| XBRL 태그만 사용 | 정확하지만 2023~2024 구간을 거의 못 뽑음. 1,054건 중 562건만 태그 보유 |
| 수작업 사전 | 통제 가능하지만 17%가 남음 |
| 자동 수집 + 정제 | 촘촘하지만 표 종류 판별과 빈도 하한 등 전처리 필요 |
| 금융업 별도 규칙 | 미매칭 36건을 커버. 계정 체계를 따로 조사해야 함 |

## 영향

| 항목 | 내용 |
|---|---|
| 영향받는 단계 | S6 값 조회 |
| 구현물 | `synonym_account` 사전 |
| 필요 작업 | W5 |

## 결정 — 2026-08-18 확정

업종에 따라 다른 계정을 하나로 묶지 않는다. 각각 원문 이름 그대로 담고 `item_code`로 구분한다.

```
제조·서비스   매출액 · 수익(매출액) · 영업수익 · 매출    → revenue 계열
은행지주      순이자손익 · 순이자이익                   → net_interest_income
              순수수료손익 · 순수수료이익                → net_fee_income
보험          보험서비스결과 · 보험손익                  → insurance_result
공통          영업이익 · 당기순이익                     업종과 무관하게 대응된다
```

코퍼스 70개 기업의 최신 사업보고서에서 연결 손익계산서 첫 계정을 전수로 셌다.

| 계열 | 기업 수 | 첫 계정 |
|---|---|---|
| 제조·서비스 | 63 | 매출액 · 수익(매출액) · 영업수익 · 매출 |
| 은행지주 | 5 | KB금융 순이자손익 · 하나금융지주 순이자이익 · 신한지주·우리금융지주·메리츠금융지주는 영업이익이 먼저 오고 그 아래 순이자손익 |
| 보험 | 2 | 삼성생명 보험서비스결과 · 삼성화재해상보험 보험손익 |

처음에는 두 갈래로 정했으나 실측하니 셋이었다. 보험사는 IFRS 17 보험계약 기준을
적용하면서 보험료를 받은 시점이 아니라 서비스를 제공한 기간에 나눠 수익을 인식한다.
그래서 은행의 이자 구조와도 다른 계정이 생겼다.

`영업수익` 은 통신·운송·서비스 업종이 쓰는데 `ifrs-full_Revenue` 태그를 단다.
회계 기준이 매출액과 같은 것으로 보므로 revenue 계열에 넣는다. 표기가 업종 관행에
따라 다를 뿐이고, 정의가 다른 것은 금융·보험 쪽이다.

묶지 않는 이유는 정의가 다르기 때문이다. 매출액은 재화를 팔아 받은 총액이고 순이자손익은 이자수익에서 이자비용을 뺀 순액이다. 회계 기준이 금융회사에 순액 표시를 허용해 손익계산서 최상단이 순이자손익으로 시작한다.

K-IFRS상 금융회사의 영업수익 개념은 존재한다. 이자수익·수수료수익·유가증권 평가처분이익 등을 합한 것이다. 그런데 표시가 강제되지 않아 KB금융 연결 포괄손익계산서에는 그 소계가 없다. 우리가 합산해 만들면 어느 항목까지 더할지를 우리가 정하게 되므로 `POLICY.md` 1항에 걸린다.

```

```

순서가 중요하다. 값을 먼저 주고 뒤에 단서를 붙이면 읽는 사람이 두 숫자를 나란히 비교한 뒤에야 그 말을 보게 된다.

# D4. 연결과 별도의 기본값

## 질문

질의에 명시가 없을 때 연결과 별도 중 무엇으로 답할 것인가.

## 왜 문제인가

두 값이 다르고, 어느 쪽을 답하느냐에 따라 수치가 달라진다. 참고 질의는 "2025년 연결기준 매출액"처럼 명시했지만 실제 평가 질의가 항상 명시하리라는 보장이 없다.

## 관측된 사실

XBRL의 `ACONTEXT`에 둘 다 들어 있어 어느 쪽이든 뽑을 수 있다.

```
CFY2024dFY_ifrs-full_ConsolidatedAndSeparateFinancialStatementsAxis_ifrs-full_ConsolidatedMember
CFY2024dFY_ifrs-full_ConsolidatedAndSeparateFinancialStatementsAxis_ifrs-full_SeparateMember
```

## 선택지

| 방향 | 결과 |
|---|---|
| 연결 우선 후 명시 | 통상 기준에 부합. 답변에 "연결 기준"이라고 밝힘 |
| 둘 다 제시 | 누락 위험 없음. 답변이 길어지고 질문에 없던 정보가 붙음 |

## 결정 — 2026-08-17 확정

연결을 기본값으로 한다. 질의에 명시가 없으면 연결 기준으로 답하고, 답변에 "연결 기준"이라고 밝힌다. 별도 기준을 물으면 그것으로 답한다.

이유는 둘이다. 참고 질의가 "2025년 연결기준 매출액"처럼 연결을 지목했고, 기업의 실적을 말할 때 통상 연결을 본다. 자회사를 포함한 그룹 전체의 살림이기 때문이다.

둘 다 제시하는 방향은 택하지 않았다. 묻지 않은 정보가 답변에 붙으면 읽는 사람이 어느 쪽이 답인지 판단해야 하고, 지표 4의 간결성에도 불리하다.

# D6. 주요 계약의 기준

## 질문

금액 기준선을 둘 것인가, 공시된 것 전부를 주요 계약으로 볼 것인가.

## 왜 문제인가

참고 질의가 "2025년에 체결한 주요 계약"이라고 표현한다. 무엇이 주요인지 정해야 답이 확정된다.

## 관측된 사실

거래소 단일판매·공급계약 공시는 일정 규모를 넘을 때 제출 의무가 생긴다. 각 공시에 매출액 대비 비율이 기재되어 있어 추가 기준선을 걸 수도 있다.

```
계약금액(원)   22,764,764,160,000
최근매출액(원)  300,870,903,000,000
매출액대비(%)   7.6
```

다만 의무공시만 있는 것이 아니다. 1,169건 전수를 열어보니 자율공시가 섞여 있다. 자율공시는 규모 요건과 무관하게 회사가 스스로 내는 것이다.

```
HD현대일렉트릭 20240830   매출액대비 2.45% · 대규모법인여부 해당
                        대규모법인 의무 기준 2.5% 에 미달해 자율공시로 제출
```

그래서 "공시된 것은 전부 규모 요건을 통과했다"는 근거는 의무공시에만 성립한다.

## 결정 — 2026-08-15 확정

금액 기준선을 두지 않는다. 공시된 것 전부가 대상이다.

근거는 규모 요건이 아니다. 공시된 거래는 전부 답변에 쓸 수 있어야 한다는 것이 이유다. 우리가 선을 그어 답을 버리면 그것은 공시에 있는 기준이 아니라 우리가 만든 기준이고, "매출액 대비 3% 미만이라 제외했습니다"는 지표 7의 한계 고지가 아니라 임의 누락이 된다.

대신 `event_contract`에 공시 구분 컬럼을 둔다. 의무공시인지 자율공시인지를 담아, 답변에서 "규모 요건에 못 미치는 자율공시도 포함되어 있습니다"를 밝힐 수 있게 한다. 지금은 이 정보가 문서 제목 문자열에만 있어서 조회로 걸러낼 수 없다.

개수를 제한하는 질의("주요 계약 5건만")에서 무엇으로 상위를 고를지는 여기서 정하지 않는다. 데이터를 거르는 문제가 아니라 답변에서 순서를 정하는 문제라 W7·W8로 넘긴다.

### 계약명 정규화 규칙 — 함께 확정

같은 계약이 표기 차이로 쪼개지는 것을 막는 규칙이다. 1,169건 전수에서 단계별로 병합 결과를 보고 정했다.

| 단계 | 병합 그룹 | 채택 |
|---|---|---|
| 유니코드 정규화 + 앞뒤 공백 제거 | 0 | 한다. 무해한 안전장치 |
| 모든 공백 제거 | 5 | 한다. 전부 같은 계약이었다 |
| 구분기호 통일 | 0 | 하지 않는다. 효과 없음 |
| 괄호 안 내용 제거 | 10 | 하지 않는다. 대부분 다른 계약 |
| 끝의 "사업" 제거 | 1 | 한다 |
| 공사·계약·건·외 제거 | 0 | 하지 않는다. 효과 없음 |

괄호를 지우면 안 되는 이유가 실물로 나왔다. 괄호 안이 계약을 구분하는 정보다.


# D7. 확인 불가의 네 갈래

## 질문

답하지 못하는 경우를 몇 갈래로 나누고 각각 어떻게 표기할 것인가.

## 왜 문제인가

의미가 전혀 다른데 같은 말로 답하면 안 된다. 지표 7번이 "보유 데이터로 답변할 수 없는 질의를 식별하고 무리한 답변 대신 한계를 고지하는가"를 본다. 식별에는 구분이 포함된다.

이 정의는 다른 항목과 성격이 다르다. 답변 형식 전체에 걸리고, 관계 테이블의 컬럼에도 들어간다.

## 관측된 사실

네 경우가 실제로 존재한다.

### 범위 밖

정정공시 1,004건 중 293건은 원본이 2023-01-01 이전이라 코퍼스에 없다. 계약 해지도 일부가 같다. 한미약품 사례의 원 계약은 2021-05-18이다.

BW 조회도 여기 해당한다. 코퍼스에 0건이다.

코퍼스에 없는 기업을 물은 경우도 마찬가지다. 대상은 70개사뿐이다.

### 문서 없음

정기공시는 상장 이후 분만 존재한다. 시프트업은 2024-07 상장이라 정기공시가 7건뿐이다. 주요사항·거래소공시는 해당 이벤트가 없으면 0건이다.

건수 0은 결측이 아니라 제출 의무가 없었다는 뜻이다.

### 추출 실패

우리 파이프라인의 한계이지 데이터의 한계가 아니다. 앞의 둘과 성격이 다르며, 이 구분을 흐리면 우리 실패를 데이터 부재로 위장하게 된다.

지금 관측된 것은 셋인데 각각 성격이 다르다. 여기 적힌 숫자는 고정값이 아니라 현재 시점의 측정값이고, W3과 W5를 거치며 줄어든다.

| 항목 | 원인 | 줄어드는가 | 언제 |
|---|---|---|---|
| 계정명 미매칭 36/207건 | 금융·보험사가 다른 계정 체계를 씀 | 줄어든다 | W5 (D3 확정 시) |
| 정정 연결 모호 43건 | 같은 날 원본이 2건 이상 | 대부분 해결된다 | W3 |
| 대체 수집 3건 | DART가 원본 XML을 제공하지 않음 | 판단 필요 | W5 또는 포기 |

정정 연결 모호는 방법이 이미 있다. 날짜로 후보를 좁힌 뒤 정정 전 값을 후보의 값과 대조하면 확정된다.

계정명 미매칭은 금융업 계정 체계를 조사해 사전에 넣으면 줄어든다. 얼마나 줄어들지는 조사해봐야 안다.

대체 수집 3건은 `{접수번호}_viewer.html`이 함께 있어 그걸 파싱하면 될 수도 있다. 확인하지 않았고, 3건을 위해 별도 파서를 만드는 것이 값어치가 있는지는 별개 판단이다.

```
한화에어로스페이스  분기보고서 (2026.03)
KB금융              [기재정정]사업보고서 (2025.12)
한화오션            [기재정정]분기보고서 (2024.03)
```

### D7이 정하는 것과 정하지 않는 것

```
정하는 것       답하지 못했을 때 무엇이라고 말할 것인가      표기 규칙
정하지 않는 것   왜 못 뽑았고 어떻게 줄일 것인가             각 작업에서
```

D7은 해결 노력을 다 한 뒤에도 남는 잔여분을 위한 규칙이다. 위 세 항목을 줄이는 작업은 W3과 W5에서 각각 다룬다.

## 결정 — 2026-08-14 확정

네 갈래로 나눈다. 셋이 아닌 이유는 문서 존재 여부 자체가 정보를 담기 때문이다.

```
문서가 있다   →  그 유형의 공시 의무가 발생했고 회사가 제출했다
문서가 없다   →  그런 사건이 없었거나 공시 대상이 아니었다
```

현대자동차에 거래소공시가 0건이라는 것은 "3년간 공시 의무가 생길 규모의 단일 공급계약이 없었다"는 뜻이고 그 자체가 답이다. 사업보고서는 있는데 설비투자 기재가 없는 것과는 다른 정보다.

| 갈래 | 코드값 | 문구 |
|---|---|---|
| 범위 밖 | `out_of_scope` | 제공된 공시 데이터(2023.01~2026.03, 70개사) 범위 밖입니다 |
| 문서 없음 | `no_document` | 해당 기간에 관련 공시가 존재하지 않습니다 |
| 미기재 | `not_disclosed` | 해당 항목이 공시에 기재되어 있지 않습니다 |
| 추출 실패 | `extract_failed` | 해당 항목을 Agent가 확인하지 못했습니다 |

넷째에 주체를 밝힌 이유는 우리 한계임을 명확히 하기 위해서다. 이걸 셋째와 섞으면 우리가 못 읽은 것을 회사가 안 쓴 것으로 진술하게 되고, 그건 지표 7의 한계 고지가 아니라 지표 4의 거짓 진술이 된다.

### 판정 규칙

앞의 둘은 SQL 한 줄로 갈린다.

```
기업이 company 에 없다 · 기간이 코퍼스 밖   →  out_of_scope
document 조회가 0건                        →  no_document
```

뒤의 둘은 문서가 있는데 값을 못 찾은 경우다. 파서 입장에서는 두 경우가 똑같이 "못 찾음"으로 보이므로 3층 확인을 거친다. 싸고 확정적인 것부터 본다.

```
값 추출 실패
  1층  이 문서가 XBRL 태그를 가졌는가?          문자열 검색 1회
         아니오 → 2층
         예 → 해당 태그가 있는가?
                없다 → not_disclosed    확정
                있다 → extract_failed   확정

  2층  해당 항목이 속할 섹션이 문서에 있는가?    SQL 1회 · 정기공시만
         없다 → not_disclosed    확정
         있다 → 3층

  3층  항목 키워드가 문서 텍스트에 있는가?       전문 검색 1회
         없다 → not_disclosed
         있다 → extract_failed
```

1층이 확정적인 이유는 XBRL 태그가 있는 문서에서 해당 태그가 없으면 회사가 그 항목을 보고하지 않은 것이기 때문이다. 다만 정기공시 894건 중 488건에만 적용된다.

2층이 결정적인 사례가 있다. 금융지주사에는 "II-3. 원재료 및 생산설비" 섹션이 아예 없다. 제조업이 아니기 때문이다. 설비투자를 물으면 섹션 부재만으로 확정된다.

3층까지 갔는데 키워드 사전에 없는 표기로 적혀 있으면 `not_disclosed`로 오판한다. 오판율은 사전 품질에 비례하며 D3과 연결된다. W10 자체 평가에서 이 오판을 세어 사전을 보강한다.

### 답변 형식

한계를 앞에 밝힌다. 뒤에 붙이면 읽는 사람이 놓치고, 읽다가 "이게 전부인가" 하는 혼란이 생긴다.

```

```

