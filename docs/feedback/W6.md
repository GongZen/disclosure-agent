# W6 — 본문 계층

정기공시 1,051건을 목차 단위로 잘라 `section` 에 담고, 임베딩 한도에 맞춰
`chunk` 로 나누고, 각 조각을 벡터로 바꾼다.

상태 — 진행 중. 한 번 전부 만들었다가 전부 버리기로 했다.

---

## 무엇을 하는 작업인가

W5 까지는 숫자를 다뤘다. 매출액이 얼마이고 자산총계가 얼마인지는
`fact_financial` 에 들어 있다. 표에서 꺼낸 값이라 정확한 위치를 알고 꺼낸다.

W6 은 문장을 다룬다.

```
지금 못 답하는 것
   삼성전자가 올해 어떤 사업을 새로 시작했나
   현대차의 주요 위험 요인은 무엇인가
   카카오의 감사인이 지적한 핵심감사사항은
```

이런 것은 표에 없고 문장으로 적혀 있다. 문장은 위치가 정해져 있지 않아
값처럼 꺼낼 수 없다. 대신 통째로 잘라 두고, 질문이 오면 비슷한 조각을 찾는다.

### 왜 자르는가

사업보고서 하나가 100만 자를 넘는다. 통째로 두면 두 가지가 안 된다.

```
검색이 안 된다      문서 하나가 통째로 걸리면 어느 부분이 답인지 모른다
임베딩이 안 된다    한 번에 넣을 수 있는 길이에 한도가 있다
```

그래서 목차 단위로 자른다. `I. 회사의 개요`, `II. 사업의 내용` 처럼
문서가 스스로 그어 둔 경계를 쓴다. 우리가 규칙을 만들면 문서마다 어긋나지만,
문서가 그은 경계는 그 문서 안에서 항상 맞는다.

### 세 겹으로 쌓는다

```
원문 XML          주최측이 준 파일. 읽기만 한다
   ↓ 목차 단위로 자른다
section           절 하나가 한 행. 텍스트가 들어 있다
   ↓ 임베딩 한도(5,000자)에 맞춰 나눈다
chunk             검색 단위. 텍스트와 벡터가 들어 있다
```

`embedding` 은 별도 테이블이 아니라 `chunk` 의 컬럼이다. 그래서 `chunk` 를
다시 만들면 임베딩도 함께 사라진다. 이 구조 때문에 아래 실패의 대가가 컸다.

## 1차 시도 — 전부 만들었다가 전부 버렸다

### 무엇을 했나

```
section    117,561 조각
chunk      141,524 조각
토큰       141,524 · 95분
OpenAI 임베딩  141,524 · 2시간 · 42,474원
CLOVA 임베딩     1,321 (진행 중 중단)
```

### 무엇이 문제였나

문서 468건(44.5%)에서 표 하나가 문서의 나머지를 통째로 삼켰다.

```
CJ제일제당 2024년 사업보고서
   "5. 정관에 관한 사항" 의 표 하나가 899,194자
   그 안에 II. 사업의 내용부터 문서 끝까지가 들어 있었다

크래프톤 2024년 사업보고서
   "2. 회사의 연혁" 이 694,293자
   끝부분이 회계감사 내용이었다

신한지주 2025년 반기보고서
   조각 125개 중 120개가 0자
   한 절이 문서 글자의 98.1%를 차지
```

삼켜진 목차가 30,426개. 영향받은 조각이 54,904개(38.8%)다.

그리고 사업보고서 210건에서 첨부 감사보고서가 통째로 빠져 있었다.

```
LG유플러스 2025년 사업보고서의 마지막 조각들

        0자   독립된 감사인의 감사보고서
        0자   (첨부)연 결 재 무 제 표
        0자   주석
        0자   연결 내부회계관리제도 감사 또는 검토의견
        0자   외부감사 실시내용
```

제목만 있고 내용이 없다.

### 어떻게 알았나

늦게 알았다. 그 경위 자체가 기록할 값어치가 있다.

```
1  section 적재 후 검증을 돌렸다
      참조 무결성 0 · 중복 0 · 스키마 이상 0      전부 통과
      0자 조각 39,677개                        이상 신호

2  그 신호를 설명으로 덮었다
      "대분류 제목은 원래 내용이 없다.
       III. 재무에 관한 사항 같은 제목은 하위 조각에 내용이 들어간다"
      설명은 그럴듯했고 일부는 사실이었다. 그러나 하나도 열어보지 않았다

3  chunk 를 만들고 임베딩했다                    42,474원 · 2시간
4  토큰을 만들었다                              95분
5  S7 검색을 만들며 조각을 들여다봤다
6  사용자께서 물으셨다
      "특정 섹션이 닫히지 않아 그 이후 모든 표가 빨려들어간 것인가?"
7  파보니 그랬다
```

2번에서 CJ제일제당 문서 하나만 열었으면 즉시 드러났다. 39,677개는 전체
조각의 33.7%다. 3분의 1이 빈 것을 "원래 그렇다" 로 넘긴 것이다.

이 실패를 `feedback/README.md` 에 규율로 남겼다. 이상 신호를 설명으로
덮지 않는다, 문제를 발견하면 멈춘다, 둘이다.

## 원인 규명 — 셋이었다

처음에는 "표가 안 닫혔다" 하나로 봤다. 파고들자 셋이었고, 뒤의 둘은 후처리로
잡을 수 없는 것이었다.

### 먼저 배제한 것 — 원문은 멀쩡하다

```
1,051건 전수

   <TABLE> 과 </TABLE> 개수 불일치        0건
   <TABLE-GROUP> 여닫이 불일치            0건
   CDATA                                  0
   주석 <!--                              0
   인코딩 깨짐                            0
   속성 값 안의 >                         0
```

DART 가 태그를 빠뜨린 것이 아니다. 우리가 읽는 방식이 문제였다.

### 원인 1 — 본문의 꺾쇠가 태그로 읽힌다

```
규모   문서 1,008건(95.9%) · 42,002개 · 기업 70개 전부
```

원문에 나오는 태그 이름을 전수로 세니 1,056종이었다. 실제 DART 서식 태그는
33종이고 나머지 1,023종은 전부 본문 텍스트였다.

```
<배틀그라운드>                              크래프톤. 게임 이름
<Mirae Asset Securities (HK) Limited>       미래에셋증권. 해외 법인명
<PlayStation 5>                             제품명
<전기말> <당기말> <당분기>                    표 머리글
<삭제> <신설> <좌동>                          정관 변경 대조표
< TV 시장점유율 추이 >                        표 제목
```

XML 에서 `<` 는 태그의 시작이다. 본문에 쓰려면 `&lt;` 로 적어야 한다.

#### 어떻게 표를 삼키는가

최소 예제로 재현했다.

```
원문
   <TABLE><TR><TD>제 <전기말> 기</TD></TR></TABLE>
   <TITLE>II. 사업의 내용</TITLE>
   <P>본문</P>

파서가 읽은 것
   TABLE
     TR
       TD
         전기말
     TITLE          ← 표 안으로 들어갔다
     P              ← 표 안으로 들어갔다
```

닫는 태그가 한 칸씩 밀린다.

```
</TD>      →  <전기말> 을 닫는다
</TR>      →  <TD> 를 닫는다
</TABLE>   →  <TR> 을 닫는다
              <TABLE> 은 닫히지 못한다
```

`<TABLE>` 이 열린 채 남으니 그 뒤 문서 전체가 표 안으로 들어간다.

### 원인 2 — 속성 값 안의 따옴표. 손실은 이쪽이 크다

```
규모   원인 1을 고친 뒤에도 오류가 남은 문서 84건 · 기업 70개 전부
손실   문서당 31~68%
```

`ENG` 는 계정과목의 영문 이름을 담는 속성이다. 그 값 안에 따옴표가
이스케이프 없이 들어 있다.

```
ENG=""Snow Corporation"                                   NAVER
ENG="" CJ telenix co.,Ltd ""                              CJ제일제당
ENG="Provisions for credit losses ... contracts ""        KB금융
ENG=""Development of a Mid-Low Temperature ... ""         HD현대일렉트릭
```

작성자가 의도한 것은 `"Snow Corporation"` 이라는, 따옴표까지 포함한 문자열이다.
그러려면 `&quot;` 로 적어야 한다.

파서는 왼쪽부터 읽는다.

```
ENG=""Snow Corporation"
    ↑ 등호. 값이 온다
     ↑ 여는 따옴표. 값이 시작됐다
      ↑ 또 따옴표. 값이 끝났다고 판단한다. 값은 빈 문자열
       ↑ 그런데 Snow 가 있다. 공백도 > 도 아니다
```

여기서 오류를 내고, `recover` 모드는 그 태그를 통째로 버린다. 여는 태그가
사라지고 닫는 태그만 남으니 원인 1과 같은 밀림이 일어난다.

현대자동차의 오류 로그가 밀림을 그대로 보여 준다.

```
줄 43118  Couldn't find end of Start Tag TH
줄 43120  mismatch: TR line 43109 and TH
줄 43137  mismatch: THEAD line 43093 and TR
줄 43138  mismatch: TABLE line 43079 and THEAD
줄 43648  mismatch: TABLE-GROUP line 41880 and TABLE
줄 44255  mismatch: SECTION-2 line 8605 and TABLE
줄 45563  mismatch: LIBRARY line 4248 and TABLE-GROUP
줄 53522  mismatch: SECTION-1 line 3671 and SECTION-2
줄 82054  mismatch: BODY line 17 and TABLE-GROUP
줄 83399  mismatch: DOCUMENT line 4 and SECTION-2
```

밀림이 `DOCUMENT` 까지 올라갔다. 문서의 최상위 요소다. 여기까지 밀리면
그 뒤 내용이 갈 곳이 없어 버려진다.

실측한 손실이다.

```
CJ제일제당      20250515    원문 263,172자  →  파싱  84,502자    67.9%
HD현대일렉트릭   20250317    원문 272,406자  →  파싱 120,396자   55.8%
KB금융          20250814    원문 798,170자  →  파싱 372,000자   53.4%
NAVER          20250318    원문 478,756자  →  파싱 327,820자   31.5%
```

#### 이것이 후처리로 안 되는 이유

`section.py` 에 `_broken()` 을 넣어 "표 안에 목차가 있으면 깨진 표" 로 보고
건너뛰는 방식을 먼저 시도했다. 그것은 파싱된 결과를 보고 판단한다.

그런데 원인 2 는 파싱 단계에서 태그가 사라진 것이다. 파싱 결과에 그 내용이
아예 없다. 없는 것을 후처리로 되살릴 방법이 없다.

증상을 덮는 것과 원인을 없애는 것의 차이가 여기 있다.

### 원인 3 — 여러 파일을 문자열로 이어붙였다

```
규모   사업보고서 210건 (전체 290건 중) · 기업 70개 전부
```

`corpus.read_raw()` 가 문서 폴더의 XML 을 전부 이어붙인다. 사업보고서는
파일이 셋이다.

```
20240319000861.xml           본문
20240319000861_00760.xml     감사보고서          208건
20240319000861_00761.xml     연결감사보고서       207건
```

이어붙이면 `<?xml ?>` 선언이 문서 중간에 오고 루트가 세 개가 된다. XML 은
루트가 하나여야 하므로 파서는 첫 루트만 읽고 나머지를 버린다.

반기·분기 보고서는 첨부가 없다. 연간 재무제표만 감사를 받고 반기·분기는
검토이기 때문이다. 그래서 이 문제는 사업보고서에만 걸린다.

```
보고서 종류   파일 1개   파일 2개   파일 3개
annual          80         5        205
half           234         -          -
quarter        527         -          -
```

## 해결 — sanitize

파싱 전에 원문의 이스케이프 누락을 바로잡는다. `src/sanitize.py` 다.

```
1  XML 밖 엔티티를 문자로 되돌린다        &reg; → ®
2  나머지 & 를 &amp; 로                  XML 은 엔티티 다섯만 안다
3  표준 태그가 아닌 <...> 를 이스케이프    <배틀그라운드> → &lt;배틀그라운드&gt;
4  표준 태그의 속성 값 따옴표를 &quot; 로
5  남은 < 를 전부 &lt; 로
```

### 표준 태그 33종을 어떻게 확정했나

전수 집계로 나온 1,056종에서 골랐다. 판별 기준은 두 가지다.

```
기준 1   문서 1,051건 전부에 나오는가
           구조 태그라면 어느 문서에나 있어야 한다
           31종이 걸렸다

기준 2   여는 것과 닫는 것의 개수가 맞는가
           진짜 태그는 짝이 맞고 텍스트는 여는 것만 있다
           A(8,662/8,662) 와 CORRECTION(160/160) 이 추가로 걸렸다
```

`<배틀그라운드>` 는 42,002개가 열리고 0개가 닫힌다. `A` 는 8,662개가 열리고
8,662개가 닫힌다.

역방향도 확인했다. STD 밖인데 여닫이가 맞는 태그가 있으면 진짜 태그를
텍스트로 만드는 셈인데, 전수에서 0종이었다.

### 속성 따옴표를 어떻게 가리나

닫는 따옴표는 그 뒤에 다른 속성이나 태그 끝이 오는 것이다.

```
ENG=""Other  receivables and others">
     ↑                              ↑
     후보 1                         후보 2
     뒤에 Other 가 온다              뒤에 > 가 온다
     → 아니다                        → 이것이다
```

값 안에 `이름=` 형태가 들어 있으면 이 판정이 어긋날 수 있어 전수로 세었다.
7개였고 전부 `ENG="Others, current="` 형태였다. 값이 등호로 끝나는 정상
속성이고 규칙이 건드리지 않는다.

### 결과

```
                        고치기 전        고친 뒤
파서 오류가 있는 문서       1,008건    →      0건
깨진 표가 있는 문서           468건    →      0건
글자 손실 0.1% 초과            84건    →      0건
```

글자 수만이 아니라 문자열 자체를 대조했다. 원문에서 표준 태그만 정규식으로
걷어낸 텍스트와, sanitize 후 파싱해 얻은 텍스트를 비교했다.

```
표본 16건 (KB금융 · NAVER · 현대자동차 · OCI홀딩스 포함)
   문자열 불일치 0
```

한 글자도 다르지 않다.

### 새 방식으로 잘라 보면

표본 40건을 지금 DB 와 나란히 놓았다.

```                        지금 DB      새 방식
조각                       4,128       4,322
0자 조각                   1,562        544
                          (37.8%)     (12.6%)
한 절이 문서를 독점         최악 99.6%   최고 33.9%
글자                    1,678만      1,951만
```

검토 기준(한 절 50% 초과 또는 0자 30% 초과)에 걸리는 문서가 0건이다.
이전에는 40건 중 16건이었다.

남은 0자 조각 12.6% 는 전부 상위 목차 제목이다. 이번에는 설명으로 덮지 않고
전부 열어 확인했다.

```
I. 회사의 개요           아래 1. 회사의 개요 · 2. 회사의 연혁 에 내용이 있다
7. 증권의 발행을 …       아래 7-1 · 7-2 에 내용이 있다
【 전문가의 확인 】       아래 1. 전문가의 확인 · 2. 이해관계 에 내용이 있다
목 차                    원문에도 텍스트가 없다. 링크 목록이다
```

### 대가

```
표본 16건 · 원문 90.6M자
   sanitize   52.8초
   파싱        8.2초

전수 1,051건 환산   sanitize 약 58분 추가
```

파싱보다 6배 무겁다. 정규식으로 300만 개 태그를 전부 훑기 때문이다.

가벼운 방식을 시도했다가 되돌렸다. 자리표시자를 쓰지 않고 정규식만으로

담는 과정은 우리가 통제한다. 만드는 과정은 원문에 달려 있다. 후자가 훨씬
자주 틀리는데 전자만 검사했다.

값 계층(W5)     파서를 고치고 다시 돌리면 된다. 몇 분
본문 계층(W6)   임베딩을 다시 해야 한다. 2시간 · 42,474원

W5 에서는 열두 번 다시 해도 몇 분씩이었다. W6 은 한 번이 2시간이다.
같은 규율로 다룰 수 없다.

그래서 단계 사이마다 관문을 둔다.

```

```

하나라도 실패하면 다음으로 가지 않는다. 스크립트는 `scripts/verify_*.py` 다.

### 벡터 단독으로 재고 판정하려다 두 번 헤맸다

임베딩이 끝난 뒤 실제 검색이 되는지 재봤다. 조각에서 질의를 만들고 그
조각이 돌아오는지 보는 방식이다.

```

```

자기 텍스트로 자기를 못 찾는 셈이라 임베딩을 의심했다. 파고드니 아니었다.

#### 첫 번째 착각 — 질의 생성 방식을 의심했다

질의를 뜨는 위치를 바꿔 가며 쟀다.

```
조각 종류   질의 방식      1위    10위내
표         전체           97%   100%
표         앞160          17%    60%
표         가운데160        3%    33%
문장       전체           97%   100%
문장       앞160          27%    53%
```

조각 전체를 질의로 쓰면 97%가 1위다. 자기 유사도가 0.9997 이므로 저장된
벡터가 그 조각의 것이 맞다. 임베딩은 정상이었다.

#### 두 번째 착각 — 조각 단위로 판정했다

같은 절의 조각들이 서로 0.86~0.97 로 매우 비슷했다.

```
현대자동차 · (금융업)영업설비        조각 13개  서로 평균 0.9685
삼성생명 · 보험계약자산 및 부채      조각 13개  서로 평균 0.8964
```

한 표가 여러 조각으로 나뉘면 머리글이 같고 항목 구조가 같다. 다른 것은
숫자뿐이다.

그런데 chunk 는 찾기 위한 단위이고 답을 주는 단위는 section 이다. 같은 절의
다른 조각이 1위면 그 절을 찾은 것이므로 성공이다. 절 단위로 다시 재니
58% → 68% 로 올랐다.

앞서 검증 3의 어휘 검사에서 같은 착각을 했다. 수단을 목적으로 재고 있었다.

#### 진짜 원인 — 부품 하나만 떼어 재고 있었다

```
정답 : KB금융 · 2-1. 연결 재무상태표 · 제 19 기 1분기말 2026.03.31
1위  : KB금융 · 2-1. 연결 재무상태표 · 제 17 기 반기말 2024.06.30
```

같은 절이 문서마다 반복된다. KB금융은 문서가 24건이고 각각에 연결
재무상태표가 있다. 벡터로는 시점을 구별할 수 없다.

실제 파이프라인은 벡터 단독이 아니다. 부품을 하나씩 더해 가며 다시 쟀다.

```
방식                     후보    절 1위   절 10위
1 기업만 + 벡터          3,375    18%     48%
2 기업+연도+종류 + 벡터    416    28%     80%
3 같은 필터 + BM25         416    54%    100%
4 같은 필터 + RRF          416    44%     96%
```

필터를 걸면 48% → 80%, BM25 를 쓰면 100% 다. 임베딩 문제가 아니라 조립
문제였다.

### 가중치 — BM25 쪽에 더 준다

`rrf()` 에 가중치 인자를 넣었다. 기본은 1대1 이다.

set 1 기업으로 만든 질의 30개로 재니 이렇게 갈렸다.

```
조합          1위 적중   10위 적중
벡터만          20%      43%
BM25만         33%      60%
RRF 1:1        30%      63%
RRF 1:2        30%      67%   ← 가장 높다
RRF 1:3        27%      67%
RRF 2:1        30%      43%
```

BM25 에 무게를 더 주는 쪽이 낫고 벡터에 더 주면 크게 나빠진다.

다만 값을 코드에 박지 않았다. 이 측정은 조각의 낱말을 그대로 쓴 질의로 한
것이라 BM25 에 유리한 조건이다. 원문 낱말을 안 쓰는 질의로 따로 재보니
둘 다 크게 떨어졌다.

```
                 벡터    BM25   1:1   1:2
원문 낱말 질의     80%   100%   96%    —
바꿔 쓴 질의       15%    28%   13%   18%
```

최종 가중치는 사용자가 준비한 평가 질의로 정한다.

### 못 찾은 것의 유형

set 1 질의 30개 중 10건을 놓쳤고 두 유형에 몰려 있었다.

```
1. 사업의 개요             8건 중 5건 실패
IV. 이사의 경영진단 및 분석의견   3건 전부 실패
```

`"어떤 사업을 하는 회사인지 사업보고서 기준으로 알려줘"` 라는 질의에
`1. 예측정보에 대한 주의사항` 이 걸렸다. 질의의 `사업보고서` 라는 낱말이
거의 모든 절에 나오기 때문이다.

질의 해석(층 1)과 경로 필터(층 2)가 없어서 생긴 일이다. 둘 다 W7 에서
만든다. 임베딩을 다시 할 사유가 아니다.

### 검증기를 또 고쳤다 — 왕복 검사 기준

set 2 검증에서 왕복 검사 1건이 걸렸다. 유사도 0.9977 이었다.

파고드니 검증 기준이 틀린 것이었다.

```
같은 입력을 세 번 불러도 서로는 완전히 같았다   1.000000
저장된 것과만 0.9977
```

API 는 배정밀도로 주는데 우리는 단정밀도로 저장한다. 3,072개 숫자를 각각
반올림하므로 오차가 쌓인다. 표본 40건을 재니 절반 가까이가 1.0 미만이었고
최소가 0.9971 이었다.

```
표본 40건   최소 0.9971 · 중앙 0.99995 · 최대 1.0
            1.0 미만 18건 · 0.999 미만 5건
```

`0.999` 를 기준으로 두면 정상인 조각을 12.5% 실패로 잡는다. `0.99` 로
낮췄다. 벡터가 실제로 뒤바뀌면 0.5 아래로 떨어지므로 충분히 잡힌다.

float32 저장은 의도한 것이다. float64 면 171,564조각에 4GB 가 든다.

set 1 에서 0건이 나온 것은 표본 30개에 우연히 안 걸렸을 뿐이었다.
