## 1. 이전 세션의 분류를 확정값으로 다뤘다

무엇을 했나
자기주식처분 157건의 갈래를 148/5/2/2로 보고 그 위에서 D1 논의를 시작했다.

무엇이 문제였나
그 숫자는 키워드 분류 결과였고 정정 중복을 세고 있었다. 그리고 나는 그것을 "사용자가 전수를 열어 분류한 결과"라고 적었다. 사용자가 원문으로 전건 확인한 것은 W3의 계약 7건이고, 이 분류는 이전 세션의 Claude가 한 것이다.

어떻게 알았나
사용자 지적. "내가 전수로 열어서 분류한 적 없다"였다.

어떻게 고쳤나
전수를 다시 뽑았다. 사람이 원문으로 확인한 숫자와 키워드로 나눈 숫자는 신뢰도가 다르므로 출처를 섞어 적지 않는다.

```
갈래                공시   사건
보상·상여            145   136
교환사채 대응           5     2
합병·주식교환·단주       5     4
자금 확보              2     2
```

이전 분류와 어긋난 곳이 둘이다. 정정 중복 13건을 세고 있었고, "주식매수청구권 행사로 취득한 자기주식의 기한 내 처분"과 "포괄적 주식교환 과정의 단주 매각"을 보상 갈래로 흘려보냈다.

무엇이 남았나
없다. 다만 출처 표기를 흐리면 검증 강도를 판단할 수 없게 된다.

## 2. 안 읽어본 항목을 쓸모없다고 판정할 뻔했다

무엇을 했나
처분방법을 대조에서 빼려 했다. 근거는 둘이었다. 146건이 전부 "시장을 통한 매도"로 나와 값이 아니라 항목명으로 보인다는 것, 그리고 매도 방식은 대금 귀속을 말해주지 않는다는 것이었다.

무엇이 문제였나
첫째는 파서가 못 읽는다는 말이고 둘째는 서식이 정보를 안 담는다는 말이다. 확인된 것은 첫째뿐인데 둘째를 단정했다.

어떻게 알았나
원문 세 건을 열었다. 서식은 이렇게 생겼다.

```
6. 처분방법
   시장을 통한 매도(주)   -
   시간외대량매매(주)     -
   장외처분(주)          210,743
   기 타(주)             -
```

네 갈래에 주식수를 나눠 적는다. 대금 귀속이 정확히 갈린다. 둘째 근거는 성립하지 않았다.

어떻게 고쳤나
처분방법을 판정의 주 기준으로 삼았다. 목적은 자유서술이고 방법은 숫자다.

무엇이 남았나
없다. `W3.md` 13번과 같은 자리였다. 파싱 실패를 데이터 부재로 읽는 것.

## 3. 항목명 비교에서 한쪽만 공백을 지웠다

무엇을 했나
처분방법 네 갈래를 읽으려고 항목명을 정규화해 비교했다.

무엇이 문제였나
입력에서만 공백을 지우고 비교 대상 키에는 남겼다.

```
"시장을 통한 매도(주)"  →  "시장을통한매도"
키                     →  "시장을 통한 매도"      영영 매칭되지 않는다
```

157건 전부에서 시장 매도 행을 못 읽었다. 다른 세 갈래는 원래 공백이 없거나("시간외대량매매", "장외처분") 공백 제거로 맞아떨어져서("기 타" → "기타") 문제가 드러나지 않았다.

그 결과 "시장 매도 2건"이라는 틀린 수를 한 번 보고했다. 실제로는 6건이다.

어떻게 알았나
자체 검증 항목이 잡았다. 처분방법 네 갈래의 합이 처분예정주식과 같은지 대조하도록 넣어뒀고, 어긋난 건이 나와 원문을 열었다. `W3.md`가 W4에 넘긴 "파생 값이 전건에서 나오는가"가 이것이다.

어떻게 고쳤나
키에도 같은 정규화를 적용했다. 판독불가로 밀려나 있던 5건에서 메리츠금융지주 434주, 신한지주 6,353주, 현대오토에버 866주가 시장 매도로 드러났다.

무엇이 남았나
없다. 검증을 먼저 짜두지 않았으면 틀린 수로 D1을 닫았다.

## 4. 현금흐름표를 판정 기준으로 삼으려 했다

무엇을 했나
공신력 있는 기준이 필요하다는 요구에 따라 사업보고서 현금흐름표를 찾았다. 회계기준이 대금을 받은 처분만 재무활동 현금유입에 적고 교부는 "현금유출입이 없는 중요한 거래"로 따로 표시한다.

```
엘에스일렉트릭   공시 635.4억  ↔  현금흐름표 633.9억
한미반도체      공시 279.8억  ↔  현금흐름표 276.4억
```

무엇이 문제였나
개별 처분 건과 대응되지 않는다. 위 두 건이 맞아떨어진 것은 그 해에 처분이 하나뿐이었기 때문이고, 처분이 여러 건인 기업에서는 어느 건의 금액인지 알 수 없다.

어떻게 알았나
역검증에서 나왔다. 교부만 한 기업 23개사의 현금흐름표를 훑어 자기주식 처분 유입이 0인지 확인했더니 3개사에서 값이 나왔다.

셋의 정체가 달랐다.

```
LIG디펜스    영업활동 조정 구간. 이웃이 주식보상비용 조정      현금 유입 아님
에스엠       ACONTEXT 축이 3종. 자본변동표                현금흐름표가 아님
SK하이닉스   재무활동 구간 확정. 2025년 650억·2024년 938억   설명되지 않음
```

앞의 둘은 `DECISIONS.md` 2026-08-13이 다룬 문제 그대로다. 같은 태그가 다른 표에 붙고 ACONTEXT 축으로 갈린다.

어떻게 고쳤나
판정 기준을 처분방법으로 되돌리고 현금흐름표는 보조 근거로 내렸다.

무엇이 남았나
SK하이닉스 한 건. 그 회사의 자기주식처분 공시 15건은 전부 교부인데 현금흐름표에는 매년 수백억이 재무활동 유입으로 잡혀 있다. 주요사항보고서는 이사회 결의를 요하는 건만 나오고 현금흐름표는 전체 흐름이라 범위가 다른 것으로 보이나 확인하지 못했다.

무엇을 했나
현금 유입 건을 세어 5건이라고 보고했다.

무엇이 문제였나

## 6. 하이픈 하나에 1,083건이 걸렸다

무엇을 했나
계약 공시 1,169건이 어느 서식인지 가려내는 판별기를 만들었다. 항목 이름의 존재로 판별하기로 하고 `\n\s*체결계약명\s*\n` 같은 패턴을 썼다.

무엇이 문제였나
1,083건이 미분류로 나왔다. 원문의 항목 이름 앞에 하이픈이 붙어 있다.

```
1. 판매ㆍ공급계약 구분
- 체결계약명           ← 하위 항목이라는 표시
내 패턴 \n\s*체결계약명   ← \s 는 공백·개행이지 하이픈이 아니다
```

세부내용에는 `-?`를 넣어뒀는데 나머지 여덟 개에는 빠뜨렸다. 시설투자와 해지는 지표 자체를 잘못 골랐다. `투자목적`이 아니라 `- 투자대상`이고 `해지사유`가 아니라 `- 해지계약명`이다.

어떻게 알았나
판별 결과를 전수로 세는 것이 1번 걸음의 목적이었다. 값을 뽑기 전에 판별기부터 검증하도록 순서를 짜둔 덕에 바로 드러났다.

어떻게 고쳤나
항목 이름 앞에 올 수 있는 것을 셋으로 정리했다. 번호, 하이픈, 없음이다. 고친 뒤 미분류 0건이 됐고 유형과 서식이 정확히 대응했다.

```
1,022  단일판매공급계약체결  → 유가증권 의무
   58  단일판매공급계약체결  → 유가증권 자율
   26  단일판매공급계약체결  → 코스닥
   43  신규시설투자등        → 시설투자
   20  단일판매공급계약해지  → 해지
```

무엇이 남았나
없다. 다만 서식이 셋인 줄 알았는데 다섯이었다. 해지와 시설투자를 따로 세지 않은 채 "셋"이라고 보고했다.

## 7. 정규식이 개행을 먹어 한 줄 걸러 하나씩 세었다

무엇을 했나
서식별 항목 이름을 전수 집계하려고 `\n항목\n` 패턴으로 훑었다.

무엇이 문제였나
개행을 소비해서 다음 줄이 안 잡힌다. 항목과 값이 번갈아 나오는 구조라 항목의 절반만 세어졌다.

```
계약금액(원)      730건 (71.4%)     실제로는 1,022건 전건에 있다
- 체결계약명      아예 목록에 없음
유 · 무 · 공사수주  항목처럼 잡힘      값 줄이 항목 자리에 걸린 것
```

어떻게 알았나
전건에 있어야 할 항목이 71.4%로 나오는 것이 이상해서 다시 읽었다.

어떻게 고쳤나
줄로 쪼개서 셌다. 문서당 한 번만 세도록 집합으로 묶었다. 고친 뒤 항목이 전부 100%로 나왔다.

무엇이 남았나
없다. 정규식으로 연속된 줄을 훑을 때는 겹침을 항상 확인한다.

## 8. 검증 항목의 성격을 잘못 잡았다

무엇을 했나
"파생 값이 전건에서 나오는가"를 검증에 넣었다. `W3.md`가 W4로 넘긴 항목이다.

무엇이 문제였나
네 건이 실패로 떴다. 열어보니 전부 원문에 값이 `-`로 적혀 있었다.

```
의무 signed_at   1,015/1,022    7건은 7. 계약(수주)일자 가 "-"
자율 base_amount    57/58       HD현대일렉트릭 정정본은 본문 전체가 "-"
```

이건 우리가 못 읽은 것이 아니라 회사가 안 쓴 것이다. D7의 `not_disclosed`에 해당한다. 그런데 검증이 이것을 실패로 세면 매번 실패가 뜨고, 그러면 검증 결과를 보지 않게 된다.

어떻게 알았나
실패 건의 원문을 열었다.

어떻게 고쳤나
검증 질문을 바꿨다. "값이 있는가"가 아니라 "원문대로 읽었는가"다.

```
바꾸기 전   e.signed_at IS NOT NULL 인 건이 전건인가
바꾼 후     비어 있는 건의 원문을 열어 그 자리가 "-" 인지 확인한다
             "-" 이면 통과. 값이 있는데 못 읽었으면 실패
```

우리가 검사할 것은 우리 파서이지 원문 품질이 아니다. 원문 품질 문제는 따로 세어 목록으로 출력한다.

같은 이유로 검산 불일치와 날짜 역전도 실패에서 뺐다. 대신 검증 끝에 원문 오류 목록을 찍는다.

```
원문 기재가 어긋난 건 6건 — 값을 고치지 않고 그대로 담았다
```

## 9. 원문 구조를 안 보고 평문으로 읽었다

무엇을 했나
W3부터 원문을 `to_text()`로 평문화한 뒤 "항목명 다음 줄이 값" 규칙으로 읽었다. W4 계약 공시도 같은 방식이었다.

무엇이 문제였나
셋 다 표 구조를 갖고 있었다. 평문으로 만들면 그 구조가 사라진다.

```
주요사항보고서   XML    TABLE / TR / TD
거래소공시       HTML   table / tr / td      확장자는 .xml 인데 내용은 HTML
지분공시         XML    TABLE / TR / TD
```

`PLAN.md`에 "거래소공시는 확장자만 .xml이고 실제로는 HTML"이라고 적어두고 구조를 못 쓴다고 짐작했다. HTML에도 표가 있는데 확인하지 않았다.

평문화가 잃는 것이 셋이다. 본문 문장이 줄바꿈된 조각이 항목으로 잡히고, 세로로 병합된 칸의 항목명이 사라지고, 한 행에 값이 둘 이상일 때 하나를 잃는다.

어떻게 알았나
사용자 지적. "현재 데이터가 저장되어 있는 구조를 고려하여 그에 맞는 구조로 값을 추출하는 방식을 지금까지 고려하지 않았나"였다.

어떻게 고쳤나
`src/docitem.py`를 만들어 표를 그대로 읽는다. 깨진 XML은 lxml 복구 모드로 처리했고 598건 전부 통과했다.

교차검증도 했다. D1 조사에서 평문으로 뽑은 자기주식 처분방법과 표 구조로 뽑은 것이 같은 답을 냈다. 시장매도 6건이 기업·날짜·주식수까지 일치한다.

무엇이 남았나
없다. 다만 이 발견으로 작업 방식에 0번 걸음을 추가했다. `feedback/README.md` 참조.

## 10. 딕셔너리가 중복 항목을 덮어썼다

무엇을 했나
항목-값을 `{항목명: 값}` 딕셔너리에 담아 조회했다.

무엇이 문제였나
같은 항목명이 여러 번 나오면 마지막 것만 남는다. KB금융 건에서 채무상환자금 2,200억이 사라져 용도 합계가 500억으로 나왔고, 검산 불일치로 잡혔다.

그리고 첫 매칭을 값으로 쓰고 있었다. 정정본에는 같은 항목이 정정사항 표와 본문에 두 번 나오고, 신한지주 건은 세 번 나온다.

```
seq  4   2. 사채의 권면총액 > 발행조건 결정에 따른 정정  = 270,000,000,000   정정 전
seq  5   2. 사채의 권면총액 > 270,000,000,000        = 400,000,000,000   정정 후
seq 14   2. 사채의 권면총액                          = 400,000,000,000   본문
```

어떻게 알았나
검산 불일치 4건의 원인을 찾다가. 처음에는 원문 오류를 의심했는데 우리 오류였다.

어떻게 고쳤나
리스트로 담고 마지막 매칭을 쓰도록 바꿨다.

```
첫 매칭 + 딕셔너리   일치 78 · 불일치 4 · 검산 불가 21
마지막 매칭 + 리스트  일치 102 · 불일치 0 · 검산 불가 1
```

무엇이 남았나
없다. 다만 "원문 오류일 수도 있다"고 먼저 말한 것이 성급했다. 확인 전에는 우리 쪽을 먼저 의심하는 편이 맞다.

## 11. 마지막 매칭이 다른 곳에서 역효과를 냈다

무엇을 했나
10번에서 마지막 매칭으로 바꿨다.

무엇이 문제였나
회사합병 서식에는 이사회결의일이 넷이다.

```
14. 이사회결의일(결정일)   2024-04-16   ← 이것이 결정일
합병결정 이사회결의일       2024-04-16
합병승인 이사회결의일       2024-05-28
합병보고 이사회결의일       2024-07-01   ← 마지막 매칭이 이것을 잡았다
```

결의일이 접수일보다 뒤가 되어 7건이 검증에 걸렸다.

어떻게 알았나
검증 항목 "결의일 > 접수일"이 잡았다. 계약 공시에서 만들어 둔 항목을 그대로 가져온 것이다.

어떻게 고쳤나
번호가 붙은 표준 항목 `이사회결의일(결정일)`을 먼저 찾고, 없을 때만 부분 매칭으로 내려간다.

무엇이 남았나
없다. 다만 "마지막 매칭"이 만능이 아니라는 것이 드러났다. 정정사항 표를 피하려는 규칙인데, 본문 안에 같은 이름의 항목이 여럿이면 틀린다.

## 12. 값이 비어 있는 이유가 둘이었다

무엇을 했나
자금조달 용도가 전부 `-`인 건을 `not_disclosed`로 분류하려 했다.

무엇이 문제였나
공시유보와 성격이 다른 것이 섞여 있었다.

```
공시유보     지금은 안 밝히고 유보기한 뒤에 밝힌다      값이 나중에 나온다
철회·취소    그 증자·합병이 없던 일이 됐다             값이 영영 없다
```

"자금조달 목적이 기재되지 않았습니다"로 답하면 틀린다. "이 유상증자는 철회되었습니다"가 맞다.

어떻게 알았나
사용자 질문. "그 회사가 유보일까지 공시를 하지 않는 그러한 이유와 유사한 이유 때문인가"였다. 답하려고 원문을 열었더니 정정사유에 이유가 적혀 있었다.

어떻게 고쳤나
`is_withdrawn`과 `correct_reason` 컬럼을 두고 정정사유에서 판정한다. 12건을 찾았다.

정정사유를 찾는 데 한 번 실패했다. 정정사항 표가 `항목 │ 정정사유 │ 정정 전 │ 정정 후` 네 칸인데, 값 앞 칸을 이름으로 잡는 규칙 때문에 사유가 항목 경로 안으로 들어갔다.

```
name  = "1. 신주의 종류와 수 > 신주 및 전환사채 발행금지가처분 인용 결정에 따른 계약 해제"
value = "1,230,000"
```

같은 사유가 표의 모든 행에 반복되므로 경로 조각 중 가장 자주 나오는 긴 문장을 사유로 본다. 다만 OCI홀딩스 건은 첫 행에만 있어 반복 조건으로 안 걸렸고, 철회를 뜻하는 말이 있으면 한 번만 나와도 채택하도록 넓혔다.

무엇이 남았나
고려아연 20241113·20241114는 값이 전부 `-`인데 철회로 안 잡혔다. 정정사유가 표에 없거나 다른 형태로 적혀 있다.

## 13. 표가 두 종류인 것을 몰랐다

무엇을 했나
9번에서 표 구조로 읽도록 바꾸면서 "첫 칸이 항목, 뒤가 값"이라는 규칙 하나를 썼다.

무엇이 문제였나
표에 두 종류가 있다.

```
종류 1  항목이 왼쪽      계약금액(원) │ 22,764,764,160,000
종류 2  머리글이 위      보고서작성기준일 │ 본인 성명 │ 특별관계자수 │ 주식등의 수(주)
                        직전보고서       │ 미래에셋   │ 1          │ 940,946
```

종류 2에 종류 1의 규칙을 쓰면 값이 한 칸씩 밀린다.

```
1 = 940,946
940,946 = 5.05
5.05 = 18,650,709
```

지분공시의 핵심 표가 대부분 종류 2라서 요약 정보를 하나도 못 읽었다.

어떻게 알았나
지분공시 요약 축을 뽑으려고 값을 출력해 보다가.

주요사항보고서 표 한 건을 열어보고 "항목이 왼쪽에 있다"고 일반화한 것이 원인이다. 0번 걸음을 만든 이유가 표본 하나로 규칙을 만들지 않으려는 것이었는데 같은 일을 했다.

어떻게 고쳤나
머리글 행을 알아보고 열 이름과 칸을 자리로 짝짓도록 했다. 머리글이 두 줄인 표가 있어 연속된 머리글 행을 합치는 처리도 넣었다.

한 번 잘못 갔다. 머리글 해석만 적용했더니 정정사항 표에서 본문 값을 잃어 주요사항 검산이 302건에서 300건으로 줄었다. 두 해석을 합치고 중복만 제거하도록 바꿔 302건으로 복구했다.

`docitem.py` 를 고쳤으므로 계약과 주요사항도 다시 적재했다. `major_item` 이 78,967행에서 83,641행으로 늘었다. 이전에 뭉개져 담기지 못하던 항목들이다.

무엇이 남았나
없다. 다만 0번 걸음 점검 항목을 구체적으로 바꿨다. "어떤 구조를 갖는가"로 물으면 "표가 있다"로 답하고 넘어가게 된다. `feedback/README.md` 참조.

## 14. 검산 분모를 몰랐다

무엇을 했나
지분공시 검산을 `보유주식수 ÷ 발행주식총수 × 100 = 보유비율` 로 시작했다.

무엇이 문제였나
93.5% 만 맞았고 불일치 70건에서 계산이 100% 를 넘었다.

```
한화오션  보유 221,991,779 / 총수 211,729,312 = 104.85%   기재 82.36%
HMM      보유 734,790,156 / 총수 489,039,496 = 150.25%   기재 71.68%
```

보유 수가 발행주식총수보다 크다. 잠재주식 때문이다. 전환사채처럼 아직 주식이 아닌 것을 보유 수에 포함해 세므로 분모에도 더해야 한다.

어떻게 알았나
공시가 산정식을 스스로 적어뒀다.

```
주식등의 보유비율 [ A + H / I + H − (E+F+G) ] × 100
   A 주권 · H 보유잠재주식 · I 의결권 있는 발행주식총수
   E·F·G 교환사채권 · 증권예탁증권 · 기타
```

어떻게 고쳤나
분모에 잠재주식을 더해 98.1% 가 됐고, 남은 20건은 대부분 케이티였다. 케이티는 잠재주식을 분모에 안 더한다. 회사마다 계산 방식이 다르다. 두 방식 중 하나가 맞으면 통과로 바꿔 99.3% 가 됐고, 반올림 오차를 0.05%p 로 두어 최종 불일치 0이 됐다.

무엇이 남았나
`E+F+G` 를 뽑지 않았다. 정확한 공식을 구현하려면 잠재주식 종류별 수치가 필요한데, 표가 문서마다 여러 개라 합계 행을 가리는 규칙이 따로 있어야 한다. 근사식과 허용 오차로 대신했다.

이 값을 뽑으면 "전환사채로 가진 지분이 얼마인가" 같은 질의에도 답할 수 있게 되므로, 필요해지면 그때 판다.
