# 작업 피드백 기록

작업 단계별로 무엇을 시도했고, 무엇이 틀렸고, 어떻게 알았고, 어떻게 고쳤는지 남긴다.

다른 문서와의 역할 구분이다.

| 문서 | 담는 것 |
|---|---|
| `SCHEMA.md` | 지금 구조가 이런 이유 — 최종 상태 |
| `feedback/W*.md` | 어떻게 여기 도달했나 — 과정 |
| `DECISIONS.md` | 되돌리기 어려운 선택과 근거 — 분기점 |

결과만 남기면 같은 실수를 반복한다. 그리고 세션이 바뀌면 과정이 통째로 사라진다.

---

## 형식

각 항목을 다섯 칸으로 쓴다.

```
무엇을 했나        1차 구현이 무엇이었나
무엇이 문제였나     구체적 건수와 함께
어떻게 알았나       검증 / 사용자 지적 / 표본 확인 / 진단 스크립트
어떻게 고쳤나       무엇을 바꿨고 건수가 어떻게 변했나
무엇이 남았나       해결 못 한 것과 그 이유
```

세 번째 칸이 핵심이다. 검증이 잡은 것과 사람이 잡은 것을 구분해야 검증 설계의 구멍이 보인다.

사용자 지적으로만 잡힌 항목이 쌓이면, 그 유형을 다음 작업의 검증 항목에 넣는다.

---

## 작성 시점

각 W 작업이 끝날 때 쓴다. 작업 중에 쌓아두었다가 마무리에 정리한다.

아직 끝나지 않은 작업은 진행 중으로 표시하고 나중에 덧붙인다.

## 작업을 걸음으로 나눈다 — W4에서 효과를 본 방식

W3에서 적재를 열두 번 다시 했다. 값을 뽑는 일과 데이터베이스에 넣는 일을 붙여놓아서, 틀린 값이 들어간 뒤에야 틀렸다는 것을 알았기 때문이다.

W4부터는 일곱 걸음으로 나눈다. 각 걸음이 끝날 때 결과를 보고하고 다음으로 간다.

```
0  원문의 저장 구조를 확인한다   무엇으로 저장돼 있고 어떤 구조를 갖는가
1  서식 판별기를 만든다        분류 안 되는 건이 0인지 전수로 센다
2  항목 이름 사전을 만든다      전수 집계로 표기 변형을 찾는다
3  값을 뽑아 파일로 저장한다     아직 DB 에 넣지 않는다
4  검산한다                  안 맞는 건을 전부 열어 원인을 밝힌다
5  테이블을 만들고 넣는다       검산을 통과한 뒤에 넣는다
6  검증 스크립트를 돌린다
```

### 0번 걸음 — 구조를 먼저 보고 스키마를 그다음에 정한다

W4 중반에 추가한 걸음이다. 그전까지 원문을 평문으로 만들어 "항목명 다음 줄이 값" 규칙으로 읽었는데, 실제로는 셋 다 표 구조를 갖고 있었다.

```
주요사항보고서   XML     TABLE / TR / TD · TE
거래소공시       HTML    table / tr / td       확장자는 .xml 이지만 내용은 HTML
지분공시         XML     TABLE / TR / TD · TE
```

평문으로 만들면 이 구조가 사라진다. 그래서 본문 문장이 줄바꿈된 조각까지 항목으로 잡히고, 세로로 병합된 칸의 항목명이 없어지고, 한 행에 값이 둘 이상일 때 하나를 잃는다.

구조를 그대로 읽으면 첫 칸이 항목이고 뒤가 값이라는 것이 문서 형식으로 보장된다. 우리가 규칙을 만들어 추측할 필요가 없다.

그래서 0번 걸음에서 이것들을 먼저 본다.

```
저장 형식이 무엇인가            XML · HTML · PDF · 텍스트
파싱이 되는가                  깨진 문서가 몇 건이고 복구되는가
그 구조가 담고 있는 정보는       XBRL 태그 · 병합 정보 · 계층

표가 몇 종류인가               항목이 왼쪽인가 · 머리글이 위인가
병합된 칸이 있는가              세로 병합 · 가로 병합
한 행에 값이 몇 개인가           하나인가 여럿인가
같은 항목이 반복되는가           반복되면 순번이 필요하다
```

아래 넷을 따로 적은 이유가 있다. "어떤 구조를 갖는가"로만 물으면 "표가 있다"로
답하고 넘어가게 된다. 답이 되지만 아무것도 확인하지 않은 답이다.

W4 에서 실제로 그렇게 넘어갔다. 주요사항보고서 표 한 건을 열어보고 "항목이
왼쪽에 있다"고 일반화했는데, 지분공시에 가서야 머리글이 위에 있는 표가
따로 있다는 것을 알았다. 그 규칙으로 읽으면 값이 옆으로 밀려 통째로 뭉개진다.

표본 하나로 규칙을 만들지 않는다. 0번 걸음을 둔 이유가 그것이다.

### 규칙을 확정하기 전에 그 규칙이 기대는 값의 분포를 센다

W5 에서 같은 실수를 세 번 반복하고 추가한 항목이다.

```
지금까지   원문 1건 관찰 → 규칙 확정 → 전수 적용 → 실패 → 수정
바꾼 것    원문 1건 관찰 → 가설 → 전수로 분포 확인 → 규칙 확정 → 전수 적용
```

세 번째가 빠져 있었다. "제목 표는 칸이 하나" 라는 가설을 세웠을 때 구간 안
표의 칸 수 분포를 세었으면, 칸 1개와 4개가 둘 다 있다는 것이 즉시 보였다.
1분이면 됐을 집계를 건너뛰어 세 번 고쳤다.

비용이 문제가 아니다. 정규식 단순 집계가 1,054건에 37~54초고, 파싱까지
해도 3~7분이다. 규칙 하나를 정하기 전에 매번 돌려도 부담이 없다.

세어야 할 것은 규칙이 기대는 성질이다. 칸 수 · 행 수 · 표기 종류 · 등장
위치처럼, "이럴 것이다" 라고 가정한 바로 그 값의 분포다.

### 앞 작업의 스키마를 그대로 쓰지 않는다

같은 W4 안에서도 계약 공시와 주요사항보고서는 구조가 달랐다. 계약은 유형 3개에 서식 5개라 컬럼 27개로 담겼지만, 주요사항은 유형 28개에 고유 항목 678개이고 한 문서 안에 같은 항목이 39번까지 반복된다. 계약의 스키마를 그대로 가져갔으면 대부분을 버렸을 것이다.

구조를 먼저 보고 그 구조를 살리는 스키마를 정한다. 컬럼으로 담기 어려운 것은 key-value 로 담고, 반복되는 것은 순번을 붙여 담는다. 원문에 있는 것을 잃지 않는 것이 먼저이고 조회 편의는 그다음이다.

### 탐색과 구현을 나눈다

W5 중반에 추가한 규율이다. 그전까지 구현 중에 탐색을 계속했고, 발견할 때마다
그 자리에서 코드를 고쳤다. `fsdoc.py` 를 다섯 번 고친 것이 그래서다.

```
탐색 국면    코드를 버릴 셈으로 짠다. 목적은 구조를 아는 것
             결과물은 "무엇이 몇 가지이고 어떤 분포인가" 라는 사실

구현 국면    탐색이 끝난 뒤 시작한다. 그때는 이미 무엇을 만들지 안다
             의사결정과 돌발 대응이 없어야 한다
```

탐색에서 전부 알아내는 것은 불가능하다. 문서를 만든 쪽이 우리 예상과 무관하게
만들었기 때문이다. 그래서 목표는 "돌발이 0" 이 아니라 다음이다.

```
구현 중 발견하면 그 자리에서 고치지 않는다
멈추고 탐색 국면으로 되돌아가 그 유형의 분포를 전수로 센다
규칙을 다시 정하고 구현을 다시 짠다
```

고치면 그 사례만 막히고 같은 유형이 또 나온다. 되돌아가면 유형 전체가 정리된다.

### 왜 이 순서인가

각 걸음에 그 걸음에서만 잡히는 오류가 있다. 뒤로 미루면 앞의 오류가 뒤의 결과에 섞여 원인을 못 찾는다.

W4에서 실제로 이렇게 잡혔다.

```
1번에서   항목 이름 앞 하이픈을 빠뜨려 1,083건 미분류
            곧바로 값을 뽑았다면 빈 행 1,022개가 들어간 뒤 알았을 것이다
2번에서   정규식이 개행을 먹어 항목의 절반만 세어짐
            전건에 있어야 할 항목이 71%로 나와 드러났다
4번에서   검산 불일치 4건. 전부 원문 기재 오류로 확인
6번에서   검증 항목의 성격 자체가 틀렸음을 발견
```

### 이상 신호를 설명으로 덮지 않는다

W6 에서 크게 데었다. section 적재 후 검증에서 0자 조각이 39,677개 나왔다.
그때 이렇게 설명하고 넘어갔다.

```
"대분류 제목이 그렇다. III. 재무에 관한 사항 같은 제목은
 그 자체로는 내용이 없고 하위 조각에 내용이 들어간다"
```

설명은 그럴듯했고 실제로 일부는 그랬다. 그러나 하나도 열어보지 않았다.

나중에 보니 문서 468건(44.5%)에서 표 하나가 문서 나머지를 통째로 삼켰고
TITLE 30,426개가 제 자리를 잃은 상태였다. 그 문서들의 절이 0자였던 것이다.
그 시점에 CJ제일제당 문서 하나만 열어봤으면 즉시 드러났다.

```
규율   이상해 보이는 수치가 나오면 반드시 표본을 열어 확인한다
       설명이 떠올라도 확인 전에는 결론으로 삼지 않는다
       "정상일 것이다" 는 가설이지 관측이 아니다
```

특히 분포가 한쪽으로 쏠릴 때가 위험하다. 한 절이 문서 글자의 절반을 넘게
차지하면 그 문서를 열어본다. 원래 긴 절일 수도 있고 구조가 무너진 것일 수도
있는데, 둘은 열어보기 전에 구분되지 않는다.

### 문제를 발견하면 멈춘다

발견한 채로 끝까지 가지 않는다.

```
잘못된 순서   문제 발견 → 일단 진행 → 나중에 한꺼번에 고침
              그 사이 만든 것이 전부 잘못된 전제 위에 쌓인다
              W6 에서 임베딩 141,524건을 다시 해야 하게 됐다

맞는 순서     문제 발견 → 멈춤 → 규모 실측 → 함께 논의 → 결정 → 재개
```

멈추는 비용은 그 자리에서 몇 시간이고, 안 멈추는 비용은 그 위에 쌓은 것
전부다. W6 에서 임베딩 2시간과 42,474원을 다시 쓰게 된 것이 그 대가다.

되돌리기 비용이 큰 작업일수록 앞 단계 검증을 엄격히 한다.

```
값 계층(W5)     파서를 고치고 다시 돌리면 된다. 몇 분
본문 계층(W6)   임베딩을 다시 해야 한다. 시간과 비용
```

### 단계 사이마다 관문을 둔다

W6 에서 추가한 규율이다. 걸음을 나누는 것만으로는 부족하다는 것을 알았다.

W4 에서 일곱 걸음으로 나눴고 W6 에서도 그렇게 했다. 그런데 걸음이 끝날 때
"결과를 보고하고 다음으로 간다" 였지, "통과하지 못하면 다음으로 안 간다" 가
아니었다. 그래서 0자 조각 39,677개를 보고하고도 다음 걸음으로 갔다.

```
걸음을 나눈다      각 걸음이 끝나면 결과를 본다
관문을 둔다        통과하지 못하면 다음 걸음으로 가지 않는다
```

관문에는 세 종류의 결과가 있다. 섞으면 안 된다.

```
실패        구조상 반드시 0 이어야 하는데 0 이 아니다
            → 멈춘다. 다음 단계로 안 간다

검토 목록    이상해 보이지만 정상일 수도 있다
            → 반드시 표본을 열어 확인한다. 설명으로 덮지 않는다
            → 확인이 끝나야 통과다. 목록이 비어 있지 않은 채로 넘어가지 않는다

참고        원문 자체가 어긋난 것
            → 실패로 세지 않는다. 답변에서 밝혀야 하므로 목록으로 남긴다
```

세 번째를 실패로 세면 매번 실패가 떠서 검증 결과를 안 보게 된다.
`verify_fact_fs.py` 에서 이미 겪었다.

### 관문 자체도 검증되지 않은 것이다

W6 에서 만든 `verify_chunk.py` · `verify_tokens.py` · `verify_embedding.py` 는
작성 시점에 실제 데이터로 돌려본 적이 없었다. 검증되지 않은 검증기를 믿는 것이
같은 실패의 축소판이 된다.

그래서 각 스크립트 머리에 그 사실을 적어 두고, 처음 돌릴 때 이렇게 본다.

```
통과가 나왔다면    그 항목이 정말 잡을 수 있는 것인지 의심한다
                   일부러 틀린 데이터를 넣어 걸리는지 본다

실패가 나왔다면    실패가 맞는지 원문으로 확인한다
                   검증기가 틀렸을 수도 있다
```

실제로 `verify_chunk.py` 를 처음 돌렸을 때 "표 조각 0개" 가 나왔다. 검증기가
고장난 줄 알았는데, section 을 만든 코드가 셀 구분자를 안 넣은 상태였다는
것이 확인됐다. 통과로 보이는 0 이 사실은 데이터가 없다는 뜻이었다.

같은 실행에서 `section.char_len` 과 본문 길이가 67,300건 어긋난 것도 잡혔다.
`char_len = text_len + table_len` 이라 조각을 잇는 줄바꿈이 빠진 것이다.

### 두 종류의 조건을 구분한다

미리 정할 수 있는 것과 데이터를 봐야 아는 것이 섞여 있으면, 정할 수 없는 것을
억지로 정하게 되고 그 숫자가 방향을 왜곡한다.

#### 구조 조건 — 결과와 무관하게 반드시 성립해야 한다

데이터가 어떻게 생겼든 0이어야 하는 것들이다. 미리 정하고 어기면 멈춘다.

| 걸음 | 구조 조건 |
|---|---|
| 1 서식 판별 | 유형과 서식의 대응이 어긋나는 건 0 |
| 2 항목 사전 | 한 이름이 두 뜻으로 쓰이는 경우 0 |
| 3 값 추출 | 빠진 건은 원문에도 없음이 확인됨 |
| 4 검산 | 불일치 건 전건 원인 규명 |
| 5 적재 | 대상 전건에 행 존재 · 문서당 한 행 · 중복 0 |
| 6 검증 | 참조 무결성 0 · 파싱 실패 0 · 원문 오류는 목록으로 출력 |

#### 정지 조건 — 데이터를 보고 판정한다

커버리지를 미리 몇 %로 정하지 않는다. 실제 분포를 보기 전에는 그 숫자가
근거 없는 목표일 뿐이고, 결과가 다르게 나오면 방향을 왜곡한다.

대신 남은 건을 어떻게 처리할지를 조건으로 정한다.

```
멈춘다        원인이 원문 특성으로 확인됐을 때
              회사가 그 항목을 안 적었다 · 서식에 그 칸이 없다
              → not_disclosed 로 표시하고 넘어간다

계속한다      원인이 우리 파서로 확인됐을 때
              같은 유형이 다른 문서에도 있으므로 고친다

판단을 올린다  원인은 밝혀졌는데 고치는 비용이 클 때
              사용자에게 선택지와 판단 가이드를 제시한다
```

#### 품질 하한선 — 미달하면 다음으로 안 간다

커버리지와 다르다. "얼마나 많이 뽑았나"가 아니라 "뽑은 값이 맞나"다.
낮으면 파서가 틀린 것이므로 목표가 아니라 경보선이다.

```
자기 검산 일치율      미달하면 원인을 밝히고 파서를 고친 뒤 다시 측정한다
회계 항등식          재무 데이터에서는 정의상 성립해야 한다
정답지 대조          골든 데이터셋과 어긋나면 그 자리에서 멈춘다
```

### 골든 데이터셋 — 사람이 만든 정답지

전수 통계만으로는 파서가 맞는지 알 수 없다. 우리가 만든 규칙으로 뽑은 값을
우리가 만든 규칙으로 세는 것이라 자기 참조이기 때문이다.

W5 에서 `fsdoc.py` 를 다섯 번 고치면서 매번 "맞아 보인다"로 넘어갔다.
정답지가 있었으면 즉시 판정됐을 일이다.

```
만드는 법     AI 가 표본을 고르고 원문 위치를 안내한다
              사람이 그 위치를 열어 값을 눈으로 읽고 적는다

               AI 가 값까지 뽑아 사람이 확인하는 방식은 쓰지 않는다.
               화면에 숫자가 적혀 있으면 사람은 맞나 보다 하고 넘어간다.
               틀린 값이 정답으로 굳으면 정답지가 해가 된다

쓰는 법       파서를 고칠 때마다 대조한다. 회귀가 잡힌다
              A 가 나아지고 B 가 깨지는 일을 통계로는 못 본다
```

### 각 걸음이 끝날 때

### 검증은 우리 파서를 검사하는 것이다

W4에서 검증 항목을 한 번 고쳤다. "값이 있는가"를 물었더니 회사가 안 쓴 칸까지 실패로 잡혔다.

```
바꾸기 전   값이 채워졌는가            원문 품질을 검사하게 된다
바꾼 후     원문대로 읽었는가          비어 있으면 원문도 비었는지 확인한다
```

원문 자체가 어긋난 건은 실패로 세지 않고 따로 모아 출력한다. 매번 실패가 뜨면 검증 결과를 안 보게 되기 때문이다. 대신 그 목록은 답변에서 밝혀야 할 사실이므로 지우지 않는다.
