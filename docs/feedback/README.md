# 작업 피드백 기록

작업 단계별로 무엇을 시도했고, 무엇이 틀렸고, 어떻게 알았고, 어떻게 고쳤는지 남긴다.

다른 문서와의 역할 구분이다.

| 문서 | 담는 것 |
|---|---|
| `SCHEMA.md` | 지금 구조가 이런 이유 — 최종 상태 |
| `feedback/W*.md` | 어떻게 여기 도달했나 — 과정 |
| `DECISIONS.md` | 되돌리기 어려운 선택과 근거 — 분기점 |

결과만 남기면 같은 실수를 반복한다. 그리고 세션이 바뀌면 과정이 통째로 사라진다.

---

## 형식

각 항목을 다섯 칸으로 쓴다.

```
무엇을 했나        1차 구현이 무엇이었나
무엇이 문제였나     구체적 건수와 함께
어떻게 알았나       검증 / 사용자 지적 / 표본 확인 / 진단 스크립트
어떻게 고쳤나       무엇을 바꿨고 건수가 어떻게 변했나
무엇이 남았나       해결 못 한 것과 그 이유
```

세 번째 칸이 핵심이다. 검증이 잡은 것과 사람이 잡은 것을 구분해야 검증 설계의 구멍이 보인다.

사용자 지적으로만 잡힌 항목이 쌓이면, 그 유형을 다음 작업의 검증 항목에 넣는다.

---

## 작성 시점

각 W 작업이 끝날 때 쓴다. 작업 중에 쌓아두었다가 마무리에 정리한다.

아직 끝나지 않은 작업은 진행 중으로 표시하고 나중에 덧붙인다.

---

## 작업을 걸음으로 나눈다 — W4에서 효과를 본 방식

W3에서 적재를 열두 번 다시 했다. 값을 뽑는 일과 데이터베이스에 넣는 일을 붙여놓아서, 틀린 값이 들어간 뒤에야 틀렸다는 것을 알았기 때문이다.

W4부터는 일곱 걸음으로 나눈다. 각 걸음이 끝날 때 결과를 보고하고 다음으로 간다.

```
0  원문의 저장 구조를 확인한다   무엇으로 저장돼 있고 어떤 구조를 갖는가
1  서식 판별기를 만든다        분류 안 되는 건이 0인지 전수로 센다
2  항목 이름 사전을 만든다      전수 집계로 표기 변형을 찾는다
3  값을 뽑아 파일로 저장한다     아직 DB 에 넣지 않는다
4  검산한다                  안 맞는 건을 전부 열어 원인을 밝힌다
5  테이블을 만들고 넣는다       검산을 통과한 뒤에 넣는다
6  검증 스크립트를 돌린다
```

### 0번 걸음 — 구조를 먼저 보고 스키마를 그다음에 정한다

W4 중반에 추가한 걸음이다. 그전까지 원문을 평문으로 만들어 "항목명 다음 줄이 값" 규칙으로 읽었는데, 실제로는 셋 다 표 구조를 갖고 있었다.

```
주요사항보고서   XML     TABLE / TR / TD · TE
거래소공시       HTML    table / tr / td       확장자는 .xml 이지만 내용은 HTML
지분공시         XML     TABLE / TR / TD · TE
```

평문으로 만들면 이 구조가 사라진다. 그래서 본문 문장이 줄바꿈된 조각까지 항목으로 잡히고, 세로로 병합된 칸의 항목명이 없어지고, 한 행에 값이 둘 이상일 때 하나를 잃는다.

구조를 그대로 읽으면 첫 칸이 항목이고 뒤가 값이라는 것이 문서 형식으로 보장된다. 우리가 규칙을 만들어 추측할 필요가 없다.

그래서 0번 걸음에서 이것들을 먼저 본다.

```
저장 형식이 무엇인가            XML · HTML · PDF · 텍스트
파싱이 되는가                  깨진 문서가 몇 건이고 복구되는가
그 구조가 담고 있는 정보는       XBRL 태그 · 병합 정보 · 계층

표가 몇 종류인가               항목이 왼쪽인가 · 머리글이 위인가
병합된 칸이 있는가              세로 병합 · 가로 병합
한 행에 값이 몇 개인가           하나인가 여럿인가
같은 항목이 반복되는가           반복되면 순번이 필요하다
```

아래 넷을 따로 적은 이유가 있다. "어떤 구조를 갖는가"로만 물으면 "표가 있다"로
답하고 넘어가게 된다. 답이 되지만 아무것도 확인하지 않은 답이다.

W4 에서 실제로 그렇게 넘어갔다. 주요사항보고서 표 한 건을 열어보고 "항목이
왼쪽에 있다"고 일반화했는데, 지분공시에 가서야 머리글이 위에 있는 표가
따로 있다는 것을 알았다. 그 규칙으로 읽으면 값이 옆으로 밀려 통째로 뭉개진다.

표본 하나로 규칙을 만들지 않는다. 0번 걸음을 둔 이유가 그것이다.

### 앞 작업의 스키마를 그대로 쓰지 않는다

같은 W4 안에서도 계약 공시와 주요사항보고서는 구조가 달랐다. 계약은 유형 3개에 서식 5개라 컬럼 27개로 담겼지만, 주요사항은 유형 28개에 고유 항목 678개이고 한 문서 안에 같은 항목이 39번까지 반복된다. 계약의 스키마를 그대로 가져갔으면 대부분을 버렸을 것이다.

구조를 먼저 보고 그 구조를 살리는 스키마를 정한다. 컬럼으로 담기 어려운 것은 key-value 로 담고, 반복되는 것은 순번을 붙여 담는다. 원문에 있는 것을 잃지 않는 것이 먼저이고 조회 편의는 그다음이다.

### 왜 이 순서인가

각 걸음에 그 걸음에서만 잡히는 오류가 있다. 뒤로 미루면 앞의 오류가 뒤의 결과에 섞여 원인을 못 찾는다.

W4에서 실제로 이렇게 잡혔다.

```
1번에서   항목 이름 앞 하이픈을 빠뜨려 1,083건 미분류
            곧바로 값을 뽑았다면 빈 행 1,022개가 들어간 뒤 알았을 것이다
2번에서   정규식이 개행을 먹어 항목의 절반만 세어짐
            전건에 있어야 할 항목이 71%로 나와 드러났다
4번에서   검산 불일치 4건. 전부 원문 기재 오류로 확인
6번에서   검증 항목의 성격 자체가 틀렸음을 발견
```

### 각 걸음의 통과 조건

숫자로 답할 수 있는 조건을 미리 정해둔다. "괜찮아 보인다"로 넘어가지 않는다.

| 걸음 | 통과 조건 |
|---|---|
| 1 서식 판별 | 미분류 0건. 유형과 서식의 대응이 어긋나는 건 0 |
| 2 항목 사전 | 필수 항목이 해당 서식의 100%에서 나온다 |
| 3 값 추출 | 항목별 추출률을 보고, 빠진 건은 원문에도 없는지 확인 |
| 4 검산 | 자기 검산 항목의 일치율. 불일치 건은 전건 원인 규명 |
| 5 적재 | 대상 문서 전건에 행 존재. 문서당 한 행 |
| 6 검증 | 실패 0. 원문 오류는 실패에서 빼되 목록으로 출력 |

### 검증은 우리 파서를 검사하는 것이다

W4에서 검증 항목을 한 번 고쳤다. "값이 있는가"를 물었더니 회사가 안 쓴 칸까지 실패로 잡혔다.

```
바꾸기 전   값이 채워졌는가            원문 품질을 검사하게 된다
바꾼 후     원문대로 읽었는가          비어 있으면 원문도 비었는지 확인한다
```

원문 자체가 어긋난 건은 실패로 세지 않고 따로 모아 출력한다. 매번 실패가 뜨면 검증 결과를 안 보게 되기 때문이다. 대신 그 목록은 답변에서 밝혀야 할 사실이므로 지우지 않는다.

## 회고에 쓰는 법

기술제안서에 "제안 방법"과 "기대효과"를 써야 한다. 시행착오 기록이 그 재료가 된다. 결과만 있으면 그때 재구성해야 한다.

그리고 "어떻게 알았나" 칸을 모아 보면 검증 방식 자체를 개선할 수 있다.
