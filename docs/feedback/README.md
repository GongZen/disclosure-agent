# 작업 피드백 기록

작업 단계별로 무엇을 시도했고, 무엇이 틀렸고, 어떻게 알았고, 어떻게 고쳤는지 남긴다.

다른 문서와의 역할 구분이다.

| 문서 | 담는 것 |
|---|---|
| `SCHEMA.md` | 지금 구조가 이런 이유 — 최종 상태 |
| `feedback/W*.md` | 어떻게 여기 도달했나 — 과정 |
| `DECISIONS.md` | 되돌리기 어려운 선택과 근거 — 분기점 |

결과만 남기면 같은 실수를 반복한다. 그리고 세션이 바뀌면 과정이 통째로 사라진다.

---

## 형식

각 항목을 다섯 칸으로 쓴다.

```
무엇을 했나        1차 구현이 무엇이었나
무엇이 문제였나     구체적 건수와 함께
어떻게 알았나       검증 / 사용자 지적 / 표본 확인 / 진단 스크립트
어떻게 고쳤나       무엇을 바꿨고 건수가 어떻게 변했나
무엇이 남았나       해결 못 한 것과 그 이유
```

세 번째 칸이 핵심이다. 검증이 잡은 것과 사람이 잡은 것을 구분해야 검증 설계의 구멍이 보인다.

사용자 지적으로만 잡힌 항목이 쌓이면, 그 유형을 다음 작업의 검증 항목에 넣는다.

---

## 작성 시점

각 W 작업이 끝날 때 쓴다. 작업 중에 쌓아두었다가 마무리에 정리한다.

아직 끝나지 않은 작업은 진행 중으로 표시하고 나중에 덧붙인다.

---

## 회고에 쓰는 법

기술제안서에 "제안 방법"과 "기대효과"를 써야 한다. 시행착오 기록이 그 재료가 된다. 결과만 있으면 그때 재구성해야 한다.

그리고 "어떻게 알았나" 칸을 모아 보면 검증 방식 자체를 개선할 수 있다.
