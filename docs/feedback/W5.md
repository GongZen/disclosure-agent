# W5 — 사실 계층 · 재무

정기공시 1,054건의 재무제표에서 값을 꺼내 `fact_financial` 에 담는다.

상태 — 진행 중.

---

## 무엇을 하는 작업인가

재무제표에서 숫자를 꺼내 표로 만드는 일이다. 매출액이 얼마인지, 영업이익이 얼마인지 같은 것이다.

W4 까지 만든 것은 사건 기록이다. 계약을 땄다, 돈을 조달했다, 지분이 변했다. 회사의 살림살이 전체를 보여주는 숫자는 정기공시에 있고 아직 손대지 않았다.

```
지금 못 답하는 것
   삼성전자의 2025년 연결 기준 매출액은 얼마인가
   2024년과 2025년 사이 영업이익이 가장 많이 늘어난 회사는 어디인가
   현대차와 기아 중 자산총계가 큰 쪽은
```

## W4 와 무엇이 다른가

서식의 성격이 다르다.

```
W4 대상   번호 매긴 서식.  "2. 계약내역 → 계약금액(원) → 그 다음 칸이 값"
          기업이 달라도 자리가 같다

W5 대상   자유로운 표.     계정 이름도 단위도 열 배치도 기업마다 다르다
```

세 가지가 겹친다.

### 계정 체계가 업종마다 다르다

사업보고서 207건의 연결 손익계산서 첫 계정 실측이다.

```
매출액        103건
영업수익       24건
수익(매출액)    24건
수익           11건
매출            9건
못 찾음        36건    금융·보험사는 계정 체계가 아예 다르다
```
> 금융 및 보험사는 계정 체계가 다르다는 게, 구체적으로 어떻게 다른 것인가? 매출액이라는 계정은 동일하게 쓸 텐데. 주된 영업이 다르다는 것을 '계정 체계가 다르다'라고 표현하는 걸까?

이것을 "같은 항목의 여섯 가지 표기"로 보면 안 된다. 매출액과 영업수익은 정의상 다른 계정이고, 회계 기준이 업종에 따라 그렇게 표시하도록 정하고 있다.

그래서 D3 의 질문은 표기 통합이 아니라 이것이다. 
업종에 따라 다른 이 계정들을 하나로 묶어도 되는가, 
묶는다면 어떤 근거로 묶고 답변에서 무엇이라고 부를 것인가.

### 단위가 섞여 있다

표 위에 "(단위: 백만원)"이라고 적혀 있고 표 안 숫자는 그 단위다.

```
백만원   47.3%
천원     32.8%
원        8.8%
```

단위를 놓치면 1,000배 틀린 값이 들어간다.

### 한 표에 세 해가 들어 있다

올해·작년·재작년을 나란히 싣는다. 어느 열이 올해인지 헤더를 읽어야 하는데 "제55기", "2024년", "당기" 등으로 표기가 갈린다.

## 열쇠 — XBRL 태그

상당수 문서에 기계가 읽을 수 있는 표시가 붙어 있다. 표의 각 숫자에 무슨 항목이고 어느 해이고 연결인지 별도인지, 단위가 무엇인지가 꼬리표로 달려 있다.

```xml
<TE ACODE="ifrs-full_Revenue"
    ACONTEXT="CFY2024dFY_..._ConsolidatedMember"
    ADECIMAL="-6">107,448,752</TE>
```

```
ACODE      ifrs-full_Revenue      이 숫자가 무슨 항목인가
ACONTEXT   CFY2024dFY             당기 2024년 · 기간(duration) 값
           ConsolidatedMember     연결. SeparateMember 면 별도
ADECIMAL   -6                     백만원. -3 천원, 0 원
```

앞의 세 어려움이 여기서 한꺼번에 해소된다. 다만 모든 문서에 있지는 않다.

0번 걸음 실측이다. 앞서 기록된 "894건 중 488건"은 모집단이 틀렸다.

```
정기공시        1,054건
XBRL 태그 보유    562건 (53%)
태그 없음         492건    그중 474건은 연결/별도 축 문맥을 갖고 있다
```

그래서 이 작업의 뼈대가 정해진다.

```
1  태그가 있는 문서에서 값을 뽑는다        정확하다. 이것이 정답지가 된다
2  같은 문서를 표 파싱으로도 뽑아 대조한다   표 파서가 맞는지 채점된다
3  채점을 통과한 파서를 태그 없는 문서에 적용한다
```

우리가 만든 표 파서를 우리가 만든 정답지로 채점하는 구조다.

## 걸음과 성공 조건

`feedback/README.md` 의 일곱 걸음을 따른다. 조건은 세 종류로 나눈다.

```
구조 조건    데이터가 어떻게 생겼든 성립해야 한다. 어기면 멈춘다
정지 조건    커버리지는 미리 수치로 정하지 않는다. 남은 건을 어떻게 처리할지만 정한다
품질 하한선   뽑은 값이 맞는지 재는 선. 미달하면 파서를 고치고 다시 잰다
```

### 0번 — 원문 구조와 규모 확인

무엇을 보나.

```
정기공시 1,054건이 XML 인가 · 깨진 문서는 몇 건인가

문서 크기와 표 개수                        사업보고서 평균 58만 자
재무제표 표를 어떻게 찾을 것인가
같은 태그가 여러 표에 나오는가              부문정보·주석에도 붙는다
```

성공 조건.

```
파싱 실패 0건 (복구 포함)

```

여기서 규모가 감당 못 할 수준으로 나오면 계획을 바꾼다.

### 1번 — 재무제표 표 판별

문서 안에 표가 수백 개 있다. 그중 재무제표 본문이 어느 것인지 가려낸다.

`DECISIONS.md` 2026-08-13 에 이미 기록된 함정이 있다.

```
ifrs-full_Revenue 가 연결 손익계산서에 36회
                     영업부문 정보 표에 82회
```

부문별 매출을 전체 매출로 착각하면 값이 완전히 틀린다. ACONTEXT 의 축으로 구분하되, 축이 2종인데 본문이 아닌 경우가 56건 있어 표 제목을 보조 조건으로 건다.

성공 조건.

```
구조 조건    부문정보 표가 본문으로 잘못 분류된 건 0
             같은 종류가 한 문서에 두 번 잡히는 건 0
정지 조건    분류 안 되는 표는 원인을 밝힌다
             원문 특성이면 멈추고, 우리 파서 문제면 고친다
확인         표본 30건을 사람이 눈으로 본다
```

첫 항목이 핵심이다. 여기서 틀리면 뒤의 모든 값이 틀린다.

### 2번 — 계정 이름 사전

태그가 있는 문서에서 "이 태그에 어떤 계정 이름이 붙어 있었나"를 자동으로 모은다.

```
ifrs-full_CostOfSales  ←  매출원가(64) · 매출원가 (주21)(4) · 매출원가 (주20,24)(4)
ifrs-full_GrossProfit  ←  매출총이익(87) · Ⅲ.매출총이익(4) · 매출총이익(손실)(3)
```

손으로 세면 6가지였던 표기가 자동 수집으로는 76가지가 나온다. 계정 이름의 30%가 두 개 이상 태그에 매핑되고 부문별 표에서 온 잡음이 섞이므로 정제가 필요하다.

D3 은 이 결과를 보고 정한다. 데이터를 보기 전에 판단하면 존재하지 않는 것을 전제한 정의가 나온다.

성공 조건.

```
담을 항목 목록 확정                매출액·영업이익·당기순이익·자산총계 등
각 항목의 표기 변형을 전수 집계
한 계정 이름이 두 태그에 걸리는 경우가 최종 목록에서 0
금융·보험사 계정 체계를 조사해 미매칭 36건의 처리 방향 결정
```

### 3번 — 값 추출 (아직 넣지 않는다)

두 경로로 뽑아 파일에 저장한다.

```
경로 A   XBRL 태그에서 직접        태그 보유 문서
경로 B   표 파싱으로               같은 문서 + 태그 없는 문서
```

같은 문서를 두 방법으로 뽑는 것이 핵심이다. 4번의 채점 재료가 된다.

성공 조건.

```
경로 A 추출률 — 항목별로 몇 % 나왔는지 확인
경로 B 가 같은 문서에서 돌아감
빠진 건은 원문에도 없는지 확인
```

### 4번 — 채점

경로 A 와 B 의 값을 대조한다. 이 작업의 중심이다.

성공 조건.

```
구조 조건      어긋난 건 전부 원인 규명 — 파서 오류인가 원문 특수사항인가
               단위 환산 오류 0건    1,000배 틀리는 유형은 하나도 남기지 않는다
               연도 매핑 오류 0건    작년 값을 올해로 읽는 유형
품질 하한선     두 경로 일치율 95%. 미달하면 파서를 고치고 다시 잰다
               골든 데이터셋과 어긋나면 그 자리에서 멈춘다
```

95% 는 커버리지 목표가 아니라 경보선이다. 두 경로가 이만큼도 안 맞으면
파서가 틀린 것이므로 다음 걸음으로 가지 않는다. 몇 건을 뽑았느냐와는 무관하다.

### 5번 — 적재

채점을 통과한 뒤에 넣는다.

성공 조건.

```
대상 문서 전건에 행 존재
같은 (문서, 계정, 연도, 기준) 조합의 중복 0
값의 출처가 컬럼에 기록됨          XBRL 인가 표 파싱인가
```

마지막 항목이 중요하다. 어느 경로로 뽑았는지 남겨두면 신뢰도를 구분할 수 있고 답변에서 근거를 댈 때도 쓰인다.

### 6번 — 검증

성공 조건.

```
실패 0 · 원문 오류는 실패에서 빼되 목록 출력
회계 항등식     자산총계 = 부채총계 + 자본총계
                매출액 − 매출원가 = 매출총이익
```

재무제표는 정의상 반드시 맞아떨어져야 하는 관계가 여럿 있다. 우리가 뽑은 값들끼리 대조하면 잘못 뽑은 것이 드러난다.

## 0번 걸음에서 드러난 것 — 태그 유무가 시기로 갈린다

```
태그 있음   2023  78 · 2024 102 · 2025 310 · 2026  72
태그 없음   2023 260 · 2024 230 · 2025   1 · 2026   1
```

2025년부터 거의 전부 태그가 있다. 회계 당국이 XBRL 제출을 단계적으로 확대한 결과로 보인다.

이 사실이 채점 계획을 흔든다. 정답지가 되는 562건이 대부분 2025~2026년 서식이고, 채점받은 파서를 적용할 492건은 대부분 2023~2024년 서식이다. 서식이 시기에 따라 달라졌다면 2025년 문서로 채점한 파서가 2023년 문서에서 틀릴 수 있다.

대비책을 4번 걸음에 넣는다. 2025년 사업보고서에는 2024년과 2023년 값이 비교 열로 함께 실린다. 태그 있는 문서에서 뽑은 과거 연도 값과 태그 없는 그 해 문서의 값을 대조하면 시기를 건너뛴 채점이 된다.

## 1번 걸음 — 배제 규칙이 오분류를 늘린 세 번의 실패

골든 데이터셋을 채우다 KB금융에서 파서가 단위를 하나도 못 뽑는 것이 드러났다.
고치는 데 세 번 걸렸고 두 번째는 첫 번째보다 나빠졌다. 기록해 두는 이유는
같은 성질의 실수를 다음 걸음에서 또 할 수 있기 때문이다.

### 수치로 본 경과

| 차수 | 오분류 | 단위없음 | 종류없음 | 표 총계 |
|---|---|---|---|---|
| 수정 전 | 75 | 258 | 482 | 9,546 |
| 1차 | 4 | 0 | 220 | 9,211 |
| 2차 | 61 | 0 | 220 | 9,209 |
| 3차 | 0 | 0 | 220 | 9,189 |

오분류는 재무제표 5종이 아닌 표가 5종으로 판정된 수다. 구조 조건이라 0이어야 한다.
2차에서 4에서 61로 늘었다. 고치려던 것이 더 나빠진 것이다. 3차에서 0이 됐다.

종류없음 220은 고칠 대상이 아니다. 주석 문장 표처럼 5종이 아닌 표라
미판정으로 남는 것이 옳다. 순서 추정(order)이 227에서 116으로 준 것이
부수 효과다. 근거가 약한 추정이 줄고 제목 판정 비율이 92.0%에서 95.5%로 올랐다.

```
<TABLE>  제 16기 반기말 : 2023년 6월 30일 현재              </TABLE>
<TABLE>  주식회사 KB금융지주와 그 종속기업 │ (단위: 백만원)   </TABLE>
<TABLE>  과 목 │ 제16기 반기말 │ 제15기말 │ …               </TABLE>   ← 데이터
```

가운데 표에 단위가 있는데 첫 칸이 회사명이라 `_title_cell` 이 제목 표로 보지 않았다.
그래서 단위를 잃고, 그 표가 데이터 표로 `buf` 에 들어가 미판정 표가 하나 늘었다.

전수로 세니 이 유형이 157개였다. 셋으로 갈렸다.

```
60   ['(단위 : 백만원)']                           단위만 있는 표
56   ['삼성생명보험주식회사', '(단위 : 백만원)']       회사명 + 단위
41   ['이익잉여금처분계산서', …, '(단위 : 원)']        이름을 모르는 표
```

세 유형의 공통점은 숫자 칸이 하나도 없다는 것이다. 여기서 규칙이 나왔다.
숫자 칸이 없고 단위 표기가 있으면 제목 표로 본다. 부작용을 전수로 확인했더니
기존에 데이터 표로 쓰이던 것이 새 조건에 걸리는 경우는 0이었다.

이 규칙으로 단위없음 258이 0이 됐다. 여기까지는 순조로웠다.

### 함께 드러난 것 — 이익잉여금처분계산서가 5종으로 읽힌다

미판정 482개의 정체를 전수로 갈랐다.

```
307   주석·회사명·단위 표         5종이 아니다. 미판정이 정답이다
167   이익잉여금처분계산서         5종이 아니다. 미판정이 정답이다
  8   진짜 재무제표 표            5종인데 못 정했다. 이것만 손실이다
```

482개 중 474개는 고칠 대상이 아니었다. 값을 잃고 있는 것은 8개뿐이다.

대신 더 나쁜 것이 나왔다. 167개 중 75개가 `_kind_by_content` 에서
ci(43) 또는 bs(32)로 읽혔다. 처분계산서에 `기타포괄손익누계액 대체` 행이 있어
ci 규칙(need=1)에 걸린다.

지금은 같은 종류가 이미 잡혀 있어 중복으로 버려진다. 우연에 기댄 것이다.
포괄손익계산서가 먼저 안 잡힌 문서에서는 미처분이익잉여금이 포괄손익 값이 된다.
값을 못 뽑는 것보다 나쁘다. 못 뽑으면 빈칸이 보이지만 잘못 뽑으면 그대로 답이 된다.

### 1차 실패 — 자본변동표의 열 이름을 몰랐다

배제어에 `미처분이익잉여금` 을 넣고 표 전체에서 찾게 했다. 오분류가 75에서 4로 줄었다.
남은 4건이 고려아연 자본변동표였다.

```
['자본','지배기업 소유지분','비지배지분','자본 합계','자본금','자본잉여금',
 '자본조정','기타포괄손익누계액','미처분이익잉여금', …]
```

진짜 자본변동표인데 열 이름으로 `미처분이익잉여금` 을 쓴다. 대부분은 `이익잉여금`
이라고만 쓰는데 고려아연은 앞에 `미처분` 을 붙였다. 표본 434개 중 4개, 0.9%다.

제목으로 이미 eq 가 확정돼 살아남았으나, 제목 없는 문서에서 같은 표기가 나오면
자본변동표를 통째로 버린다.

### 2차 실패 — 재무상태표의 행을 몰랐다

두 표가 그 말을 쓰는 위치가 다르다고 보고 규칙을 나눴다.

```
처분계산서   'Ⅰ. 미처분이익잉여금'      행의 첫 칸. 계정이 세로로 늘어선다
자본변동표   '미처분이익잉여금'         머리글의 열 이름. 계정이 가로로 눕는다
```

행 머리에서만 찾도록 바꿨다. 오분류가 4에서 61로 늘었다.

새로 걸린 것이 한전기술 재무상태표였다. 자본 항목을 세분화하면 재무상태표에도
`미처분이익잉여금` 이 행으로 나온다.

`미처분이익잉여금` 은 세 표에 다 나온다. 배제 신호로 쓸 수 없는 말이었다.

### 3차 — 분포를 먼저 세고 규칙을 정했다

표본 300건에서 계정별로 어느 쪽에 나오는지 셌다.

| 계정 | 처분계산서 | 그 밖의 표 |
|---|---|---|
| 미처분이익잉여금 | 101 | 14 |
| 차기이월미처분이익잉여금 | 36 | 0 |
| 이익잉여금처분액 | 41 | 0 |
| 임의적립금이입액 | 4 | 0 |
| 미처리결손금 | 9 | 6 |
| 자산총계 | 0 | 584 |
| 부채총계 | 0 | 868 |
| 영업이익 | 0 | 781 |

고유한 것과 겹치는 것이 갈렸다. 겹치는 둘을 빼고 고유한 셋만 남겼다.

그리고 역방향 안전장치를 넣었다. 자산총계·부채총계·자본총계·영업이익·매출총이익·
영업활동·투자활동·재무활동 중 하나라도 행 머리에 있으면 배제를 취소한다.

이것이 두 실패에서 배운 것이다. 배제 신호를 아무리 정교하게 골라도 예상 못 한
표기가 또 나온다. 5종임을 확정하는 신호가 배제 규칙보다 우선하면, 배제 쪽이
틀려도 진짜 재무제표는 살아남는다.

### 무엇이 반복됐는가

1차와 2차 모두 규칙을 먼저 세우고 분포를 나중에 봤다.

```
1차   "처분계산서에는 미처분이익잉여금이 있다"        맞다
      "그러니 그 말이 있으면 처분계산서다"           틀렸다
      자본변동표에도 있다는 것을 안 세어봤다

2차   "자본변동표는 열 이름으로 쓴다"                맞다
      "그러니 행 머리에서만 찾으면 된다"             틀렸다
      재무상태표에도 행으로 온다는 것을 안 세어봤다
```

두 번 다 관찰은 맞았고 일반화가 틀렸다. 한 곳에서 본 사실을 전체 규칙으로 옮길 때
반대쪽을 세어보지 않았다.

3차에서 한 일은 규칙을 정교하게 만든 것이 아니다. 계정마다 양쪽 등장 횟수를
먼저 세고, 0이 나온 것만 골랐다. 순서를 바꾼 것뿐이다.

### 배제 규칙은 양방향으로 확인한다

이 걸음에서 얻은 규율이다. 무엇을 버리는 규칙을 만들 때는 두 수치를 함께 센다.

```
버리려는 것에서 이 신호가 몇 번 나오는가       규칙이 작동하는가
남기려는 것에서 이 신호가 몇 번 나오는가       규칙이 해치는가
```

앞의 것만 세면 1차와 2차가 반복된다. 뒤의 것이 0이 아니면 그 신호는 쓸 수 없다.

그리고 배제 규칙에는 역방향 안전장치를 함께 둔다. 남겨야 할 것을 확정하는 신호가
버리는 신호보다 우선하게 하면, 규칙이 틀렸을 때 손실이 아니라 소음이 남는다.

## 1번 걸음 — 열을 잘못 읽고 있었다

골든 데이터셋 대조에서 드러났다. 표는 제대로 찾았는데 그 안에서 엉뚱한 열을 읽고
있었다. 표를 찾는 것과 값을 꺼내는 것이 다른 문제라는 것을 여기서 알았다.

### 발단

삼성전자 2023 반기 손익 세 값이 전부 어긋났다.

```
수익(매출액)   파서  60,005,533   골든 123,750,904
영업이익       파서     668,547   골든   1,308,725
당기순이익      파서   1,723,571   골든   3,298,171
```

파서 값이 정확히 2분기 3개월치였다. 골든은 상반기 누적이다.

같은 반기보고서인데 KB금융은 맞았다. 원문 구조가 달랐다.

```
삼성전자 반기   과 목 │ 당기 3개월 │ 당기 누적 │ 전기 3개월 │ 전기 누적
KB금융 반기     과 목 │ 제16기 반기 │ 제15기 반기 │ 제15기
                       (누적)      (전기 누적)  (전기 연간)
```

KB금융에는 3개월 열이 없다. 첫 열이 곧 누적이라 우연히 맞았다. 표본 둘 중 하나가
우연히 통과하면 규칙이 맞는 것처럼 보인다.

### 열 구조 전수 실측

연결 손익계산서 1,374개의 머리글 모양이다.

| 3개월 표기 | 누적 표기 | 칸수 | 건수 | 비율 |
|---|---|---|---|---|
| 있음 | 있음 | 4 | 949 | 69.1% |
| 없음 | 없음 | 3 | 377 | 27.4% |
| 없음 | 없음 | 1 | 20 | 1.5% |
| 나머지 | | | 28 | 2.0% |

칸 1개짜리 20건은 주석 문장이 `is` 로 오분류된 것이다. 별개 문제로 남겨두었다.

보고서 종류가 정확히 가른다.

| 종류 | 표 | 3개월 열 있음 |
|---|---|---|
| annual | 377 | 0 · 0.0% |
| half | 311 | 294 · 94.5% |
| quarter | 686 | 656 · 95.6% |

사업보고서에는 3개월 열이 하나도 없다. 반기·분기는 95%가 가지고 있다.

### 머리글은 2단이다

```
['제 55 기 반기', '제 54 기 반기']              1행  기수. 칸 2개
['3개월', '누적', '3개월', '누적']               2행  기간 구분. 칸 4개
['수익(매출액)', 60,005,533, 123,750,904, …]    데이터. 값 4개
```

기간 행의 칸 수가 데이터 행의 값 개수와 같다. 그대로 짝지으면 열마다 기간이 정해진다.
파서가 읽던 첫 값이 당기 3개월이고 누적은 그다음이다.

### 양방향으로 확인했다

배제 규칙에서 두 번 실패한 뒤라 이번에는 규칙을 정하기 전에 반대쪽도 셌다.

```
"3개월" 등장       1,900회
"누적" 등장        1,900회        정확히 같다. 항상 쌍으로 나온다
"누계"                8회        변형 표기

"3개월" 이 연간 보고서에 나오는가        377표 중 0건
3개월 열이 있는데 "누적" 표기가 없는가    (있음, 없음) 조합 0건
```

두 말이 쌍으로만 나오므로 판정 신호로 쓸 수 있다. `미처분이익잉여금` 처럼 양쪽에
걸치지 않는다. 이 확인을 먼저 했기에 이번에는 한 번에 끝났다.

### columns() 가 하는 일

값 열마다 기간 유형을 낸다. 세 가지 중 하나씩이다.

```
삼성전자 반기    ['quarter', 'cumulative', 'quarter', 'cumulative']
삼성전자 1분기   ['quarter', 'cumulative', 'quarter', 'cumulative']
삼성전자 연간    ['annual', 'annual', 'annual']
```

기간 행이 없는 문서는 기수 행에서 "반기"·"분기" 표시를 본다. KB금융이 그 형태다.

```
['과 목', '제16기 반기', '제15기 반기', '제15기']
  →  cumulative · cumulative · annual
```

1분기는 3개월과 누적이 같은 값이라 어느 열을 읽어도 맞지만 구분은 살아 있다.
`period_type` 을 채울 때 이 값을 그대로 쓴다.

### 결과

골든 대조가 세 번에 걸쳐 통과했다.

| 차수 | 일치 | 불일치 | 무엇을 고쳤나 |
|---|---|---|---|
| 1차 | 27 | 7 | — |
| 2차 | 33 | 3 | 계정 완전 일치 우선 · 항목 사전 보강 |
| 3차 | 36 | 0 | 열 선택 |

앞의 둘은 대조 스크립트의 결함이었고 파서와 무관했다. 셋째만 진짜 문제였다.

|---|---|---|---|

### 실패 38건은 열 문제가 아니었다

전부 `is` 이고, 그 표를 열어보면 값이 아니라 주석 문장이다.

```
KB금융 반기 is
   ['주1) 제15기말은 당기 K-IFRS 제1117호(보험계약)적용에 따라 소급재작성 되었습니다.…']
```

`columns()` 가 빈 리스트를 낸 것은 값 열이 하나도 없기 때문이다. 열 판정이 틀린 것이
아니라 손익계산서가 아닌 표가 `is` 로 판정된 것이다.

`_resolve` 가 마지막 수단으로 법정 순서를 채울 때 아직 안 나온 종류를 그 자리 표에
붙인다. 그 표가 주석이어도 붙는다. 다음 탐색 대상이다.

### 얻은 것

표를 찾는 것과 값을 꺼내는 것은 다른 문제다. 1번 걸음의 성공 조건을 "재무제표 표를
찾는다" 로만 두면 열이 틀린 채 통과한다. 표 판별이 끝나면 그 안에서 어느 열·어느 행을
읽을지가 남고, 그것은 골든 대조로만 잡힌다.

그리고 표본 둘로 규칙을 확인하면 안 된다. 삼성전자와 KB금융을 봤는데 KB금융이 우연히
통과해 문제가 절반만 보였다.

## 1번 걸음 — 없는 재무제표를 만들어내고 있었다

열 판정 실패 38건을 쫓다 나왔다. 열이 틀린 것이 아니라 손익계산서가 아닌 표가
`is` 로 판정돼 있었다.

### 원인 — 순서 채움이 남는 표에 이름을 붙인다

```python
# _resolve 의 마지막 수단
left = [x for x in _ORDER if x not in known]     # 아직 안 나온 종류
if left:
    known.add(left[0])
    yield basis, left[0], table, "order", unit   # 이 표에 붙인다
```

출발점이 표다. 종류가 안 정해진 표가 남아 있으면 아직 안 나온 종류를 붙인다.

```
KB금융 사업보고서에서 일어난 일

   1  제목으로 bs · ci · eq · cf 가 잡혔다
   2  주석 문장 표가 종류 미정으로 남았다
   3  아직 안 나온 종류는 is 하나다
   4  주석 표에 is 를 붙였다
```

금융지주는 손익계산서를 따로 내지 않는다. 포괄손익계산서 하나만 낸다. 원문에 없는
재무제표를 파서가 만들어낸 것이다. 기업별로 KB금융 13 · 메리츠금융지주 12 ·
삼성화재 8로 금융지주에 몰린 이유가 이것이다.

### 전수

| 판정 근거 | 값 있음 | 값 없음 | 값 없음 비율 |
|---|---|---|---|
| name | 8,779 | 0 | 0.0% |
| content | 74 | 0 | 0.0% |
| order | 72 | 44 | 37.9% |

제목과 계정 조합으로 판정한 것은 하나도 틀리지 않았다. 순서 채움만 열에 하나 이상이
가짜였다.

### 손실처럼 보이나 아니다

44개 전부가 그 종류의 유일한 후보였다. 빼면 그 문서에서 `is` 가 통째로 사라진다.
그런데 지금 담고 있는 것이 값이 아니라 주석 문장이라 빼든 안 빼든 담을 값은 없다.

빼면 `is` 자리가 비는데 그것이 원문에 맞는 상태다. `POLICY.md` 에서 "원문에 없는 값"과
"못 뽑은 값"을 구분하기로 한 것과 같다. 주석 표를 `is` 로 담아두면 나중에 그 문서에
손익계산서가 있다고 착각한다.

### 규칙

값 칸이 하나도 없는 표는 순서 채움과 내용 판정 대상에서 뺀다. 데이터가 없으면
재무제표일 수 없다.

`_is_not_fs` 와 나란히 두었으나 거르는 것이 다르다.

```
_has_value    값이 없는 표. 주석 문장이나 회사명처럼 애초에 데이터가 아니다
```

```
값이 같으면 문제없다
값이 다르면 어느 것을 쓸지 정해야 한다
   소급재작성 225건 / 1,051건 = 21.4%
   회계기준이 바뀌면 전기 값을 다시 계산해 적는다
```

다섯 건 중 하나가 갈린다. 그리고 답변에 근거 공시를 표시해야 하는데 같은 값이
세 문서에 있으면 어느 것을 댈지도 정해야 한다. 당기만 담으면
(기업, 연도, 항목)이 문서 하나에 대응한다.

### 고유 키에 기간 유형이 들어간다

성공 조건이 "같은 (문서, 계정, 연도, 기준) 조합의 중복 0" 이었으나 좌표가
하나 더 있다.

```
삼성전자 2023 반기보고서 매출
   2분기 3개월치    60,005,533
   상반기 누적     123,750,904
둘 다 원문 값이고 둘 다 담기로 정했다
```

`UNIQUE (doc_id, item_code, fiscal_year, period_type, basis)` 로 두었다.

### value 와 value_raw 를 나눈다

조회는 원 단위로 해야 기업 간 비교가 되고, 근거를 댈 때는 원문에 적힌 숫자를
그대로 보여야 한다. 삼성화재는 원 단위로 삼성전자는 백만원 단위로 적는데
"원문에 96,450,389,944,868로 기재" 라고 말하려면 표기값이 필요하다.

### 태그가 있어도 못 쓰는 경우가 둘 더 나왔다

적재하고 보니 값이 빈 행이 22개였다.

```
ACONTEXT 없음   반기보고서 7건 + 사업보고서 2건
                당기인지 전기인지, 누적인지 3개월치인지 모른다
                태그가 3개월치를 골라 누적과 두 배 어긋났다

ADECIMAL 없음   KB금융 2024-03-26 · 메리츠금융지주 2024-02-08
                단위를 몰라 원 단위 환산이 안 된다
```

둘 다 같은 성질이다. 태그가 계정은 알려주는데 값을 특정하는 좌표 하나가 빠졌다.
좌표가 빠지면 태그의 이점이 사라지므로 전부 읽어내는 표 파싱으로 넘긴다.

표 파싱이 두 문서의 단위를 읽어냈다. KB금융은 백만원, 메리츠금융지주는 원이다.
1번 걸음에서 단위 추출 실패 258건을 0으로 고쳐두지 않았다면 여기서 막혔을 것이다.

### 2차 항목은 자체 항등식이 있다

`매출액 − 매출원가 = 매출총이익` 은 1차 8항목에 매출원가와 매출총이익이 없어
확인할 수 없었다. 2차 항목을 담으면 이 검증이 살아난다.

```
매출액 − 매출원가 = 매출총이익
영업이익 = 매출총이익 − 판매비와관리비
영업활동 + 투자활동 + 재무활동 = 현금 증감
```

골든에 정답지가 없어도 값들끼리 맞춰 볼 수 있다. 1차 항목보다 오히려
검증이 강하다. 1차는 회계 항등식 하나뿐이었다.

## 2차 항목 — 자체 항등식이 검증 장치가 된다

1차를 검증한 뒤 이어서 담았다. 골든에 정답지가 없으나 값들끼리 맞물리는
관계가 있어 1차보다 오히려 검증이 강했다.

### 담은 것

| 묶음 | item_code |
|---|---|
| 재무상태표 | current_assets · noncurrent_assets · current_liabilities · noncurrent_liabilities |
| 대분류 예외 | held_for_sale_assets · held_for_sale_liabilities · financial_business_assets · financial_business_liabilities |
| 손익 | cost_of_sales · gross_profit · sga · pretax_income |
| 현금흐름표 | cf_operating · cf_investing · cf_financing · capex |
| 금융·보험 | net_fee_income · insurance_revenue |

`capex` 가 D2 설비투자다. 참고 질의에 "설비투자 규모가 더 큰 기업" 이 있는데
1차만으로는 답할 수 없었다.

### 부호 규약을 정해야 했다

같은 항목이 경로마다, 문서마다 부호가 갈렸다.

```
capex            XBRL 은 "취득한 금액" 이라 양수로 태깅한다
                 현금흐름표는 현금이 나간 것이라 (47,522,179) 로 적는다
                 532쌍 중 199쌍이 부호만 반대. 절댓값은 같다

cost_of_sales    table + 1,117 / − 72 · xbrl + 1,141 / − 69
sga              table + 1,097 / − 148 · xbrl + 1,262 / − 122
```

셋 다 양수로 통일했다. "설비투자 5조" 라고 말하고 "규모가 더 큰 기업" 을
물으므로 크기 비교가 바로 되어야 한다. 부호가 섞이면 순서가 뒤집힌다.

비용 부호를 통일하니 매출총이익 항등식 어긋남이 142건에서 2건으로 줄었다.

`cf_operating` · `cf_investing` · `cf_financing` 은 그대로 둔다. 부호 자체가
정보다. 영업활동이 음수면 영업으로 현금을 벌지 못했다는 뜻이다. 두 경로가
1,654쌍 전부 일치해 손댈 것도 없었다.

### 유동 + 비유동 = 총계가 항상 성립하지 않는다

```
와이지엔터테인먼트   유동부채 201,406 + 비유동부채 22,466 + 매각예정 부채 22,589 = 246,462
카카오            유동자산 8,109,598 + 비유동자산 16,495,206 + 금융업자산 981,572 = 25,586,377
```

매각예정 처분집단은 K-IFRS 1105호가 유동·비유동 어느 쪽에도 넣지 않게 한다.
팔기로 한 사업부는 계속 쓰는 자산과 구분해야 하기 때문이다. 금융업 자산·부채는
금융 자회사를 둔 지주회사가 일반 영업과 나눠 적는다.

둘을 항목으로 담아 검산에 더했다. 다만 포함 관계가 기업마다 다르다.
CJ제일제당은 매각예정을 유동·비유동 밖에 두고 카카오는 비유동 안에 넣는다.
무조건 더하면 이번엔 카카오가 어긋난다. 조합을 전부 시도해 맞는 것을 찾는다.

### 기업이 만든 확장 태그

```
entity00258801_AssetsFromFinancialServiceSegmentOfAssetsAbstract
entity00635134_NonCurrentAssetsOrDisposalGroupsClassifiedAsHeldForSale…
```

`entity{법인등록번호}_` 접두어가 붙어 이름을 고정할 수 없다. 접두어를 떼고
뒷부분으로 견준다. 문서 14건이고 우리 26개 항목 중에는 매각예정과 금융업만 걸린다.

뒷부분을 완전 일치로 견주는 이유가 있다. 금융업자산 대분류는
`OfAssetsAbstract` 로 끝나고 그 안의 현금및현금성자산은
`OfAssetsFromFinancialServiceSegment…` 로 이어진다. 부분 일치를 쓰면
세부 항목이 함께 걸린다.

### 주석 칸 때문에 열이 밀렸다

```
매출      4,23,29 │ 1,048,977,927 │ 885,023,767      주석 칸 있음
매출총이익           151,343,929 │ 133,451,345        주석 칸 없음
```

같은 표 안에서 주석 칸이 있는 행과 없는 행이 섞인다. `to_num` 이 주석을
None 으로 내주므로 값 목록은 만들어지나 위치가 한 칸 밀린다. 매출총이익의
당기 값 자리에 전기 값이 왔다.

값 목록을 만들기 전에 앞쪽 주석 칸을 떼도록 고쳤다. 매출총이익 항등식이
100.00% 가 됐다.

이 오류는 다른 장치로 못 잡았다. 원문에 있는 숫자라 크기 검산에 안 걸리고,
태그 없는 문서라 두 경로 대조도 닿지 않았다. 2차 항등식이 없었으면 남았다.

### 반드시 성립과 대체로 성립을 나눈다

넷을 다 항등식이라 부른 것이 부정확했다.

| 관계 | 대상 | 어긋남 | 성질 |
|---|---|---|---|
| 자산총계 = 부채총계 + 자본총계 | 1,735 | 0 | 반드시 성립 |
| 매출액 − 매출원가 = 매출총이익 | 2,349 | 0 | 반드시 성립 |
| 매출총이익 − 판관비 = 영업이익 | 2,298 | 274 | 대체로 성립 |
| 유동 + 비유동 = 자산총계 | 1,564 | 11 | 대체로 성립 |
| 유동 + 비유동 = 부채총계 | 1,562 | 4 | 대체로 성립 |

뒤의 셋은 기업의 표시 방식에 따라 어긋날 수 있다. 판관비 밖에 기타영업비용을
따로 적거나 대분류를 더 두는 경우다. 참고 지표로 두고 실패로 세지 않는다.

`(기업, 항목, 연도, 기준, 기간)` 조합에 행이 여럿인 경우가 9,857건이었다.

`base_month` 를 넣고 고유 키에 포함하니 676건으로 줄었다.

### 정정본이 여럿인 문서

남은 676건은 정정본 중복이었다.

```
카카오 2023 사업보고서
   20240320  원본
   20240321  정정본 → 원본 지목
   20240328  정정본 → 원본 지목
   20240418  정정본 → 원본 지목
```

정정본 서식이 "정정대상 공시서류의 최초제출일" 을 적게 되어 있다. 직전
정정일이 아니라 최초 제출일이다. 그래서 세 번 정정하면 셋 다 원본을 가리킨다.
전체 1,024건 관계 중 정정본을 가리킨 것은 0건이다.

W3 이 불완전한 것이 아니라 제 적재 로직이 잘못됐다. `doc_relation` 에 지목된
원본만 제외하니 정정본 셋이 남았다. 같은 (기업, 회계연도, 기준월, 보고서종류)
에서 최종 접수분만 담도록 고쳐 좌표 중복이 0이 됐다.

2026-08-15에 "값 자체의 판본 선택은 W4·W5에서 별도로 정한다" 고 적어둔 것이
이 자리다. 관계 테이블만으로 판본을 고를 수 있다고 본 것이 잘못이었다.
