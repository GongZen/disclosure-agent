## 1. 날짜 표기가 세 가지였다

무엇을 했나
정정 헤더의 "정정대상 공시서류의 최초제출일"에서 날짜를 뽑았다. 한글 표기(`2024년 03월 12일`)와 거래소 ISO 표기(`2025-10-30`) 두 가지를 처리했다.

무엇이 문제였나
1,004건 중 108건에서 추출 실패. 10.8%다.

어떻게 알았나
실패 건의 원문을 직접 열어봤다. 사용자가 "실패 5건에 대해서도 검토가 필요한 거 아니냐"고 지적하기 전, 108건 단계에서는 내가 먼저 조사했다.

어떻게 고쳤나
같은 필드 안에서도 표기가 섞여 있었다.

```
2024년 03월 12일    한글
2023-01-27          하이픈
2022.06.28          점
```

구분자를 `[-.년월]`로 통합했다. 108건이 5건으로 줄었다.

나중에 `2025년 08년 28일`처럼 구분자가 잘못 쓰인 원본 오타도 발견해 `월` 자리에 `년`이 와도 받도록 했다.

추가로 발견한 것
`20250008` 같은 값이 나왔다. 월 00, 일 08이다. 월일 범위 검사를 넣어 걸러냈다. 이걸 안 걸렀으면 존재하지 않는 날짜로 후보를 찾아 조용히 실패했을 것이다.

무엇이 남았나
2건. 아래 8번 참조.

## 2. 주요사항보고서의 후보가 섞였다

무엇을 했나
후보를 좁힐 때 `doc_subtype`으로 필터했다.

무엇이 문제였나
주요사항보고서는 `doc_subtype`이 598건 전부 결측이라 필터가 작동하지 않았다. 같은 날 다른 종류 공시가 후보로 잡혔다.

```
SK하이닉스 2023-04-03
  주요사항보고서(교환사채권발행결정)
  주요사항보고서(자기주식처분결정)
```

어떻게 알았나
진단 스크립트로 ambiguous 사례의 후보 구성을 출력해 봤다.

어떻게 고쳤나
W2에서 만들어 둔 `major_kind`로 좁혔다. 121건에서 106건으로 줄었다.

W2의 파생 컬럼이 여기서 값을 했다. 그때는 "D1에서 쓸 것"이라고만 생각했는데 관계 연결에도 필요했다.

## 3. 한 갈래만 따라가면 안 됐다

무엇을 했나
연쇄 정정을 따라갈 때 한 날짜에 정정본이 1건이면 따라가고, 2건 이상이면 포기했다.

무엇이 문제였나
후보 여럿 91건 중 88건이 "그 날짜 문서가 전부 정정본"이었다. 정정본이 여럿이라 어느 쪽을 따라갈지 몰라 포기한 것이다.

어떻게 알았나
사용자 지적. "왜 위 사항들을 여기서 해결할 수 있는 부분을 제대로 해결하지 않고 W4로 넘어가는가"라는 물음이었다.

그 전에 나는 "W4에서 event_contract가 구조화되면 더 정확하다"고 미뤘다. 그건 편의를 필요성으로 포장한 것이었다. 정보는 지금도 원문에 다 있었다.

어떻게 고쳤나
너비 우선 탐색으로 바꿨다. 한 갈래만 따라가지 않고 도달 가능한 원본을 전부 모은다.

```
정정본 X → 2024-05-13 (정정본 A, B 둘 다 존재)
             A → 2024-03-11 원본 C
             B → 2024-03-11 원본 C      → 원본 집합 {C}. 확정
```

정정본이 여럿이어도 결국 같은 원본을 가리키면 확정된다. 91건이 43건으로 줄었다.

무엇이 남았나
37건. 도달한 원본이 실제로 둘 이상이거나 제자리를 도는 경우다. 뒤쪽은 모호가 아니었다. 8번 참조.

## 4. 값 대조가 첫 날짜만 보고 있었다

무엇을 했나
후보가 여럿일 때 정정 헤더의 큰 숫자를 후보 원문과 대조해 확정하는 패스를 넣었다. 정정 전 값은 원본에 있고 정정 후 값은 어느 원본에도 없다는 성질을 쓴다.

무엇이 문제였나
대조 대상을 `target_date`의 원본으로 한정했다. 너비 우선 탐색으로 바꾼 뒤에는 원본이 체인 깊은 곳에 있을 수 있는데 그걸 놓쳤다.

어떻게 알았나
탐색 방식을 바꾼 뒤 값 대조 확정 건수가 늘지 않는 것을 보고 코드를 다시 읽었다.

어떻게 고쳤나
탐색이 찾은 원본 집합을 반환하도록 하고 그것을 대조 대상으로 삼았다. 16건에서 22건으로 늘었다.

## 5. 필터를 포기하는 fallback이 오연결을 만들었다

무엇을 했나
후보를 유형으로 좁힐 때, 일치하는 후보가 없으면 필터를 포기하고 원래 후보를 그대로 썼다. 아무것도 못 찾는 것보다 낫다고 생각했다.

무엇이 문제였나
15건이 잘못 연결됐다.

```
두산로보틱스  [기재정정]주요사항보고서(회사합병결정)
  → 주요사항보고서(타법인주식및출자증권양수결정)
```

회사합병결정의 정정본이 타법인주식양수결정을 가리키게 됐다.

어떻게 알았나
검증 스크립트의 표본 출력을 눈으로 보다가 발견했다. 건수 검사만 있었으면 못 잡았다.

어떻게 고쳤나
fallback을 제거해 유형이 일치하는 후보가 없으면 미연결로 두었다. 연결이 544건에서 529건으로 줄었지만 틀린 이력을 답변에 내보내는 것보다 낫다.

그리고 검증에 "정정 연결은 세부 유형이 같다"를 추가했다.

무엇이 남았나
없다. 다만 처음 검증을 짤 때 이 항목을 넣지 않은 것이 문제였다. 방향·기업·시간 순서는 검사했는데 유형은 빠뜨렸다.

## 6. 해지 연결에 체인 추적이 빠져 있었다

무엇을 했나
계약 해지 공시가 지목한 날짜에서 계약체결 공시를 찾아 연결했다.

무엇이 문제였나
지목한 날짜에 정정본만 있는 경우를 처리하지 않았다. 정정본을 원계약으로 잡으면 "언제 체결한 계약인가"에 정정일자를 답하게 된다.

```
삼성중공업 해지 → 지목 20240612 · 후보 2건
   exchange_20240612800459   [기재정정]단일판매ㆍ공급계약체결
   exchange_20240612800468   [기재정정]단일판매ㆍ공급계약체결
```

어떻게 알았나
사용자 지적 후 조사. "그 외에 개선할 여지가 있을 것"이라는 요구에 따라 termination 3건의 후보 구성을 출력해 보다 발견했다.

정정 연결에는 체인 추적을 넣었는데 해지 연결에는 넣지 않았다. 같은 문제인데 한쪽만 고친 것이다.

어떻게 고쳤나
해지 연결도 같은 탐색 함수를 쓰도록 바꿨다. 원본 미확정이 3건에서 1건으로 줄었다.

## 7. 검증 항목 자체가 틀렸던 적

무엇을 했나
"연결된 두 문서의 세부 유형이 같다"를 모든 관계에 적용했다.

무엇이 문제였나
계약 해지는 해지공시가 체결공시를 가리키므로 유형이 다른 것이 정상이다. 5건이 실패로 나왔다.

어떻게 알았나
검증 실행 결과. 실패 5건이 정확히 termination 연결 5건과 같아 바로 보였다.

어떻게 고쳤나
유형 일치 검사를 정정에만 적용하고, 해지에는 "도착점이 계약 체결 공시인가"를 따로 검사하도록 나눴다.

## 8. 사유 하나에 두 상황이 뭉쳐 있었다

무엇을 했나
되짚기가 원본에 닿지 못하면 `ambiguous`로 기록했다. 37건이 나왔고 "후보 여럿"이라 불렀다.

무엇이 문제였나
이름도 틀렸고 사유도 틀렸다. `candidates` 값으로 갈라보니 두 상황이 섞여 있었다.

```
candidates = 0     24건    원본에 아예 못 닿음
candidates = 2~3   14건    원본이 실제로 둘 이상
```

앞의 24건은 모호한 것이 아니다. 아무 데도 도달하지 못한 것이다. 그런데 같은 사유로 기록해 D7에서 "여러 건이 있어 특정할 수 없습니다"라고 답하게 돼 있었다.

어떻게 알았나
사용자 지적. "후보 1건 23건이 무슨 뜻이냐, 설명이 구체적이지 않다"는 물음이었다.

설명하려고 실제 사례를 추적했더니 정정본이 자기 접수일을 지목하고 있었다.

```
에코프로비엠   접수 20241022  지목일 20241022
  깊이 0  후보 1건 → exchange_20241022900223  정정본
  깊이 1  후보 1건 → exchange_20241022900223  같은 문서
```

내가 앞서 "모호함이 체인 깊은 곳에서 생긴다"고 보고한 것은 틀렸다. 제자리를 도는 것이었다.

어떻게 고쳤나
계약 체결일을 봤다. 계약 체결 공시는 체결 시점에 내므로 수주일자가 수집 시작 전이면 원본도 범위 밖이다.

```
2023-01-01 이전  16건    현대로템 20210714 · 한전기술 20140828 · 삼성바이오로직스 20201103
2023-01-01 이후   7건    현대건설 20230624 · 삼성E&A 20231213
날짜 없음         1건    에코프로비엠
```

`parse_contract_date()`를 만들고, 원본에 하나도 닿지 못한 건에만 적용해 `out_of_scope`로 바꿨다. 원본에 하나라도 닿은 건은 건드리지 않았다. 그건 진짜 모호다.

삼성E&A 2건도 같은 규칙에 걸렸다. 지목일이 `2043-05-31`이라 읽을 수 없었지만 수주일자가 2020-11-19이었다. 아래 남은 것에 적어둔 것을 별도 처리 없이 함께 해결했다.

```
범위 밖        434 → 452    +18
원본 미확정      37 →  21    -16
날짜 추출 실패     4 →   2     -2
연결 가능분    92.8% → 95.8%
```

추가로 발견한 것
`candidates` 컬럼 이름이 뜻과 어긋나 있었다. `SCHEMA.md`에는 "마지막 단계의 후보 문서 수"라고 적혀 있는데 실제로는 도달한 원본의 수다. 내가 후보와 원본을 섞어 쓴 원인이기도 하다. W4에서 이름을 바꾼다.

검증도 하나 고쳤다. "범위 밖은 날짜를 갖고 있다"가 실패로 잡혔는데, 판정 경로가 둘로 늘어난 것이 맞으므로 검증을 나눴다. 지목일이 없는 범위 밖은 원문을 다시 읽어 체결일이 수집 시작 전인지 확인한다.

무엇이 남았나
19건. 뒤이어 10-2·10-3 에서 7건까지 줄었다.

이 규칙은 가정 하나에 기댄다. 공시유보였다가 나중에 해제되며 처음 공시되는 계약이면 수주일자가 과거여도 최초 공시가 코퍼스 안에 있을 수 있다. 다만 그 경우 되짚기가 원본에 닿으므로 판정 대상이 되지 않는다.

## 9. 용어를 정의 없이 만들어 썼다

무엇을 했나
정정 연결을 설명하며 후보·단계·레이어·체인 같은 말을 그때그때 만들어 썼다.

무엇이 문제였나
"단계"는 이미 S1~S11에 배정된 말이다. `CLAUDE.md` 기호표에 못박혀 있는데 연쇄 정정의 되짚기 횟수를 가리키는 데 갖다 썼다. 사용자가 D7의 3층 판정과 혼동했다.

어떻게 알았나
사용자 지적. "제발 명칭 좀 통일해라, 계속 새로운 명칭 생성하지 마라"였다.

어떻게 고쳤나
`GLOSSARY.md`에 고정 용어 절을 신설했다. 정정본·원본·지목일·후보·연쇄 깊이·미연결 사유 여섯 개로 제한하고 각각을 DB 컬럼에 대응시켰다.

겹치는 말도 못박았다.

```
단계   S1~S11 에만
층     D7 판정에만
작업   W1~W10 에만
계층   DB 테이블 묶음에만
레이어  쓰지 않음
```

`SCHEMA.md`의 관계 계층 서술도 이 여섯 개로 다시 썼다.

무엇이 남았나
없다. 다만 이건 문서 문제로 끝나지 않았다. 후보와 원본을 구분 없이 쓴 것이 8번의 사유 오분류를 늦게 발견한 원인이다. 말이 흐리면 데이터의 오류도 안 보인다.

추가로 발견한 것

무엇이 남았나
없다.

## 11. 같은 날 다른 계약의 원본을 잡고 있었다

무엇을 했나
지목일의 후보를 유형으로 좁히고, 그중 정정본이 아닌 것을 원본으로 택했다. "최초제출일은 정의상 원본의 제출일"이라는 근거였다.

무엇이 문제였나
같은 날 여러 계약을 공시하는 기업이 있다. 그 경우 무관한 계약의 원본이 잡힌다.

```
한화오션 정정본   계약명 FCS(필드제어설비) 1기   수주일자 2022-01-10
지목일 20231222 후보 3건
    정정  수상함 1척            수주 2018-12-06   → 코퍼스 밖
    정정  FCS(필드제어설비) 1기   수주 2022-01-10   → 코퍼스 밖   진짜 짝
    원본  잠수함 1척            수주 2023-12-22   ← 이것이 잡혔다
```

정답은 out_of_scope 인데 잠수함 계약에 연결됐다. "FCS 계약이 언제 체결됐나"를 물으면 잠수함 계약의 날짜를 답한다.

어떻게 알았나
LG에너지솔루션 필드 대조를 넣은 뒤 검증 항목을 하나 더 만들려고, 연결된 두 문서의 수주일자가 같은지 전수 대조했다. 180건 중 25건이 달랐다.

처음에는 표본을 잘못 뽑아 멀쩡한 건을 보고 "정상"이라고 판단할 뻔했다. 불일치 건을 직접 지목해 다시 뽑고서야 보였다.

어떻게 고쳤나
후보를 좁힐 때 계약 식별 항목을 대조하도록 했다. 체결계약명과 수주일자 둘 다 어긋나면 다른 계약으로 보고 뺀다.

기준을 세 번 바꿨다.

```
1차  후보 2건 이상일 때만 · 항목 하나만 어긋나도 뺌 · 비면 되돌림
       오연결 25 → 15. 후보 1건일 때를 안 걸러 6건이 남았다

2차  후보 1건일 때도 · 항목 2개 이상 어긋나야 뺌
       오연결 0. 그러나 연결이 22건 줄었다

3차  식별 항목만 사용 · 둘 다 어긋나야 뺌
       오연결 0. 연결 손실 최소
```

2차가 과했던 이유는 계약금액과 매출액대비를 별개로 센 것이다. 금액이 바뀌면 매출액대비도 함께 바뀐다. 하나의 정정을 둘로 세어 멀쩡한 연결을 다른 계약으로 판정했다.

추가로 발견한 것
1차와 2차를 나란히 돌려 차이를 확인했다. 두 기준으로 각각 적재하고 연결 집합을 뺄셈해 사라진 23건을 전부 열어봤다. 눈대중으로 정했으면 2차를 그대로 뒀을 것이다.

검증에 "계약 연결은 같은 계약을 가리킨다"를 추가했다.

무엇이 남았나
계약명만 다른 8건이 남아 있다. 띄어쓰기나 표현 차이로 보이지만 전수 확인하지 않았다.

```
차륜형장갑차 4차양산  vs  차륜형장갑차 4차 양산사업
```

## 12. LG에너지솔루션 — 정정사항에 없는 항목으로 갈랐다

무엇을 했나
후보 원본이 둘 이상 남은 건을 정정 전 값으로 갈랐다. 쉼표가 두 번 이상 들어간 큰 숫자를 후보 원문과 대조하는 방식이다.

무엇이 문제였나
공시유보 상태로 냈던 계약은 원본의 금액이 `-` 다. 대조할 숫자가 하나도 없다.

```
LG에너지솔루션  Ford 와 같은 날 두 건을 공시
    exchange_20241015800258   2027-01-01 ~ 2032-12-31   유보기한 2032-12-31
    exchange_20241015800261   2026-10-01 ~ 2030-12-31   유보기한 2030-12-31
```

계약명·계약상대·공급지역·수주일자가 전부 같다. 날짜로도 값으로도 안 갈린다.

어떻게 알았나
사용자가 검토 자료에서 "왜 후보1이 원본이라고 판단했는지 근거가 무엇이냐"고 물었다. 답하려고 원문을 다시 읽으며 정정사항 표를 봤다.

그 자료에는 "정정사항 표 없음"이라고 찍혀 있었는데 원문에는 있었다. 표 추출에 400자 상한을 걸었고 "9. 기타 투자판단" 항목의 값이 그보다 길어 표 끝을 못 찾은 것이다. 검토 자료 생성기의 결함이었다.

어떻게 고쳤나
정정본이 "4. 정정사항"에 적어둔 항목을 파싱하고, 거기 없는 항목으로 후보를 대조하도록 했다.

```
정정사항  계약금액 · 매출액대비 · 유보사유 · 유보기한
계약기간이 없으므로 원본과 같아야 한다  →  후보1
```

같은 건에서 정정 전 값도 후보1을 가리킨다. 유보기한 정정 전 값이 2032-12-31 이고 후보1의 유보기한이 그것이다.

사용자가 원문 XML 153행에서 세 번째 근거를 찾았다. 정정본 본문에 "총 75GWh"라고 적혀 있고 후보1이 75GWh, 후보2가 34GWh다. 다른 계약이 맞다.

해지 공시에도 같은 방법을 썼다. 해지 공시에는 정정사항 표가 없으므로 제외할 항목이 없고 본문의 계약기간이 그대로 대조에 쓰인다. LG 해지 1건이 이것으로 갈렸다.

무엇이 남았나
정정 5건과 해지 1건을 확정했다. 원본 미확정은 7건이 남았다.

## 13. 구조적 한계라고 단정한 것이 아니었다

무엇을 했나
pdf+html 2건을 "원문에 정정 헤더가 없다"며 구조적 한계로 두고, 원본 미확정 7건도 "대조할 항목이 없다"며 남겼다. W3 을 마무리로 보고했다.

무엇이 문제였나
9건 중 8건이 풀 수 있는 것이었다. 근거 없이 닫았다.

어떻게 알았나
사용자 지적. "왜 W3을 마무리라고 하는가, 이 9건이 불가피한 한계로 받아들여야 하는 항목들인가, 왜 그렇게 속단하는가"였다.

확인해 보니 셋 다 내가 안 본 것이었다.

어떻게 고쳤나
PDF 2건. 뷰어 HTML 에 본문이 없는 것은 맞지만 PDF 에는 있다. `pypdf` 가 이미 설치돼 있었고 5쪽만 읽으면 0.4초에 지목일이 나온다. "2건을 위해 PDF 파서를 만드는 것은 값어치가 낮다"고 썼는데, 값어치 계산의 전제인 비용이 틀렸다.

```
KB금융    1,085쪽 → 5쪽에서 발견   0.4초   지목일 20260313
한화오션     252쪽 → 5쪽에서 발견   0.2초   지목일 20240513
```

순환 5건. 되짚기가 제자리를 돌면 `ambiguous` 로 기록하고 있었다. 그러나 방문한 지목일 어디에도 원본이 없었다면 모호한 것이 아니라 원본이 코퍼스에 없는 것이다. `out_of_scope` 로 바꿨다.

서식 파싱 1건. 한미약품 건은 대조할 항목이 없는 것이 아니라 내가 못 뽑고 있었다. `_BODY_MARKS` 에 계약 서식만 넣어두어 투자판단 서식에서 본문 시작을 못 찾았고, 문서 전체를 정정사항 표로 취급해 유보기한이 "정정된 항목"으로 잘못 걸러졌다.

대조 방식 1건. 삼성E&A 건은 전부 일치를 요구한 것이 문제였다. 되짚기가 깊으면 중간 정정본들이 값을 바꿔놓아 원본과 어긋나는 항목이 남는다. 교집합에서 점수로 바꿨다.

```
정정본 종료일 2026-03-31
후보A 2025-10-31 · 후보B 2027-04-30    어느 쪽과도 다르다
그러나 계약명과 시작일은 후보A 와 같다     → 후보A
```

```
연결          525 → 529
원본 미확정      7 →   0
날짜 추출 실패    2 →   0
연결 가능분  98.3% → 100.0%
```

무엇이 남았나
없다. 다만 이건 코드 문제가 아니라 판단 문제였다.

"구조적 한계"라고 쓰면 검토가 멈춘다. 실제로는 세 건 모두 내가 확인하지 않은 것을 확인했다고 쓴 것이다. PDF 라이브러리가 있는지 안 찾아봤고, 순환의 의미를 따지지 않았고, 파싱 실패를 데이터 부재로 읽었다.

앞으로 "구조적 한계"는 무엇을 확인했는지 함께 적는다. 확인 없이 쓰면 그건 한계가 아니라 미확인이다.

## 14. 순환을 "원본 없음"으로 읽은 것도 틀렸다

무엇을 했나
13번에서 되짚기가 제자리를 도는 5건을 `out_of_scope`로 바꿨다. "방문한 지목일 어디에도 원본이 없었으니 원본이 코퍼스에 없다"는 논리였다.

무엇이 문제였나
원본이 코퍼스에 있었다. 4건이 그랬다.

```
에코프로비엠   정정본 20241022  →  원본 20230523  투자목적·투자금액·결의일 동일
엘에스일렉트릭  정정본 20240813  →  원본 20240521  정정 전 금액 80,300,000,000 과 일치
```

어떻게 알았나
사용자 질문. "당일에 원본을 갈음하는 경우라면 out_of_scope 가 아니라 다른 분류가 맞지 않나"였다.

답하려고 원문을 다시 열었더니 에코프로비엠 이사회결의일이 2023-05-23이었다. 정정본 접수는 2024-10-22다. 1년 반 전 결정이면 원본도 그때 나왔을 것이라 짐작하고 전체 목록을 뽑아보니 20230523에 원본이 있었다.

내 논리의 구멍은 "지목일을 따라가 못 찾았다"를 "코퍼스에 없다"로 읽은 것이다. 지목일이 틀렸을 가능성을 빼놓았다.

어떻게 고쳤나
원문 헤더를 확인하니 파싱은 정확했다. 문서 자체가 자기 접수일을 원본 제출일로 적어두었다.

```
에코프로비엠  접수 20241022   원문 "2. 정정관련 공시서류제출일 | 2024-10-22"
```

공시자의 기재 오류다. 날짜를 못 믿으므로 내용으로 찾도록 했다. 같은 기업·같은 유형의 이전 원본 중 항목이 가장 많이 맞는 것을 택한다.

`parse_contract_fields` 에 투자목적·투자금액·결의일을 추가했다. 신규시설투자 서식에는 계약 항목이 없어 대조할 것이 없었다.

추가로 발견한 것
첫 구현이 오연결을 만들었고 검증이 잡았다.

```
한전기술  정정본 신고리 5,6호기 원자로계통설계    수주 2014-08-28
          붙은 원본 신한울 3,4호기 설계용역      수주 2023-03-29
          계약상대가 둘 다 두산에너빌리티라 점수를 받았다
```

11번에서 만든 식별 항목 가드를 내용 검색에는 안 걸었다. 같은 가드를 한 곳에서 쓰도록 고쳤다.

무엇이 남았나
없다. 다만 13번에서 "구조적 한계는 무엇을 확인했는지 함께 적는다"고 써놓고 바로 다음 항목에서 같은 실수를 했다. 순환 5건을 "원본이 코퍼스에 없다"고 단정할 때 그 기업의 문서 목록을 뽑아보지 않았다.

확인 방법이 어렵지도 않았다. 같은 기업 같은 유형 문서를 나열하는 조회 한 번이면 됐다.

## 15. 정정사항 항목명을 못 알아본 표기가 여럿이었다

무엇을 했나
정정본이 고쳤다고 적은 항목을 알아내려고, 정정사항 블록에 필드명이 들어 있는지 문자열로 확인했다.

무엇이 문제였나
필드명이 항목명의 부분문자열이 아닌 경우가 있었다.

```
"수주일자"  는  "계약(수주)일자" 에 들어 있지 않다      괄호가 끼어 있다
"5. 계약기간"  만 적힌 경우 43건                    시작일·종료일이 안 걸린다
"2. 계약내역"  만 적힌 경우 52건                    계약금액·매출액대비가 안 걸린다
```

두산퓨얼셀 정정본은 `7.계약(수주)일자 | 2026-02-12 | 2025-02-12` 이라고 명시했는데도 대조에서 빼지 못했다. 그래서 원본과 값이 다른 채로 검토 목록에 남았다.

어떻게 알았나
사용자 지적. 원본 122행을 보고 "수주일자를 잘못 읽은 것 아니냐"고 물었다. 122행은 계약기간 시작일이고 수주일자는 138~139행이라 내 추출은 맞았지만, 확인하려고 정정사항 표를 다시 읽다가 발견했다.

어떻게 고쳤나
거래소 정정본 전건의 정정사항 항목명을 전수 집계했다. 표기가 20종이 넘었다. 절 이름만 적힌 경우도 받도록 마커를 넓혔다.

추가로 발견한 것
넓혔더니 LG에너지솔루션이 미확정으로 돌아갔다. "9. 기타 투자판단" 값 칸에 "공급물량 및 계약기간 등의 계약조건은 …" 이라는 문장이 있어 계약기간이 정정된 것으로 오인됐고, 후보를 가를 항목이 전부 사라졌다.

블록 전체가 아니라 짧은 칸에서만 찾도록 좁혔다. 항목명은 40자를 넘지 않는다.

"과잉 제외는 안전하다"고 주석에 써두었는데 틀렸다. 과잉 제외는 오연결을 만들지 않을 뿐이고, 연결을 잃는 손해는 낸다.

그리고 `_body()` 가 표지에서 150자 물러나 정정사항 꼬리를 끌어들이고 있었다. 삼성전자 정정본에서 계약명 자리에 "체결계약명, 계약상대, 주요 계약조건은 유보기한일의 다음 영업일에 공개될 예정임" 이 뽑혔다. 물러날 이유가 없어 제거했다.

무엇이 남았나
없다.

## 판정이 끝난 7건

식별 항목이 하나만 어긋나는 계약 연결이다. 사용자가 원문으로 전건 확인했다.

| 건 | 어긋난 항목 | 판정 근거 |
|---|---|---|
| 두산퓨얼셀 1건 | 수주일자 2025-02-12 / 2026-02-12 | 원본 오타 |
| 삼성E&A 4건 | 수주일자 2024-03-27 / 2024-03-29 | 선언 없이 2일 변경. 계약금액 정정 전 값이 원본과 일치 |
| 한전기술 1건 | 계약명 괄호 앞 공백 | 표기 차이 |
| 현대로템 1건 | 계약명 "사업" 접미 유무 | 표기 차이 |

두산퓨얼셀 오타 판정의 근거가 셋인데 서로 성격이 다르다.

```
문서 내부 모순    수주일자 2026-02-12 > 계약 종료일 2026-01-31       사용자
실무 관행        공시는 체결 후에 내는데 접수일보다 1년 뒤다          내가 댄 것
발행사의 진술     정정본이 7.계약(수주)일자를 2025-02-12 로 고쳤다     둘 다 놓쳤다가 발견
```

첫째가 가장 강하다. 관행을 몰라도 문서 안에서 모순이 보인다. 나는 둘째만 댔고, 셋째는 파서가 못 잡아 목록에 남아 있던 것이다.
