### 공시 검색이 어려운 이유는 문서가 길어서가 아니다

다루는 자료는 70개사의 2023년 1월부터 2026년 3월까지 공시 4,204건이다.

| 항목 | 규모 |
|---|---|
| 기업 | 70개사 (KOSPI 61 · KOSDAQ 9) |
| 기간 | 2023-01-01 ~ 2026-03-31 |
| 원문 | 4,204건 · 5.56 GB |
| 절 | 122,871개 |
| 검색 조각 | 171,564개 |

문서가 많은 것은 기계가 감당한다. 진짜 어려움은 다른 데 있다.

### 어려움 1 — 같은 내용을 회사마다 다르게 부른다 (정규화, 매칭표로 해결)

법정 목차는 같아도 그 아래 절 제목은 회사가 정한다. 실제로 세어 봤다.

| 같은 항목 | 이름 가짓수 | 예 |
|---|---|---|
| 차입금 | 19가지 | 차입금 및 사채 · 장ㆍ단기금융부채 · 차입금과 사채 · 차입금 등 |
| 종속기업·관계기업 투자 | 31가지 | 종속기업투자 · 관계기업 및 공동기업투자 · 종속기업, 공동기업 및 관계기업 투자 |
| 고객과의 계약에서 생기는 수익 | 23가지 | 수익 · 매출액 · 계약자산과 계약부채 · 건설계약 |

사용자가 "빚이 얼마야" 라고 물으면 어느 절을 봐야 하는지 회사마다 답이
다르다. 이름이 다르니 이름으로 찾는 방법이 통하지 않는다.

### 어려움 2 — 질문의 말과 문서의 말이 다르다: 워딩의 차이 (범용성, 일반성 vs 전문성, 매칭표로 해결)

사용자는 짧고 일상적인 말로 묻고 공시는 길고 전문적인 말로 쓰여 있다.

```
사용자    전속 연예인들 회계 처리가 어떻게 돼?
공시      무형자산 — 전속계약금
```

두 표현은 글자가 하나도 안 겹친다. 낱말이 겹쳐야 찾아내는 검색으로는
닿지 않는다.

### 어려움 3 - 하나의 금액이 여러 섹션에 걸쳐서 다양한 형태로 변형되어 등장한다. 이 맥락을 AI가 이해하는 게 어려웠다.

### 3-1. 핵심 장치 — 매칭표

공시의 목차는 법으로 정해져 있다. 어느 회사 사업보고서를 열어도 큰 뼈대가
같다.

| 대분류 | 내용 |
|---|---|
| I | 회사의 개요 — 소개 · 연혁 · 주식 총수 · 정관 |
| II | 사업의 내용 — 무엇을 팔아 돈을 버는가 |
| III | 재무에 관한 사항 — 재무제표와 주석 · 배당 |
| IV | 이사의 경영진단 — 경영진이 스스로 쓴 진단 |
| V~XI | 감사 · 이사회 · 주주 · 임원 · 계열회사 · 대주주 거래 |
| XII | 상세표 — 수주 · 특허 등 부속 표 |

매칭표는 이 목차의 각 절마다 "이 절을 가리키는 말" 을 사람이 적어 둔 표다.

| 질의에 나오는 말 | 가리키는 절 |
|---|---|
| 주주환원 · 배당정책 · 배당금 | III/6 배당에 관한 사항 |
| 이사회 · 사외이사 · 이사 선임 | VI/1 이사회에 관한 사항 |
| 전속계약금 · 소속 연예인 | III 무형자산 주석 |
| 빚 · 부채 규모 · 대출 | III 차입금 주석 |

질의에 이 말이 나오면 해당 절을 곧바로 지목한다. 통계로 추측하는 대신
사람이 정한 대응을 쓴다.

### 왜 사람이 만들어야 하는가: 매칭표를 만들게 된 배경은 생략 -> 의도, 유의점, 핵심 기능, 요구 사항, 우리가 어떻게 노가다했는지(포장) 납득시키는 게 포인트, 우리가 이걸 어떻게 차별화 포인트로 가져가는지, 구체적으로 AI의 한계를 짚어주는 것(사례까지 들어서라도 한계를 밝혀주는 것) 서사를 구체적으로. 일반어, 범용어 -> 약간 이런 뉘앙스 말 쓰기

자동으로 만들어 봤다. 프로그램이 "그 절에만 자주 나오는 말" 을 뽑게 했더니
이런 결과가 나왔다.

| 절 | 자동으로 뽑힌 말 |
|---|---|
| 이사회에 관한 사항 | 권한사항 · 위원회명 · 의결사항 · 출석률 · 개최일자 |
| 감사제도에 관한 사항 | 결격 · 교육일자 · 활동내역 · 불참 |
| 계열회사 현황 | 회사수 · 기업명 · 상장여부 · 비상장 |

전부 표의 머리글이다. 통계적으로는 완벽하게 그 절만 가리키지만 아무도
그런 말로 질문하지 않는다. 정작 "이사회" 는 여러 절에 나와 변별력이
낮다는 이유로 잘려 나갔다.

기계는 그 절에만 있는 말을 찾고 사람은 그 절을 부르는 말을 안다. 이
차이가 매칭표를 사람이 만들어야 하는 이유다.

### 매칭표가 하는 일 — 생성 모델에 맥락을 준다 + 위랑 합치기

생성 모델은 주어진 근거만 보고 답을 쓴다. 근거가 맞으면 답이 맞고 근거가
틀리면 아무리 좋은 모델도 틀린다.

매칭표는 모델을 바꾸지 않는다. 모델에게 무엇을 보여줄지를 바로잡는다.
"이 질문은 배당 절을 봐야 한다" 를 사람이 미리 정해 두면 모델은 배당 절만
읽고 답한다. 엉뚱한 절을 읽고 그럴듯하게 지어낼 여지가 줄어든다.

          4-1 두 갈래 저장 — 값은 표로, 설명은 글로   (지금 3-2)
          4-2 검색 세 갈래                        (지금 3-3)
          4-3 지어내지 않게 하는 장치               (지금 3-4)

     4-3 은 평가지표 4번(근거 기반)과 7번(정보한계 대응)을 정면으로
     겨냥하는 부분이라 눈에 띄게 두는 편이 좋다. -->

공시 질의는 성격이 둘로 갈린다.

```
"매출액이 얼마인가"          숫자 하나.  정확해야 한다
"어떤 사업을 하는 회사인가"    설명.  맥락이 있어야 한다
```

앞의 것은 미리 표로 뽑아 두었다.

| 표 | 건수 |
|---|---|
| 재무 수치 | 38,893 |
| 주요사항보고 | 598 |
| 지분공시 | 1,083 |
| 공급계약 | 1,169 |

조회하면 바로 나오므로 검색 오차가 없다. 뒤의 것은 본문에서 찾는다.
여기에 매칭표와 검색이 쓰인다.

### 3-3. 검색 — 세 갈래를 합친다 -> 이건 4. 시스템 구성도에서 어필하는 게

| 갈래 | 하는 일 |
|---|---|
| 낱말 검색 | 질문의 말이 그대로 들어 있는 곳을 찾는다 |
| 의미 검색 | 말이 달라도 뜻이 비슷한 곳을 찾는다 |
| 매칭표 | 사람이 정해 둔 절을 지목한다 |

앞의 둘을 합쳐 순위를 매기고 매칭표가 지목한 절을 위로 끌어올린다.
매칭표가 틀려도 후보에서 빼지는 않으므로 잘못 짚어도 정답을 잃지 않는다.

### 3-4. 지어내지 않게 하는 장치 -> 이건 4. 시스템 구성도에서 어필하는 게

생성 지시에 네 가지를 명시한다.

```
주어진 근거에만 있는 내용으로 답한다
확인할 수 없으면 확인되지 않음이라고 적는다
주가 전망 · 투자 추천을 하지 않는다
답변 끝에 근거로 삼은 공시를 적는다
```

생성이 끝나면 출력 검증을 한 번 더 한다. 답변에 나온 숫자가 근거 안에
실제로 있는지 대조하고, 없으면 경고를 남긴다.

## 4. 시스템 구성도

```
   [사용자 · 평가자]
          │  GET /answer?question_id=&question=
          ▼
   ┌──────────────────────────────┐
   │  API 서버 (FastAPI)           │   네이버 클라우드
   └──────────────────────────────┘
          │
          ▼
   ┌──────────────────────────────┐
   │  질의 해석                     │  기업 · 연도 · 보고서 종류 · 검색어
   └──────────────────────────────┘
          │
          ├───────────────┬───────────────┐
          ▼               ▼               ▼
   ┌───────────┐   ┌───────────┐   ┌───────────┐
   │  매칭표     │   │ 낱말 검색   │   │ 의미 검색   │
   │  사람이 만든 │   │  BM25     │   │  임베딩     │
   │  절 지목    │   │           │   │           │
   └───────────┘   └───────────┘   └───────────┘
          └───────────────┴───────────────┘
                          ▼
                   ┌───────────┐
                   │  근거 조립  │  절 단위로 4개까지
                   └───────────┘
                          ▼
                   ┌───────────┐
                   │ HyperCLOVA │  답변 생성
                   │     X      │
                   └───────────┘
                          ▼
                   ┌───────────┐
                   │  출력 검증  │  숫자가 근거에 있는지
                   └───────────┘
                          ▼
        {question_id, question, retrieved_context,
         think_trace, answer}
```

데이터는 SQLite 한 파일에 담았다. 절 122,871개, 조각 171,564개, 값 표
여러 종이 한곳에 있어 조회와 검색이 같은 자리에서 일어난다.

## 5. 주요 기능 흐름

질의 하나가 처리되는 과정을 열한 단계로 나눴다.

| 묶음 | 단계 |
|---|---|
| 대상 좁히기 | S1 질의 해석 → S2 대상 확정 → S3 문서 선별 |
| 근거 확보 | S6 값 조회 · S7 본문 검색 · S8 연산 |
| 응답 생성 | S9 근거 조립 → S10 답변 생성 → S11 출력 검증 |

앞의 셋과 뒤의 셋은 모든 질의에서 실행된다. 가운데는 질의 성격에 따라
갈린다. 숫자를 묻는 질의는 값 조회로, 설명을 묻는 질의는 본문 검색으로
간다.

각 단계가 무엇을 했는지 기록해 `think_trace` 로 함께 돌려준다. 어느 절을
왜 골랐는지, 매칭표가 무엇을 지목했는지, 검증에서 무엇이 걸렸는지가 그대로
보인다.

## 6. 사용자 시나리오

### 시나리오 1 — 숫자를 묻는다

```
질문   삼성전자의 2025년 연결기준 매출액은 얼마인가

       근거로 해당 재무제표 절을 함께 제시한다

```

### 시나리오 2 — 설명을 묻는다

```
질문   삼성전자의 주주환원 정책이 어떻게 되는지 알려줘

처리   매칭표가 "주주환원" 을 보고 배당에 관한 사항을 지목한다
       낱말 · 의미 검색 결과와 합쳐 순위를 매긴다
       상위 절의 원문을 근거로 모아 생성 모델에 넘긴다

답변   배당 정책 요약 + 근거로 쓴 절 이름
```

### 시나리오 3 — 답할 수 없는 것을 묻는다

```
질문   삼성전자 주가가 오를까
답변   공시를 근거로 하는 서비스라 주가 전망은 제공하지 않는다
       공시에서 확인 가능한 것은 배당 정책과 자기주식 취득 계획이다
```

모른다고 말하는 것을 실패로 두지 않았다. 지어내는 쪽이 실패다.

## 7. 기대효과와 확장성

### 기대효과

| 항목 | 내용 |
|---|---|
| 근거가 분명하다 | 답변마다 어느 공시 어느 절에서 나왔는지 제시한다. 사용자가 원문으로 바로 확인할 수 있다 |
| 과정이 보인다 | 어떤 절을 왜 골랐는지 기록으로 남긴다. 틀렸을 때 어디서 틀렸는지 짚을 수 있다 |
| 모르는 것을 안다 | 값 표에 없고 검색에도 안 걸리면 없다고 말한다. 그럴듯한 문장으로 덮지 않는다 |

### 확장성

매칭표는 목차 구조에 붙어 있고 회사 이름에 붙어 있지 않다. 공시 목차는
법으로 정해져 있으므로 새 기업이 늘어도 표를 다시 만들 필요가 없다. 그
기업의 공시를 넣기만 하면 기존 표가 그대로 작동한다.

그대로 적용된다.

표를 고치는 데 개발이 필요 없다는 점도 있다. 검색 결과가 마음에 안 들면
표에 한 줄을 더하면 된다. 모델을 다시 학습시키거나 코드를 고치지 않는다.

수치를 3-1 절에 넣는다. 숫자 하나가 논리 열 줄보다 강하다.
