# 참고. 데이터 파일 형식 기초

이 데이터셋에는 7가지 파일 형식이 섞여 있다. 각 형식이 왜 그 자리에 쓰였는지 알면 처리 방식이 자연스럽게 결정된다.

## 한눈에 보기

| 형식 | 정체 | 이 데이터셋에서 | 핵심 주의점 |
|---|---|---|---|
| `.xml` | 태그로 감싼 계층 구조 문서 | 공시 원문 3,147건 (정기·주요사항·지분) | 용량이 크다. 태그가 내용보다 많다 |
| `.xml`이지만 HTML | 웹 문서 형식 | 거래소공시 1,469건 | 확장자가 거짓말을 한다. XML 파서로 못 읽는다 |
| `.jsonl` | 한 줄에 JSON 하나씩 | `manifest.jsonl` 4,204행 | 표준 JSON 파서로 통째로 못 읽는다 |
| `.json` | 키-값 구조 데이터 | 기업 폴더의 `list_*.json` | 파일 전체가 하나의 값이라 전량 로딩 필요 |
| `.csv` | 쉼표로 나눈 표 | `universe.csv` | 타입 정보가 없어 선행 0이 사라진다 |
| `.xlsx` | Excel 통합문서 | `universe.xlsx` | 열람용. 프로그래밍에는 무겁다 |
| `.md` | 사람이 읽는 문서 | `README.md`, `data_filter.md` | 기계 처리 대상 아님 |
| `.pdf` | 인쇄 레이아웃 고정 문서 | 대체 수집 3건 | 텍스트 추출이 어렵고 표 구조가 깨진다 |

## XML

태그로 내용을 감싸 계층을 표현하는 형식이다.

```xml
<DOCUMENT>
  <COMPANY-NAME AREGCIK="00126380">삼성전자주식회사</COMPANY-NAME>
  <BODY>...</BODY>
</DOCUMENT>
```

`<태그 속성="값">내용</태그>` 구조이며, 태그 안에 태그를 넣어 트리를 만든다. 스키마 파일(`.xsd`)로 "이 문서는 이런 태그만 쓸 수 있다"고 강제할 수 있고, DART는 `dart3.xsd` · `dart4.xsd`를 쓴다.

장점은 두 가지다. 계층 구조를 그대로 표현할 수 있어 문서 안의 절·항 관계가 보존된다. 그리고 속성에 메타데이터를 붙일 수 있다. 이 데이터셋에서 `ACODE="ifrs-full_Revenue"`나 `AUNITVALUE="20230101"` 같은 기계 판독용 값이 붙어 있는 것이 이 특성 덕분이다.

단점은 용량과 속도다. 여는 태그와 닫는 태그가 계속 반복돼 실제 내용보다 태그가 더 많은 경우가 흔하다. 이 데이터셋의 사업보고서가 평균 8MB인데, 태그를 걷어낸 순수 텍스트는 그 절반 이하다.

주의할 점은 인코딩 선언과 실제 인코딩이 다를 수 있다는 것, 그리고 태그가 하나라도 어긋나면 엄격한 파서가 문서 전체를 거부한다는 것이다.

주로 쓰이는 곳은 문서 구조가 복잡하고 표준화가 필요한 영역이다. 전자공시, 금융 표준, 문서 교환 규격 등.

## HTML

XML의 사촌이지만 규칙이 훨씬 느슨하다. 웹 브라우저가 조금 깨진 문서도 최대한 화면에 그려주도록 설계됐기 때문이다.

```html
<html><head><meta charset="euc-kr"></head>
<body><table><tr><td>계약금액</td><td>22,764,764,160,000</td></tr></table></body></html>
```

닫히지 않은 태그나 잘못 중첩된 태그를 허용한다. 이것이 XML 파서로 읽으면 깨지는 이유다. HTML은 관대한 파서(예: BeautifulSoup)로 읽어야 한다.

이 데이터셋에서는 거래소공시 1,469건이 HTML인데 파일 확장자만 `.xml`이다. 확장자를 믿지 말고 `doc_group == "exchange"`로 판별해야 한다.

## JSON

키와 값의 쌍으로 데이터를 표현한다.

```json
{"corp_name": "삼성전자", "stock_code": "005930", "n_periodic": 13}
```

중괄호는 객체, 대괄호는 배열이다. 사람도 읽을 수 있고 기계도 읽을 수 있으며 프로그래밍 언어를 가리지 않아, 오늘날 데이터 교환의 사실상 표준이다.

단점은 파일 전체가 하나의 값이라는 점이다. 100MB짜리 JSON에서 첫 줄만 보고 싶어도 전체를 메모리에 올려야 한다. 대용량 로그나 레코드 모음에는 맞지 않는다.

## JSONL (JSON Lines)

방금 말한 JSON의 단점을 해결한 형식이다. 한 줄이 완전한 JSON 하나이고, 줄바꿈으로 레코드를 구분한다.

```
{"doc_id": "periodic_20230515002335", "corp_name": "삼성전자", ...}
{"doc_id": "periodic_20230814001067", "corp_name": "삼성전자", ...}
```

장점은 한 줄씩 읽어 처리할 수 있다는 것이다. 파일이 아무리 커도 메모리에 한 줄만 올리면 되고, 새 레코드는 파일 끝에 한 줄 덧붙이면 끝이다.

단점이자 함정은 이것이 표준 JSON이 아니라는 점이다. 전체가 하나의 배열로 감싸여 있지 않으므로 일반 JSON 파서로 파일을 통째로 읽으면 오류가 난다. 반드시 줄 단위 옵션을 켜야 한다.

```python
manifest = pd.read_json("manifest.jsonl", lines=True)   # lines=True 필수
```

이 데이터셋의 `manifest.jsonl`이 4,204행이다. 문서 메타데이터처럼 "같은 모양의 레코드가 아주 많은" 데이터에 적합하다.

## CSV

쉼표로 열을 나눈 표다. 가장 단순하고 가장 오래됐다.

```
corp_code,stock_code,corp_name,market_cap
00126380,005930,삼성전자,14586465
```

장점은 어디서나 열린다는 것이다. Excel, 메모장, 어떤 프로그래밍 언어에서도 읽힌다. 용량도 가볍다.

단점은 타입 정보가 전혀 없다는 것이다. `005930`이 숫자인지 문자열인지 파일 자체는 모른다. 그래서 프로그램이 숫자로 추측해 읽으면 `5930`이 되어 선행 0이 사라진다. 이 데이터셋에서 `corp_code`·`stock_code`에 `dtype=str`을 반드시 지정해야 하는 이유다.

인코딩 문제도 잦다. `universe.csv`는 UTF-8 BOM으로 저장돼 있는데, BOM은 파일 맨 앞에 붙는 3바이트 표식으로 "이 파일은 UTF-8이다"라고 알려주는 역할을 한다. Excel이 한글 CSV를 열 때 글자가 깨지는 것을 막기 위해 넣는다. 다만 BOM을 모르는 프로그램은 첫 컬럼명 앞에 이상한 문자가 붙은 것으로 읽기도 한다. pandas는 자동 처리한다.

## XLSX

Excel 통합문서 형식이다. 내부적으로는 여러 XML 파일을 압축해 묶은 것이다.

장점은 타입이 보존된다는 것이다. `005930`을 문자열로 저장했으면 문자열로 읽힌다. 서식·수식·여러 시트도 담을 수 있어 사람이 열어보기에 좋다.

단점은 프로그래밍 로딩이 무겁다는 것이다. 별도 라이브러리(`openpyxl`)가 필요하고 CSV보다 느리다.

이 데이터셋이 `universe.csv`와 `universe.xlsx`를 둘 다 제공하는 이유가 여기 있다. 눈으로 볼 때는 xlsx, 코드로 읽을 때는 csv를 쓰라는 뜻이다.

## PDF

인쇄 레이아웃을 고정하는 형식이다. 어느 기기에서 열어도 똑같이 보인다.

문제는 그 고정이 "글자를 페이지의 어느 좌표에 그릴 것인가"로 구현돼 있다는 점이다. 문서 안에 "이것은 표의 3행 2열"이라는 정보가 없다. 그래서 텍스트를 뽑으면 표가 뭉개지고 읽는 순서가 뒤엉킨다.

이 데이터셋에는 DART가 원본 XML을 제공하지 않은 3건만 PDF로 들어 있다. `file_format == "pdf+html"`로 식별된다.

## 인코딩 — 형식과 별개인 축

파일 형식과 문자 인코딩은 다른 문제다. 같은 XML이라도 UTF-8일 수도, EUC-KR일 수도 있다.

| 용어 | 의미 |
|---|---|
| UTF-8 | 전 세계 문자를 담는 표준. 이 데이터셋의 실제 인코딩 |
| EUC-KR | 한글 전용 구형 인코딩. 거래소공시 HTML에 이렇게 선언돼 있지만 실제 내용은 UTF-8 |
| BOM | 파일 맨 앞 3바이트 표식. UTF-8임을 알리는 용도 |
| NFC / NFD | 한글 한 글자를 완성형 하나로 저장할지, 자모로 쪼개 저장할지의 차이 |

선언된 인코딩과 실제 인코딩이 다를 수 있다는 것이 이 데이터셋의 실제 사례다. 거래소공시 HTML은 `charset=euc-kr`이라 적혀 있지만 UTF-8로 읽어야 한다.

1. 폴더명이 NFD(자모 분리)인데 manifest의 `file_path`는 NFC(완성형)다. 변환 없이 열면 4,204건 전부 실패한다.
> NFD와 NFC가 무슨 의미인가? 무슨 차이인가? 정규화 변환이 왜 해답인가? 정규화 변환하면 무엇이 달라져서 데이터셋을 구축할 수 있게 되는가?
>
> 답 — 한글 '삼'을 컴퓨터에 저장하는 방식이 두 가지다. NFC는 완성된 글자 하나로(`0xC0BC`), NFD는 자모 셋으로 쪼개서(`ㅅ`+`ㅏ`+`ㅁ`) 저장한다. 화면에는 똑같이 '삼'으로 보이지만 컴퓨터에게는 전혀 다른 문자열이다. 파일 열기는 이름이 바이트 단위로 정확히 일치할 때만 성공하므로, 표기법이 다르면 "그런 파일 없음"이 된다. 정규화 변환은 한쪽 표기법으로 통일하는 작업이다. manifest의 NFC 경로를 NFD로 바꾸면 파일시스템의 실제 이름과 일치해 파일이 열린다. 열려야 원문을 읽고, 읽어야 파싱·색인이 가능하다. 이 변환 하나가 4,204건 전체 접근의 전제조건이다.
2. 거래소공시 1,469건은 확장자만 `.xml`이고 실제로는 HTML이다. XML 파서로 열면 깨진다.
3. 사업보고서 1건이 평균 36만 토큰이다. HCX 최대 입력(32,768 토큰)의 11배다.
> 그렇다면 무슨 문제가 생기는가? HCX가 사업보고서 1건도 제대로 처리할 수 없다는 뜻인가?
>
> 답 — 통째로 넣을 수 없다는 뜻이지 처리하지 못한다는 뜻이 아니다. 필요한 부분만 잘라서 넣으면 정상 처리된다. 진짜 문제는 그 다음이다. 무엇을 잘라 넣을지 우리가 정확히 골라야 하고, 잘못 고르면 답이 문서 안에 있는데도 못 찾는다. 즉 한계는 모델 성능이 아니라 검색 설계에 있다. 반대로 거래소공시·주요사항보고서·지분공시는 통째로 넣어도 한도의 3~27%라 이 문제가 없다.
4. 재무 XBRL 태그가 FY2023 구간에는 없다. 정기공시 894건 중 488건(54.6%)만 보유하며, 2023년과 2024년 3분기까지의 재무 수치는 표 파싱으로만 뽑을 수 있다. 상세는 4-2 참조.

# 2. 반드시 지켜야 할 3가지 함정

## 2-1. 한글 경로 정규화 — NFD vs NFC

파일시스템의 폴더명은 NFD(자모 분리), manifest의 `file_path`는 NFC(완성형)다.

```
파일시스템: 'CJ제일제당' → 0x43 0x4a 0x110c 0x1166 ...   (자모 분리)
manifest  : '삼성전자'    → 0xc0bc 0xc131 0xc804 0xc790   (완성형)
```

manifest 경로를 그대로 쓰면 `Path.exists()`가 전부 False를 반환한다. 실측으로 4,204건 중 4,054건이 열리지 않았다.

해결 코드

```python
import unicodedata as ud, os
from pathlib import Path

CORPUS = Path(r"assets/공시/공시/corpus")

def resolve(rel_path: str) -> Path:
    """manifest의 file_path(NFC) → 실제 파일시스템 경로(NFD)"""
    return Path(os.path.join(str(CORPUS), ud.normalize("NFD", rel_path).replace("/", os.sep)))
```

이 변환을 적용하면 4,204건 전부 열린다 (미존재 0건 확인).

## 2-2. 거래소공시는 XML이 아니라 HTML

`raw/exchange/` 아래 1,469건은 확장자가 `.xml`이지만 내용은 HTML이다.

```html
<html><head>
  <meta content="text/html; charset=euc-kr" http-equiv="Content-Type">
  <STYLE> .xforms * { font-family: 돋움체;} ... </STYLE>
```

선언된 charset은 euc-kr이지만 실제 파일 인코딩은 UTF-8이다. 소문자 태그(`<td>`, `<tr>`, `<span>`)를 쓰고 DART 표준 태그가 전혀 없다.

나머지 3종(periodic, major, holding)은 DART 표준 XML이다.

```xml
<DOCUMENT xsi:noNamespaceSchemaLocation="dart3.xsd">
  <DOCUMENT-NAME ACODE="11013">분기보고서</DOCUMENT-NAME>
  <COMPANY-NAME AREGCIK="00126380">삼성전자주식회사</COMPANY-NAME>
  <BODY><LIBRARY><SECTION-1>...
```

파서를 두 갈래로 나눠야 한다. 유형 판별은 `doc_group == "exchange"`로 하면 된다.

## 2-3. 코드 컬럼의 선행 0

`corp_code`(8자리) · `stock_code`(6자리)는 문자열이다. 숫자로 읽으면 선행 0이 사라진다.

```python
universe = pd.read_csv("universe.csv", dtype={"corp_code": str, "stock_code": str})
manifest = pd.read_json("manifest.jsonl", lines=True,
                        dtype={"corp_code": str, "stock_code": str,
                               "rcept_no": str, "rcept_dt": str})
```

`rcept_no`(14자리)와 `rcept_dt`(8자리)도 같은 이유로 문자열 지정이 필요하다.

## 4-2. DART 고유 태그 — 기계 판독 속성

정기공시·주요사항보고서·지분공시에는 값이 속성으로 정규화되어 들어 있다.

```xml
<TU AUNIT="PERIODFROM" AUNITVALUE="20230101">2023년 01월 01일</TU>
<TU AUNIT="PERIODTO"   AUNITVALUE="20231231">2023년 12월 31일</TU>
<TU AUNIT="PB_TYPE"    AUNITVALUE="1">주권상장법인</TU>
<TE ACODE="ifrs-full_Revenue" ...>258,935,494</TE>
```

| 태그 | 역할 |
|---|---|
| `TU` | 단위/코드값이 있는 셀. `AUNIT`=필드명, `AUNITVALUE`=정규화된 값 |
| `TE` | 추출 대상 셀. `ACODE`=필드 코드 |
| `TD` / `TH` | 일반 표 셀 / 헤더 |

정기공시 30건 표본에서 `ACODE` 3,917종, `AUNIT` 149종이 나왔다. `ACODE`에는 XBRL 표준 태그(`ifrs-full_*`)와 DART 코드(`CRP_NM`, `INV_PRM` 등), 기업 고유 태그(`entity00164779_*`)가 섞여 있다.

## 4-2-1. XBRL 태그는 시점에 따라 있고 없다

정기공시 894건(원본, XML) 전수 측정 결과다. 기업이나 업종이 아니라 기준기가 보유 여부를 가른다.

| 기준기 | 유형 | 문서 | `ifrs-full_*` 보유율 |
|---|---|---|---|
| 2023-03 | 분기 | 66 | 0% |
| 2023-06 | 반기 | 67 | 0% |
| 2023-09 | 분기 | 68 | 100% |
| 2023-12 | 사업 | 68 | 1.5% |
| 2024-03 | 분기 | 68 | 1.5% |
| 2024-06 | 반기 | 69 | 0% |
| 2024-09 | 분기 | 70 | 0% |
| 2024-12 | 사업 | 70 | 100% |
| 2025-03 이후 전부 | 분기·반기·사업 | 418 | 100% |

전체 894건 중 488건(54.6%)이 보유한다. 2023-09 한 구간만 튀는데 원인은 특정하지 못했다. 시범 적용 구간으로 보이나 이는 추정이다.

태그가 있는 문서에서는 값도 100% 있다. 사업보고서 207건 전수에서 태그가 있고 값이 공란인 경우는 0건이었다.

이것이 만드는 문제는 셋이다. 2023년 전체와 2024년 3분기까지의 재무 수치를 XBRL로 뽑을 수 없다. 참고 질의 set의 "2023년 사업보고서와 2025년 사업보고서를 비교" 유형이 정확히 그 구간을 겨냥한다. 그리고 연도별 비교에서 한쪽은 태그로 확정되고 한쪽은 추측으로 뽑히므로 오차가 한쪽에만 실린다.

## 4-2-2. ACONTEXT와 ADECIMAL — 표 파싱 없이 값을 확정한다

태그 셀에는 `ACODE` 외에 두 속성이 더 붙는다. 이 둘이 표 파싱의 3대 함정을 전부 해소한다.

```xml
<TE ACODE="ifrs-full_Revenue"
    ACONTEXT="CFY2024dFY_ifrs-full_ConsolidatedAndSeparateFinancialStatementsAxis_ifrs-full_ConsolidatedMember"
    ADECIMAL="-6">107,448,752</TE>
```

`ACONTEXT`는 세 정보를 담는다.

| 부분 | 의미 |
|---|---|
| `CFY2024` / `PFY2023` / `BPFY2022` | 당기 / 전기 / 전전기 |
| `dFY` / `eFY` | 기간 개념(손익) / 시점 개념(재무상태) |
| `...ConsolidatedMember` / `...SeparateMember` | 연결 / 별도 |

`ADECIMAL`은 단위 지수다. 사업보고서 30건 실측 분포다.

| 값 | 의미 | 건수 |
|---|---|---|
| -6 | 백만원 | 41,210 |
| -3 | 천원 | 14,525 |
| 0 | 원 | 12,612 |

이 분포는 표 헤더의 `(단위: ...)` 표기를 따로 세어 얻은 분포(백만원 47.3%, 천원 32.8%, 원 8.8%)와 일치한다. 서로 다른 두 경로의 값이 맞아떨어지므로 둘 다 신뢰할 수 있다.

`ACONTEXT` 보유율은 ifrs 태그 98,427개 중 73,466개(74.6%)다. 나머지 25.4%는 속성이 없어 표 구조를 봐야 한다.

## 4-2-3. 같은 태그가 여러 표에 붙는다

XBRL은 재무제표 본문뿐 아니라 주석까지 태깅한다. 매출액이라는 개념 하나가 전사·부문별·지역별로 분해되어 반복 등장하고, 전부 같은 요소명을 쓴다.

사업보고서 20건에서 `ifrs-full_Revenue`가 나타난 표다.

| 표 | 등장 |
|---|---|
| 4. 영업부문 (연결) | 82 |
| 40. 영업부문 (연결) | 82 |
| 2-2. 연결 포괄손익계산서 | 54 |
| 30. 부문별 보고 (연결) | 44 |
| 37. 부문정보 (연결) | 42 |
| 28. 수익 (연결) | 42 |
| 2-2. 연결 손익계산서 | 36 |

손익계산서보다 부문정보 쪽이 많다. 태그명만 보고 값을 채택하면 부문별 분해 값이 전사 매출로 섞여 들어간다.

구분은 `ACONTEXT`의 축 부분으로 한다.

```
손익계산서 : ...Axis_ConsolidatedMember                                    (축 2종)
부문정보   : ...Axis_ConsolidatedMember_ifrs-full_SegmentConsolidationItemsAxis_...
지역별     : ...Axis_ConsolidatedMember_ifrs-full_GeographicalAreasAxis_...
```

축 종류는 손익계산서 안이 2종, 그 외 표가 146종이다. 축이 2종인 것만 고르면 노이즈 대부분이 걸러진다. 다만 그 외 표에서도 축이 2종인 사례가 56건 있어 축만으로는 불완전하고, 표 제목(`TITLE`)을 보조 조건으로 함께 걸어야 한다.

## 4-2-4. 태그를 계정명 사전 자동 수집에 쓴다

태그가 있는 문서에서는 같은 행에 계정명과 태그가 함께 나온다. 둘을 짝지으면 계정명 표기 변형을 자동으로 모을 수 있다. 사업보고서 60건에서 뽑은 결과다.

```
ifrs-full_CostOfSales  ←  매출원가(64) · 매출원가 (주21)(4) · 매출원가 (주20,24)(4)
ifrs-full_GrossProfit  ←  매출총이익(87) · Ⅲ.매출총이익(4) · 매출총이익(손실)(3)
ifrs-full_ProfitLoss   ←  당기순이익(312) · 당기순이익(손실)(303) · 당기순손익(49) · 연결당기순이익(32)
ifrs-full_Assets       ←  자산총계(124) · 자산(123) · 기말 자산(36)
```

태그 1,396종, 계정명 7,107종이 모였다. 손으로 세어 여섯 가지였던 매출 계정명이 자동 수집으로는 76가지가 나온다.

그대로 쓸 수는 없다. 계정명의 30%(2,134/7,107)가 두 개 이상 태그에 매핑된다.

```
"자산"      → ifrs-full_AssetsAbstract  또는  ifrs-full_Assets
"유동자산"  → ifrs-full_CurrentAssets   또는  ifrs-full_CashAndCashEquivalents
```

그리고 4-2-3의 문제 때문에 노이즈가 섞인다. 매출액 사전 76개 안에 "고객", "금융", "기타", "기아(주)" 같은 것이 들어 있다. 부문별·고객별 표에서 첫 칸이 고객명이나 지역명이기 때문이다.

정제 절차가 필요하다.

```
1. 표 종류를 먼저 특정            연결 손익계산서 / 연결 재무상태표
2. 그 표 안에서만 태그-계정명 수집
3. 출현 빈도 하한으로 노이즈 제거
4. 주석 번호 정규화               "매출원가 (주21)" → "매출원가"
5. 모호한 계정명은 표 종류로 구분
```

## 4-2-5. 정리 — 재무 수치 추출 전략

```
1차 경로  ACONTEXT·ADECIMAL 보유 문서 → 속성에서 값·기간·기준·단위를 직접 확정
2차 경로  속성 없는 문서 → 표 파싱 (계정명 사전 + 단위 헤더 + 연도 열 매핑)
검증      1차 경로 488건을 정답지로 2차 경로 파서를 채점한 뒤 확대 적용
```

평가지표 6번이 겨냥하는 것도 공시에 있는 정보를 전달하는 행위가 아니라 질의와 무관한 개인정보를 끌고 들어오는 행위일 가능성이 높다. 다만 이 해석은 추정이며 과제 자료에 명시된 바는 없다.

# 8. 재현용 코드

```python
import pandas as pd, unicodedata as ud, os, re
from pathlib import Path

CORPUS = Path(r"assets/공시/공시/corpus")

def resolve(rel_path: str) -> Path:
    """manifest file_path(NFC) → 실제 경로(NFD)"""
    return Path(os.path.join(str(CORPUS),
                ud.normalize("NFD", rel_path).replace("/", os.sep)))

universe = pd.read_csv(CORPUS/"universe.csv",
                       dtype={"corp_code": str, "stock_code": str})
manifest = pd.read_json(CORPUS/"manifest.jsonl", lines=True,
                        dtype={"corp_code": str, "stock_code": str,
                               "rcept_no": str, "rcept_dt": str})

def load_text(row) -> str:
    """문서 1건의 전체 텍스트 (태그 제거)"""
    parts = []
    for f in sorted(resolve(row.file_path).glob("*.xml")):
        raw = f.read_text(encoding="utf-8", errors="replace")
        parts.append(re.sub(r"\s+", " ", re.sub(r"<[^>]+>", " ", raw)))
    return "\n".join(parts)

# 정정 헤더에서 원본 제출일 추출
PAT_XML  = re.compile(r"정정대상\s*공시서류의?\s*최초제출일\s*[:：]?\s*"
                      r"(\d{4})\s*년?\s*(\d{1,2})\s*월?\s*(\d{1,2})\s*일?")
PAT_HTML = re.compile(r"정정관련\s*공시서류\s*제출일\s*(\d{4})-(\d{2})-(\d{2})")

def original_date(row):
    t = load_text(row)[:60000]
    mo = PAT_XML.search(t) or PAT_HTML.search(t)
    return f"{mo.group(1)}{int(mo.group(2)):02d}{int(mo.group(3)):02d}" if mo else None
```
